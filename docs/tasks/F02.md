# F02 — Login account storage

## STATUS
**VERIFIED_WITH_EXPLICIT_CHECK_TOKEN_AND_LEGACY_CAPTCHA_MIGRATION_UNKNOWNS**

F02 recovers how Login account rows are persisted and separated from runtime online tracking.

Primary evidence is the frozen original inner EXE:
`15c8044f215680d6851c8f901a5dc7d181068d91a8938f2a628077cf21a2df22`.

F01 remains authoritative for the Login widget layout and fixed 100-row UI contract.

## 1. Persistent account store

Login stores account rows in the shared TLM settings file:

`%APPDATA%\TLMTool\settings.ini`

under section:
`[Settings]`

using key:
`accounts`.

Direct original constants in the save-on-destroy path recover:

- `_settings_lock`
- `read_settings`
- section `Settings`
- local row fields `check`, `user`, `pass`, `captcha`, `proxy`
- literal field separator `|`
- literal row separator newline
- key `accounts`
- `write_settings`.

Therefore the on-disk account payload is a **multiline string**:
- one logical account row per line;
- row fields are pipe-separated.

The recovered current save field order is:

`check | user | pass | captcha | proxy`

The exact text token used for the `check` boolean is not source-visible from printable constants and remains **UNKNOWN**.

## 2. Load-time normalized row schema

The original Login loader uses normalized in-memory field names:

1. `check`
2. `username`
3. `password`
4. `captcha_mode`
5. `proxy_env`.

These five field names occur as one compiled tuple in the `_load_config` constant block.

Therefore F02 treats the persistent row as a fixed five-field logical record even though the save-side local variable names use shorter aliases.

## 3. Captcha compatibility token

The same loader block contains the values:

- `Không`
- `Có`
- `Tool`
- `Proxy`.

Current F01 UI modes are:
`Không / Tool / Proxy`.

The extra `Có` value is therefore evidence of a compatibility/migration path for older stored account rows.

Static constants alone do not prove the exact transformation rule for legacy `Có`; F02 does **not** silently rewrite it to `Tool` without source-level proof.

Status:
- legacy token support: VERIFIED
- exact `Có` migration mapping: **EXPLICIT UNKNOWN**.

## 4. _accounts_cache is the storage-side model

Login initialization contains:
- `_accounts_cache`
- `_save_after_id`
- `_saving_enabled`.

Exact original documentation for `_sync_accounts_cache`:

`Ghi data từ widget state vào _accounts_cache (plain dicts).`
`Gọi mỗi lần cần save — đảm bảo cache đúng trước khi ghi file.`

This establishes the intended direction:

```text
row widgets
→ _sync_accounts_cache
→ plain-dict account records
→ serialized settings.ini accounts payload
```

The cache is the persistence-safe representation; Tk Entry/StringVar/Button objects themselves are not the serialized format.

## 5. Fixed 100-row logical model

F01 recovered the exact original statement:
`Số dòng tài khoản cố định — luôn 100 dòng.`

Therefore account storage belongs to a logical **100-row model**.

The screenshot only exposes 17 full rows plus part of row 18, but persistence is not limited to what is currently visible in the Canvas viewport.

## 6. Plan-limited hidden rows preserve data

The original account-limit method documents:

- plan decreases → extra rows move to `_hidden_rows`, preserving FIFO order;
- plan increases → hidden rows are restored first, then blank rows are added if needed;
- the limit is reapplied when server plan payload changes.

F01 also recovered that password-display handling includes entries currently inside `_hidden_rows`.

F02 therefore records:

**hiding a row because of plan limit is not deleting its stored account data.**

The hidden-row collection is part of the preservation lifecycle and must survive save operations.

The exact source statement used by the destroy path to combine visible + hidden rows is not decompiled; the verified requirement is that the storage/cache contract preserves plan-hidden row data.

## 7. Autosave lifecycle

Original `_schedule_save` documentation:

`Debounce auto-save: trì hoãn 300ms, gộp nhiều thay đổi liên tiếp.`

Original `_save_accounts` documentation:

`Lưu tài khoản tự động khi có thay đổi.`

The save flow is therefore:

```text
account-row change
→ _schedule_save
→ cancel/coalesce pending save
→ wait 300 ms
→ _save_accounts
→ _sync_accounts_cache
→ persist accounts
```

Successful save UI text:
`✅ Đã lưu tài khoản`

Failure text:
`❌ Lỗi lưu: ...`

The exact set of every widget event that can schedule a save is feature UI detail; static evidence confirms at least row FocusOut/change handlers, checkbox/captcha/proxy change paths, and the shared debounce service.

## 8. Save-on-destroy is an independent safety path

Login binds:
`<Destroy> → _save_on_destroy`.

Its compiled constant block directly contains the shared settings lock/read/write path plus account serialization fields and delimiters.

This provides a final persistence path even if the last debounced autosave has not yet fired.

The destroy path catches/logs:
`[CONFIG] Login save on destroy error: ...`

F02 does not claim that destroy-save and debounced-save are instruction-for-instruction identical; they converge on the same account storage contract.

## 9. Broader Login config shares the same lifecycle but is distinct from account rows

`_load_config` also contains:
- `game_dir`
- `proxy_mode`
- `schedule_on`
- `login_mode`
- `after_login`
- `schedule_close`
- `schedule_open`
- `shutdown_after_close`.

These are Login configuration fields, not account-record fields.

F02 keeps the account payload schema separate from those scalar Login settings even when they are loaded/saved by the same Login config lifecycle.

## 10. Runtime online-state JSON is NOT the account database

Separate path:
`login_online.json`

Original exact documentation:
`Ghi dict tracking ra login_online.json (cùng thư mục app).`

The writer uses:
- `json.dump`
- UTF-8
- `ensure_ascii`
- `indent`.

The runtime online tracking record contains evidence for fields such as:
- live HWND/tracked-window identity
- `use_proxy`
- `iid`
- `exe_path`
- `profile_idx`
- `port`
- `user`
- row/proxy tracking state.

Exact documentation for mark-online:
`Ghi nhớ cửa sổ đã login OK của row + tô xanh + lưu state file.`
`Lưu proxy riêng (nếu có) để monitor worker reload giữ đúng proxy.`

This is **runtime session tracking**, not persistent credential/account-row storage.

## 11. Online-state restoration

Exact original documentation:

`Sau restart: đọc login_online.json → hwnd còn sống → tô xanh lại.`

Therefore startup restoration:

```text
read login_online.json
→ validate tracked HWND still alive
→ restore row/window tracking
→ repaint Login row online state
```

Dead HWND entries are not equivalent to deleting the account from settings.ini.

## 12. last_login_times.json is also separate

The original contains:
- `last_login_times.json`
- `_load_last_login_times`
- `_save_last_login_times`.

Exact docs:
- `Load last login timestamps từ file.`
- `Lưu last login timestamps ra file (giữ giữa các phiên).`
- `Ghi lại thời điểm login thành công.`

This file persists login timestamps/history used by proxy/login timing logic.

It is not the account credential list.

## 13. Three different persistence concerns

The Login subsystem therefore has three distinct storage concerns:

### A. Account/config persistence
`settings.ini [Settings]`
- account row payload
- game/schedule/Login config fields.

### B. Runtime online window tracking
`login_online.json`
- live HWND/session/proxy tracking
- used to repaint/recover live online state after TLMTool restart.

### C. Login-time history
`last_login_times.json`
- successful-login timestamps preserved between sessions.

These stores must not be merged into one reconstructed JSON file.

## 14. Field-name mapping

Persistence/save-side local names:
- `check`

Normalized cache/load names:
