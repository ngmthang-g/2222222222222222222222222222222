## 1. Master là một HWND runtime riêng, không phải tên nhân vật

State gốc trong `TLMStartTab` chứa:
- `hwnd_master`
- `_prev_hwnd_master`
- `_master_var`
- `_master_hwnd_cache`
- `_hwnd_by_name`
- `_master_radio_buttons`
- `_master_initial_selected`

Điều này tách rõ:
- **giá trị điều khiển thực tế** = HWND master;
- **text người dùng nhìn/chọn** = label/radiobutton;
- mapping label → HWND = `_hwnd_by_name`.

Do đó character name/title chỉ là lớp hiển thị/chọn; sync/layout cuối cùng dùng HWND.

## 2. UI chọn master là danh sách radiobutton động

Gate-B screenshot Xếp lưới trực tiếp cho thấy:
- label `Cửa sổ chính:`
- nhiều radiobutton theo các acc đang có;
- một radio đang selected.

Original binary xác nhận:
- container: `_master_radio_frame`
- `Radiobutton`
- `_master_var`
- callback: `_on_master_change`

Original documentation:

`Cập nhật danh sách radiobutton chọn cửa sổ chính.
Chỉ rebuild khi danh sách hwnd thay đổi (radiobutton không có dropdown nên không lo đóng).`

Vì vậy:
- danh sách master không phải combobox tĩnh;
- nó rebuild theo tập HWND game hiện tại;
- nếu tập HWND không đổi thì không phá/recreate radio vô ích.

## 3. Label master ưu tiên character-info cache

Block `_update_master_combobox` chứa:
- `windows`
- `_master_hwnd_cache`
- `ci_cache`
- literal fallback `Cửa sổ `
- `hwnd_by_name`
- `names`
- `_hwnd_by_name`

C02 đã xác minh worker cache chứa RoleName/HP/... theo HWND.

Kết luận VERIFIED:
- master radio list dùng cache character-info để tạo label khi có tên nhân vật;
- có fallback bắt đầu bằng `Cửa sổ ` khi chưa có tên thật;
- mapping label→HWND được rebuild cùng radio list.

### Explicit unknown
Readable static evidence chưa chứng minh exact format đầy đủ của label fallback/suffix trong mọi trường hợp.

C05 không bịa dạng `Cửa sổ <HWND>` hay `Tên (title)` nếu source expression chưa nhìn thấy.

## 4. Manual master change

Original log:
`[MASTER] Đã chọn cửa sổ chính: ... (hwnd=...)`

`_on_master_change` có local/state:
- selected name;
- `hwnd_by_name`;
- resolved `hwnd`.

Do đó manual radio selection:
1. đọc label từ `_master_var`;
2. resolve qua `_hwnd_by_name`;
3. cập nhật master HWND;
4. log master mới.

## 5. Đổi master khi sync phím/chuột đang bật

Original exact documentation:

`Radiobutton chọn cửa sổ chính. Đơn giản: nếu đang bật đồng bộ phím
chuột → tự tắt (mọi slave unlock). User bật lại sau khi chọn master.`

Đây là behavior quan trọng:

```text
user chọn master mới
↓
_on_master_change
↓
nếu input-sync đang ON
↓
tắt input sync
↓
unlock mọi slave
↓
master mới được nhận
↓
user phải bật lại Đồng bộ phím chuột
```

C05 không thấy bằng chứng rằng đổi master bắt buộc tắt layout-sync; documentation nói cụ thể về **đồng bộ phím chuột**.

## 6. Master luôn đứng đầu trong mọi layout đã recover

### Stack / offset commands
Original doc:

`Cửa sổ chính (master) luôn được xếp ở vị trí đầu tiên (index 0).`

### Auto tile
Original doc:

`Xếp các cửa sổ game theo kiểu xếp ngói, sort theo tên nhân vật.
Cửa sổ chính (master) luôn ở vị trí đầu tiên.`

### Grid arranger
Original doc:

`Xếp cửa sổ theo grid dựa trên thứ tự array.
Cửa sổ chính (master) luôn ở vị trí 0 (góc trên trái),
các cửa sổ khác xếp lần lượt theo sau.`

Kết luận:
- master là phần tử ưu tiên số 0;
- các cửa sổ còn lại là follower/slave về thứ tự layout;
- C06–C11 sẽ phân tích công thức bố trí chi tiết, nhưng quy tắc master-first đã chắc chắn ở C05.

## 7. Master là nguồn input của realtime sync

Original event handlers:
- `_on_master_click`
- `_on_master_scroll`
- `_on_master_move`
- `_on_master_key_press`
- `_on_master_key_release`

Static docs:
- `Handle mouse wheel scroll from master and sync to slaves.`
- `Handle mouse move from master and sync to slaves (throttled).`
- `Chuyển client coord của master sang slave theo tỷ lệ kích thước cửa sổ.`

Therefore:
- input is captured relative to master;
- targets are slave HWNDs;
- coordinates are transformed/scaled when slave client sizes differ.

Deep input details belong to C18/C19, but C05 establishes the role:
**master = input source, all others = sync targets.**

## 8. Master change / close is treated as a synchronization boundary

Static watchdog text:

`Mở khóa slave block quá 10s (mất release — master đóng/đổi/thoát).`

This confirms the system explicitly anticipates:
- master closed;
- master changed;
- master/app exit;

while a synchronized input release may be missing.

The watchdog unlocks stale blocked slaves rather than leaving them permanently locked.

This is a safety consequence of master lifecycle.

## 9. Master selection is runtime, not persisted in Start settings.ini

Recovered Start settings load/save block contains:
- `grid_cols`
- `grid_rows`
- `detached_auto_open`
- `detached_grid`

No master HWND/name key appears in that recovered Start settings block.

This is consistent with C02:
- HWND changes each game open;
- persistent per-character state elsewhere uses RoleName rather than HWND.

C05 therefore classifies master selection as **runtime-derived**, not a stable persisted HWND setting.

## 10. Automatic initialization exists, but exact selection formula is not proven

The original class has:
- `_master_initial_selected`
- `_auto_master_and_sync`

and `_auto_master_and_sync` is referenced during Start initialization.

Its constant block also references:
- `hwnd`
- `_sync_windows_loop`

This proves there is an automatic master/sync initialization path.

### What is NOT yet source-level proven
Readable constants do not reveal the exact conditional expression for:
- which available HWND is chosen automatically;
- whether the rule is “first discovered”, “first sorted by name”, “previous still-alive”, or another fallback;
- exact condition under which `_sync_windows_loop` is invoked by this helper.

Therefore C05 does **not** promote a guessed “first window wins” rule to fact.

## 11. Stale-window/list handling

`_update_master_combobox`:
- keeps `_master_hwnd_cache`;
- only rebuilds radio controls when the HWND list changes.

C01/C02 already proved:
- closed HWNDs leave the discovery set;
- reused HWND with different PID is treated as a new generation;
- worker cache refreshes the window list.

Therefore a closed/reused master causes the master candidate list to rebuild.

### Explicit unknown
The readable constants do not prove the exact UI fallback after the currently selected master disappears:
- automatic selection of a new master;
- clearing selection;
- or waiting for `_auto_master_and_sync`.

That exact fallback remains explicit UNKNOWN until stronger code/runtime evidence.

## 13. C05 recovered model

```text
current game HWND set
↓
_update_master_combobox
├─ compare against _master_hwnd_cache
├─ character-info cache for labels
├─ fallback "Cửa sổ ..."
├─ rebuild radiobuttons only if HWND list changed
└─ _hwnd_by_name[label] = HWND
↓
user/automatic selection
↓
hwnd_master
↓
master roles:
  ├─ layout position index 0
  ├─ top-left in grid
  ├─ first in auto tile
  └─ source of mouse/keyboard sync
↓
all other game HWNDs = followers/slaves
```

Manual change safety:

```text
master radio changed
↓
resolve label → HWND
↓
if input-sync ON:
  stop sync
  unlock all slaves
↓
set/use new master
↓
user re-enables input sync
```
