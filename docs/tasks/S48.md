# S48 — Multiple concurrent F09 stop requests retain cancellation fence

## Proven source defect (S47)
- Continued exact LIVE STATE.md NEXT_ACTION S48 after reading PLAN.md, source S47, F09/S43–S47 documentation and verifying that docs/tasks/S48.md did not yet exist.
- Original F09 supports an independent, cooperative 20-second worker and a 1-second Tk countdown, not recovered complete game-launch actions. Current S42–S47 implementation is deliberately read-only, test-owned.
- S47 stop() sets one shared _stop_requested Event before waiting for _lifecycle_lock, then its successful cleanup clears that Event without checking whether a second stop() is still waiting on the same mutex. A waiting second stop has already requested cancellation, yet a competing start() could see the fence cleared between cleanups. A first stop's success alone cannot represent a second stop's pending intent.

## Narrow S48 source change
- Only src/login_schedule_worker.py is modified in production logic.
- _stop_request_lock protects _pending_stop_callers. Each stop() registers its cancellation intent, sets _stop_requested and _cancel BEFORE lifecycle mutex acquisition; every exit path unregisters in finally.
- A successful stopper clears _stop_requested only if all registered stop callers have completed AND permanent _closed is false.
- Any timed-out/failed stop preserves the cancellation fence until a later explicit successful cleanup. A waiting second stop keeps the fence set even if the first has finished joining.
- Preserve S47 monotonic total deadline covering mutex+join; do not put Tk, clock callback, thread join, I/O, game actions or credential access under _stop_request_lock. Preserve S46 lock-free request_shutdown, S45 Tk lifetime, old 20-second work evaluation.
