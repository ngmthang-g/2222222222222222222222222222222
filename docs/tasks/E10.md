# E10 — Start / stop coordinator

## STATUS
**VERIFIED_DISTRIBUTED_COORDINATOR_WITH_EXPLICIT_NO_GLOBAL_MUTEX_ASSUMPTION**

E10 closes Gate E by recovering how start/stop control is distributed across the shell, StartTab and each feature tab.

The most important result is negative as well as positive:

**There is no evidence of one universal shell FSM that owns every feature.**

Instead, the original architecture coordinates several independent feature-owned FSMs through cross-tab references, mode-change rules, permission/limit guards, shared button synchronization and cooperative cancellation.

## 1. Three coordination layers

### Layer A — TLMMainApp shell
Owns:
- tab visibility/enabled state;
- permission/plan/account-limit snapshots;
- selected-tab refresh lifecycle;
- cross-tab instance references.

The shell decides whether a feature can be reached/enabled, but does not own its internal run state.

### Layer B — StartTab quick coordinator
Owns:
- Start-page quick buttons;
- Auto/Xếp-lưới mode;
- window/input synchronization;
- cross-feature convenience commands through tab refs;
- button mirroring for Farm/Train LSV/Đồn/Tối ưu/Daily.

### Layer C — feature-owned FSM
Each automation tab owns:
- running state;
- per-account state;
- cancellation Events/generation flags;
- worker lists;
- all-account start/stop;
- status/button updates;
- feature-specific recovery and post-action routing.

This distributed model is a core parity constraint.

## 2. StartTab mode change is the strongest global mutual-exclusion rule

C08 exact evidence remains authoritative.

When changing to internal mode `sync` / visible `Xếp lưới`, StartTab checks and stops conflicting automation:

- Train/Farm:
  - `farm_tab_ref._is_farming`
  - `_toggle_farm`
- Daily Trừng Ác:
  - `_punish_running`
  - `_punish_toggle`
- Daily Tàng Bảo Đồ:
  - `_treasure_map_running`
  - `_treasure_map_toggle`.

After conflicting automation is stopped, Xếp-lưới automatically activates:
1. layout/window synchronization;
2. input/mouse-key synchronization.

Switching back to Auto/manual disables both synchronization systems.

This is explicit mutual exclusion. E10 does not generalize it to unrelated feature pairs without evidence.

## 3. Start quick controls delegate instead of duplicating FSM logic

StartTab exposes commands such as:
- `_farm_control_cmd`
- `_toggle_farm_cmd`
- `_train_lsv_action`
- `_toggle_train_lsv_cmd`
- `_donvang_action`
- `_toggle_donvang_cmd`
- `_daily_tab_action`
- Tối ưu mirror/toggle commands.

Exact Start documentation says Farm/LSV/Đồn actions call the corresponding tab method **in a thread**.

Therefore Start is an orchestrator/facade:
`Start button → call feature-tab method → feature tab owns actual transition`.

Do not copy feature FSM logic into StartTab during reconstruction.

## 4. Feature state is mirrored back to Start

Farm exposes:
- `_sync_start_tab_btn`
- `_is_farming`.

Train LSV exposes:
- `_sync_start_tab_btn`
- `_is_farming`.

Đồn exposes:
- `_sync_start_tab_btn`
- `_is_farming`.

Daily exposes:
- `_sync_start_tab_btns`
- punish/treasure running state.

Start's Tối ưu buttons are polled/mirrored against Tối ưu row/monitor state.

This is bidirectional coordination:

```text
Start quick command
→ feature transition
→ feature-owned state changes
→ _sync_start_tab_btn(s)
→ Start button text/color/state mirrors reality
```

The UI mirror is not the authoritative running state; the feature FSM is.

## 5. Farm/Train/Đồn family has per-account + all-account control

Recovered Farm methods include:
- `_toggle_single_farm`
- `_stop_acc`
- `_farm_acc`
- `_stop_all`
- `_farm_all`
- `_toggle_farm`
- `_is_farming`
- `_is_acc_farming`
- `_check_stop`.

Train LSV contains the same family:
- single-account toggle/stop;
- `_stop_all`;
- `_farm_all`;
- `_toggle_farm`;
- `_is_farming`;
- `_check_stop`.

Đồn similarly contains:
- per-account toggle/stop;
- `_stop_all`;
- `_farm_all`;
- `_toggle_farm`;
- `_is_farming`;
- `_check_stop`.

Therefore all-account Start/Stop is not a separate shell service. It aggregates feature-owned per-account FSMs.

## 6. Daily has two distinct activity FSMs

Daily separately owns:
- Trừng Ác:
  - `_punish_toggle`
  - `_punish_run_worker`
  - running HWND set/state;
- Tàng Bảo Đồ:
  - `_treasure_map_toggle`
  - `_treasure_map_run_worker`.

It also has:
- `_start_all_accs`
- per-account toggle/workers
- `_stop_reason`
- state-label scheduling
- Start button synchronization.

E10 therefore keeps Trừng Ác and Tàng Bảo Đồ as separate Daily modes rather than collapsing them into one generic Daily-running Boolean.

## 7. Other all-account / run guards

Recovered examples:

- Rao:
  - `_start_all_accs`
  - `_start_all_busy`.
- Tối ưu:
  - `_start_all_accs`
  - `_start_all_busy`.
- Phó Bản:
  - `_stop_all_runs`.
- Party:
  - per-group worker/cancel state and a single post-party completion stage.

Busy/running flags prevent duplicate starts inside the owning feature. Exact compare-and-set order for every flag is feature-specific and deferred to the corresponding feature gate.

## 8. Cancellation propagates cooperatively

E07 established the common stop model:
- `threading.Event`
- halt/running flags
- generation snapshots
- per-account state
- worker collections
- bounded joins where present.

Feature workers check their owner stop state through helpers such as:
- `_check_stop`
- per-row `stop_event`
- cancellation sets/events.

Therefore a Stop command normally means:
`set/propagate stop state → workers observe it → cleanup/reset UI`.

It is not a generic Python thread kill.

## 9. Permission and account-limit guards precede execution

E03/E04/E09 recovered:
- `has_permission`
- `has_permission_with_limit`
- `check_account_limit`
- per-row permission application
- child-widget enable/disable state.

Runtime permission guard is authoritative; disabled UI is only cosmetic.

Therefore a reconstructed Start command must not bypass the feature's runtime guard merely because the Start button itself is visible/clickable.

## 10. Synchronization max-window guard is a separate stop coordinator

Start synchronization has:
- `_get_max_windows`
- cached running-process count
- `_auto_stop_sync`.

If over the runtime max-window limit, both:
- layout sync
- input sync

are stopped together.

This rule belongs to synchronization, not to every feature FSM.

## 11. Login post-login routing is feature-owned orchestration

Login contains:
- `_auto_start_after_login`
- `_auto_start_party_after_login`.

Exact docs show post-login routing can wait for login completion then activate:
- Party
- Train
- Train LSV
- Đồn

or remain waiting according to configuration.

The route crosses tabs through their public controls/references; Login remains the owner of this post-login routing decision.

## 12. Party post-action routing waits for all groups

Party exact documentation:
`Chạy SONG SONG các cụm: mỗi cụm 1 thread ... xong hết mới làm hành động Sau khi party + reset UI (1 lần duy nhất).`

Party owns:
- `_after_party`
- `_after_party_action`.

Visible post-party choices from Gate B include:
- Chờ
- Train
- Train LSV
- Dồn vàng
- Phó Bản.

Thus Party post-routing occurs **after all configured group workers finish**, not as soon as the first group completes.

## 13. Selected-tab refresh start/stop is not feature execution start/stop

TLMMainApp/E03 centralizes:
- `_start_refresh`
- `_stop_refresh`
for the selected refresh-capable tab.

This only controls UI/data polling.

Stopping a tab's refresh does **not** mean stopping Farm/Train/Daily automation.

This distinction must be preserved.

## 14. Start-page quick action threads are not feature worker ownership

Start uses short daemon threads around delegated actions so UI clicks do not block.

The long-running worker/FSM remains in the destination feature tab.

Therefore:
- Start thread lifetime != feature run lifetime;
- Start button completion != automation complete;
- state must be re-read/mirrored from the feature tab.

## 15. No universal feature mutual exclusion is proven

The original explicitly stops Train + Daily modes when entering sync/Xếp-lưới.

E10 did **not** recover a universal rule such as:
`starting any feature automatically stops every other feature`.

Do not invent this.

Other mutual-exclusion rules may exist inside later feature-specific FSMs and will be handled in their gates.

## 16. Distributed coordination model

```text
permission / plan / limit service
          ↓
TLMMainApp tab visibility + enabled state
          ↓
StartTab quick facade ───────────────┐
          │                          │
          ├─ FarmTab FSM             │ state mirror
          ├─ TrainLsvTab FSM         │ ← _sync_start_tab_btn(s)
          ├─ Daily punish/treasure   │
          ├─ DonVangTab FSM          │
          └─ Toiuu controls ─────────┘

feature Start
→ owner guard
→ owner running/busy state
→ spawn/activate owner workers
→ per-account FSMs

feature Stop
→ owner cancel/Event/generation state
→ workers stop cooperatively
→ owner cleanup
→ owner UI state
→ mirror to Start

cross-feature explicit rule:
enter Xếp-lưới
→ stop Farm + Daily punish + Daily treasure
→ enable layout + input sync
```

## 17. Reconstruction contract

For parity:

1. keep feature FSM state inside the feature tab/module;
2. make Start quick buttons delegate to feature APIs;
3. mirror Start button state from feature-owned state;
4. preserve the explicit Xếp-lưới conflict-stop rule;
5. do not invent a universal feature mutex;
6. keep layout/input sync stop logic separate from Farm/Daily/other stops;
7. preserve per-account and all-account control surfaces;
8. stop workers cooperatively through owner Events/flags/generation;
9. enforce permission/account-limit guards at action time;
10. distinguish refresh polling start/stop from automation start/stop;
11. preserve Login post-login routing ownership;
12. preserve Party after-all-groups post-action routing;
13. do not make Start's short delegation thread the owner of long-running automation.
