## 1. There are two verified discovery paths

### A. Start-tab discovery
The original `start_tab.py` contains a module-level `get_windows()` callback path used by the Start/multi-window subsystem.

Verified static chain:

`EnumWindows`
→ top-level HWND callback
→ `IsWindowVisible`
→ safe title reader
→ class/process lookup
→ game predicates
→ append qualifying `(hwnd, title)`

The callback constant block contains:
- `EnumWindows`
- `IsWindowVisible`
- `_get_window_title_safe`
- `_get_window_info`
- normalized target process literal `thần long mobile.exe`
- `UnityWndClass`
- `WINDOW_NAME`
- local predicate names `is_game_process` and `is_unity`

### B. Shared coordinate-utils discovery
`coordinate_utils.py` independently contains `get_game_windows()` with the description:

`Enumerate visible Thần Long Mobile game windows with Win11-safe matching.`

Its callback contains the same discovery primitives:
- `EnumWindows`
- `IsWindowVisible`
- safe title
- class/process info
- `thần long mobile.exe`
- `UnityWndClass`
- `_title_matches_game`

This confirms the discovery design is not a screenshot inference; it exists in the compiled original.

## 2. Window title is read with a non-blocking timeout

The Start implementation contains the explicit original documentation:

`Đọc tiêu đề cửa sổ không block vô hạn.`

It further states that normal `GetWindowText`/WM_GETTEXT can block when the game window is not responding and hold the GIL, freezing the app.

The original replaces that path with:
- `user32.SendMessageTimeoutW`
- timeout: **150 ms**

So an unresponsive game top-level window is not allowed to indefinitely block the TLM UI while its title is queried.

This is a discovery safety mechanism, not merely a preview feature.

## 3. Class and process identity

`_get_window_info(hwnd)` is documented in the original as returning:

`(class_name, process_name)`

Verified APIs:
- `win32gui.GetClassName`
- `win32process.GetWindowThreadProcessId`
- `psutil.Process(...)`

Verified discovery constants:
- process target: **`thần long mobile.exe`**
- Unity class: **`UnityWndClass`**

The compiled callback also contains `.split` immediately before the normalized lowercase process literal, and other original TLM process-count code explicitly documents tolerance for the game's one-space/two-space executable-name variation. This strongly supports whitespace-normalized process comparison rather than depending on one raw spacing form.

C01 does not claim the exact Python expression used for that normalization because source text is not present.

## 4. Title predicates

Start-tab callback contains:
- `WINDOW_NAME`
- module constant string `Thần Long  Mobile`

Shared coordinate utils contains:
- `GAME_WINDOW_TITLE`
- `_title_matches_game`
- `DEFAULT_WINDOW_TITLES`
- strings:
  - `Thần Long  Mobile`
  - `Thần Long Mobile`
  - `Lineage W`

### What is verified
- title is part of the discovery decision path;
- Start has `WINDOW_NAME`;
- coordinate-utils has an explicit `_title_matches_game` predicate;
- Unity class and process identity are separately evaluated.

### Explicit unknown
The exact compiled Boolean grouping is not recoverable from the readable constant/string table.

Therefore C01 does **not** falsely state an exact formula such as:

`process AND (UnityWndClass OR title-match)`

even though that is the strongest structural reading of the local predicate names and constant ordering.

Likewise, the presence of `Lineage W` in `DEFAULT_WINDOW_TITLES` does not by itself prove that Start-tab's TLM `get_windows()` accepts a Lineage W window.

## 5. Exclusion rules recovered

### VERIFIED exclusions
1. **Non-visible top-level windows are rejected at enumeration time**
   - `EnumWindows` only supplies top-level windows;
   - callback explicitly calls `IsWindowVisible`.

2. **Non-game process/class/title candidates are filtered**
   - process, Unity class and title predicates are all present in the callback path.

3. **Child windows are not the discovery source**
   - the primary scan is `EnumWindows`, not `EnumChildWindows`.

### Hung-window handling
The discovery callback itself does not show `IsHungAppWindow` in its constant block.

Instead:
- title retrieval uses the 150 ms timeout to avoid a hang;
- `IsHungAppWindow` exists later in Start preview handling.

So C01 does not claim that a hung HWND is automatically excluded from the initial EnumWindows candidate list.

### Debug synthetic path
The Start `get_windows()` constant block also contains:
- `FAKE_ACCOUNTS`
- `Fake Account`

This is a synthetic/debug augmentation path, separate from physical HWNDs discovered through `EnumWindows`. It must not be mistaken for real game-window enumeration.

## 6. Refresh cadence — three different clocks

The original binary distinguishes the UI poll, background discovery worker and preview repaint cycle.

### Start UI list poll
Exact original text:

`Tự động cập nhật danh sách cửa sổ mỗi 2 giây (dừng khi rời tab).`

Also:
- `Bắt đầu lại poll khi quay về tab Start (gọi từ TLMTool).`
- `Dừng poll nền khi rời tab Start — detached preview giữ nguyên.`

Therefore:
- Start-tab list/UI polling cadence: **2 seconds**
- poll stops when leaving Start
- poll restarts when returning to Start

### Background EnumWindows/cache worker
Exact original text:

`Background thread: enum windows + đọc character info mỗi ~3s.`

and:

`Đọc memory mỗi ~8s (giảm EnumModulesEx load lên game process).`

Therefore:
- background window enumeration + character-info cache: approximately **3 seconds**
- heavier memory read: approximately **8 seconds**

The original also documents:
- `Cập nhật cache window list từ worker thread (không block main thread).`
- `Lấy danh sách (hwnd, title) từ cache worker thread (không block main thread).`

This is important: the 2-second UI poll is not the same thing as saying `EnumWindows` itself necessarily executes every 2 seconds. The background producer is explicitly documented at ~3 seconds.

### Preview display cycle
Separate original text:

`Delay loop preview theo số acc: ít acc mượt 800ms, đông acc 2000ms.`

So preview repaint/update delay is:
- **800 ms** for fewer accounts
- **2000 ms** for more accounts

The threshold that separates “ít acc” from “đông acc” is not proven by readable static evidence in C01.

## 7. Strict specific-window resolver is separate from discovery

`coordinate_utils.find_target_window` is a different path from `get_game_windows`.

The original explicitly documents:

`Strict exact-title resolve — KHÔNG đoán cửa sổ.`

Rules:
- resolve only the exact requested `window_title` via `FindWindow`;
- missing title or no exact match → return `(0, "")`;
- do not select the first HWND;
- do not scan default titles as a fallback.

The original explains that the old “take the first window” behavior was a source of clicking/pixel-reading the wrong account.

This strict resolver will matter again in later behavior tasks, but C01 records it now because it defines a critical anti-wrong-window rule.
