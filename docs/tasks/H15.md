## Outcome

H01–H14 provide the complete static/visual Train reconstruction contract currently recoverable from the frozen TLMTool 2.1.2 binary.

H15 found two kinds of pre-existing runtime evidence:

1. **User-supplied live screenshots**
   - Train stopped/default UI is directly observed.
   - StartTab stopped quick-control state is directly observed.
   - These prove only visible stopped-state rendering, not button-transition behavior.

2. **Packaged runtime trace**
   - `TLMTool.dist/data/automove_log.txt`
   - SHA-256: `17f6daf02916e42b562e09a41afdf6affbdad8129c3f3bd25b92f80e9d259500`
   - size: 15,741,058 bytes
   - 387,238 lines
   - archived mtime after extraction: 2026-10-01 20:13:16 UTC

The trace contains real execution records for several low-level primitives, including AutoMove/AutoPath, AutoFight UI invocation, mount toggle, Game.GoTo, NPCShop probing and ItemAction action=4.

Important limitation: the trace does **not self-identify a top-level Train button/session/version in each line**. Because it is bundled inside the exact frozen archive it is valid existing runtime evidence for those low-level primitives, but it cannot prove which top-level Train FSM branch caused each invocation or that navigation/selling/recovery completed successfully.

Therefore H15 never upgrades an end-to-end Train scenario to runtime-verified merely because one of its lower-level primitives appears in the log.

## Gate decision

**Gate H is CLOSED for static/visual research and reconstruction handoff.**

This matches the project pattern used for Gate F/G:
- static contracts are locked;
- runtime-only unknowns remain explicitly classified;
- Windows original-vs-reconstruction parity remains mandatory later.

**Gate H is NOT declared end-to-end runtime-parity complete.**

The current analysis environment cannot execute the Windows GUI EXE against a live Than Long client. All scenarios requiring that environment are marked `RUNTIME_ENV_REQUIRED`, not guessed.

No scenario is marked `BLOCKED` at this time: every unresolved user-visible runtime case has a concrete Windows test procedure. Exact source micro-order/daemon internals that are not user-visible remain H14 implementation unknowns rather than falsely promoted to runtime parity requirements.
