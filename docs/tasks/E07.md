## 1. Four different concurrency mechanisms coexist

The original does not have one generic task framework. It uses:

1. **Tk scheduled jobs**
   - `root.after(...)`
   - `after_cancel(...)`
   - used for UI-safe callbacks, refresh cadence, debounce and heartbeat scheduling.

2. **Python worker threads**
   - `threading.Thread`
   - feature/action/background I/O work.

3. **Listener/service threads**
   - pynput mouse/keyboard listeners;
   - emulator `ThreadingHTTPServer`;
   - CPU monitor;
   - Start preview/cache worker.

4. **External/native boundaries**
   - helper processes such as `forwarder.exe`;
   - Win32 `CreateRemoteThread` for DLL injection;
   - Frida guest/server execution.

These must remain distinct in reconstruction.

## 2. Tk main-thread handoff is deliberate

Multiple original docs explicitly state that background workers must not directly manipulate Tk widgets.

Examples:
- Daily:
  `Marshal _apply_state_label về Tk main thread qua after(0).`
- Farm:
  same main-thread handoff pattern for state-label/UI updates.
- Debug workers:
  background work followed by a main-thread apply callback.
- shared block notifier:
  E04 recovered `root.after` for service→GUI notifications.

Therefore:
`worker computes / blocks → root.after(0, apply) → Tk widget mutation`.

Reconstruction must not call Tk widgets directly from worker threads.

## 3. Tk after jobs are task handles, not threads

Recovered state across tabs includes fields such as:
- `_refresh_id`
- `_refresh_job`
- `_preview_loop_id`
- `_preview_reposition_after_id`
- `_heartbeat_after_id`
- `_save_after_id`
- `_scroll_after`.

Corresponding `after_cancel` paths are present.

These jobs belong to widget/root lifetime. They must be cancelled when the owning tab/widget stops or is destroyed.

E07 does not reinterpret them as daemon threads.

## 7. StartTab preview/cache worker

Exact original docs state:
- background thread enumerates windows and basic character info at about **3 seconds**;
- heavier memory info is refreshed at about **8 seconds**;
- the worker does **not** call Tk APIs;
- it only writes cache;
- the UI/preview loop consumes the cache.

This architecture was chosen specifically to avoid GUI hangs caused by blocking window/process/memory enumeration.

Start also tracks:
- `_preview_worker_started`
- preview caches
- preview lock
- refresh/timer IDs.

The exact Python Thread constructor/daemon value for this specific worker is not fully source-visible in readable constants, so only its background-worker contract is marked VERIFIED.

## 14. Stop signals are cooperative first

Common patterns:
- `threading.Event`
- boolean running flags
- generation counters
- cancel tokens
- worker lists
- `join(timeout=...)`.

This means feature shutdown normally requests cooperative stop and waits boundedly rather than blindly killing Python threads.

The original does still contain forced process-exit and process-kill paths for special cases:
- heartbeat-enforced `os._exit`;
- helper/game process cleanup;
- DLL injection remote-thread primitives.

These are not the normal feature worker-stop mechanism.

## 15. Daemon flags are mixed

Many representative background tasks explicitly use `daemon`:
- CPU monitor
- pynput listeners
- emulator HTTP service
- several short feature/debug workers.

However E01's forced-quit documentation explicitly warns that non-daemon threads such as pynput/farm-related workers can keep the interpreter alive in some paths.

Therefore E07 does **not** claim that every worker is daemon.

Exact daemon value for every worker remains per-worker evidence, not a global policy.

## 16. Thread joins are bounded where needed

Recovered `join` + `timeout` appears in:
- CPU monitor;
- Party parallel-group completion;
- feature worker cleanup;
- other worker/service shutdown paths.

The exact timeout constants vary and are not all readable.

Reconstruction must preserve bounded shutdown rather than unconditionally blocking the Tk main thread forever.

## 17. Lock ownership

Recovered examples:
- Start: `_sync_locked_guard`, preview/cache state
- Login: `_launch_lock`
- Party: `_run_lock`, `_targets_lock`
- emulator manager/remote: `RLock`
- injection/Lua paths: separate Locks.

Locks protect subsystem-owned state; they are not one global application lock.

E07 does not invent lock reentrancy unless `RLock` is explicitly recovered.

## 18. Native remote threads are a different category

`CreateRemoteThread` appears in DLL injection paths.

That is a Windows thread created **inside the target game process** for payload loading/execution.

It must not be modeled as a Python worker thread or joined through Python `threading.Thread`.

## 19. Reconstruction contract

For parity:

1. retain Tk `after` jobs for GUI timers/debounce/refresh;
2. cancel scheduled jobs when owner stops/destroys;
3. move blocking I/O/process/memory/action work off the Tk thread;
4. return UI mutations through `root.after`;
5. retain Event/flag/generation cooperative cancellation;
6. retain per-subsystem Locks/RLocks rather than one global lock;
7. preserve Start input queue serialization;
8. preserve Party one-thread-per-group behavior;
9. preserve per-account feature worker ownership;
10. preserve Start preview cache worker separation from Tk;
11. preserve emulator HTTP listener as its own service thread;
12. treat helper processes and CreateRemoteThread as separate concurrency boundaries;
13. use bounded joins where the original exposes them;
14. do not mark all workers daemon without evidence.
