# E09 — Error handling / fallback policy

## STATUS
**VERIFIED_WITH_EXPLICIT_LOCAL_EXCEPTION_SCOPE_AND_RETRY_TIMING_UNKNOWNS**

E09 recovers how the original application contains failures at process, worker, UI, WinAPI, configuration, network/server and permission boundaries.

The central rule is **layered containment**:
- fatal/native diagnostics are captured globally;
- worker exceptions are logged and marshalled back to UI where appropriate;
- blocking WinAPI calls use timeout/hung guards;
- configuration parsers return safe fallbacks/log errors rather than crashing the whole shell;
- permission/account-limit decisions deliberately fail closed in security-sensitive states;
- feature-specific retry/skip behavior remains owned by the feature.

## 1. Process-level diagnostic containment

Main startup installs:
- `debug_logger.setup`
- `faulthandler.enable(... crash_fault.log ...)`
- custom `threading.excepthook`.

Unhandled worker-thread exceptions are reported with:
- `[THREAD-EXC]`
- thread identity
- exception type/value
- `traceback.print_exception`.

This does not recover every exception, but it prevents unhandled worker failures from becoming silent.

## 2. Worker done/error callbacks

Many feature workers follow the pattern:

```text
background worker
→ try operation
→ root.after(... done callback)
or
→ root.after(... error callback)
→ restore button/state
→ log/show user-facing error
```

A direct example is Login `_reload_worker`:
- `_done`
- `_err`
- `[RELOAD] Worker error: ...`
- main-thread lambda restores `btn_reload` state/background.

Therefore feature errors are generally contained at their owner boundary rather than allowed to permanently leave the UI in a busy/disabled state.

## 3. User-facing messagebox layer

The original application contains localized uses of:
- `messagebox.showerror`
- `showwarning`
- `showinfo`
- `askyesno`.

These are used selectively for actionable failures/confirmation, for example:
- updater confirmation/failure;
- heartbeat forced-close warning;
- license activation outcomes;
- missing/invalid user input in feature tabs.

E09 does not treat every logged error as a popup. Logging and user notification are separate decisions.

## 4. Config load/save errors are non-fatal

Shared central config helper contains:
- `[CONFIG] Error loading ...`
- `[CONFIG] Error saving ...`.

Start config save contains:
- `[CONFIG] Save error: ...`.

Info simple-dict config contains:
- `Error saving config: ...`.

E05 already established duplicate-tolerant settings reads and atomic settings writes.

The recovered behavior is therefore:
- configuration I/O/parsing failures are caught/logged locally;
- app startup/feature UI can continue with defaults/fallbacks where the tab owns them;
- malformed scalar conversion helpers catch `ValueError`, `TypeError`, `AttributeError` and can return `None`.

Exact fallback value for every individual key remains feature-owned and is not centralized by E09.

## 5. Network/server startup errors do not immediately crash the GUI

Info startup/server path contains:
- request timeout state;
- `Server API call failed`
- `Server did not return a valid token`
- `Token verification/decode failed: ...`
- `Error calling server API: ...`.

Heartbeat path contains:
- `Heartbeat prerequisites not ready`
- `Heartbeat did not return a valid token`
- `Heartbeat token decode failed: ...`
- `[HEARTBEAT] app_heartbeat failed: ...`
- `record_heartbeat_failure`
- `_schedule_next_heartbeat`.

Thus a single network/JSON/token failure is recorded and handled inside the heartbeat/service lifecycle rather than directly crashing the Tk process.

## 6. Repeated server/permission failure can deliberately become fail-closed

`permission_guard` exact documentation for account/window-limit checks contains:
`Fail-closed` for states such as missing server payload / invalid or blocking permission state.

It also documents a special limit semantic:
`limit <= 0` is treated as trial/unlimited and allowed through.

The runtime guard explicitly exists because:
`UI enable/disable is only cosmetic; this module provides logic-level checks.`

Therefore:
- permission-sensitive action execution must pass the runtime guard;
- certain invalid/missing server states deny execution rather than trusting stale UI state;
- UI disabled state is not the security/logic boundary.

Exact four-cause wording of every `has_permission=False` branch is partly fragmented in the compiled strings, so E09 preserves the fail-closed contract without inventing a complete source-level branch table.

## 7. Heartbeat failure has staged escalation

The server/heartbeat layer does not hard-exit on first failure.

Recovered lifecycle:
- record heartbeat failure;
- schedule next heartbeat;
- permission/limit state evaluates current failure/grace data;
- blocking state strike 1 waits for confirmation;
- second blocking strike triggers delayed forced close.

This is a staged recovery/escalation policy, not immediate process termination.

## 8. WinAPI calls defend against hung windows

Shared window helpers use:
- `SendMessageTimeoutW`
- Start input sync uses `SendMessageTimeout`
- `SMTO_ABORTIFHUNG`
- `IsHungAppWindow`.

Exact Start input documentation states:
- do not let a hung game window block the synchronization worker;
- retry a short path **2 times** when Unity may be temporarily busy/frame-spiking;
- if sending still fails, skip that slave for the current action so the worker remains alive.

This is a strong parity rule: a single hung game HWND should not hang the whole tool.

Exact retry delay remains UNKNOWN.

## 9. Safe window/process enumeration

Shared `utils` wraps:
- window title/class/process discovery;
- `GetWindowThreadProcessId`
- process lookup;
- safe title retrieval through timeout-capable WinAPI.

Enumeration filters invalid/invisible/non-game windows rather than assuming every HWND is valid.

This provides fault containment for windows closing between enumeration and action.

## 10. Input-sync stale-state recovery

C19/E07 recovered:
- idempotent slave block/unblock helpers;
- stale lock watchdog around 10 seconds;
- retry/skip behavior;
- master-change unlock.

Thus a missing mouse release, master close/change, or transient send failure has an explicit recovery path instead of permanently locking a slave window.

## 11. JSON/protocol validation on emulator remote path

`emu_remote` returns structured `ok/error` results and validates:
- token;
- supported action;
- emulator discovery/identity;
- required map/x/y/name/key/value fields;
- allowed config keys;
- boolean/int/text formats;
- buff format.

Examples of recovered error responses include:
- token wrong;
- unsupported action;
- machine not found;
- missing discovery;
- missing map/x/y;
- unsupported key;
- invalid integer/string/buff/condition/method.

Therefore malformed remote input is rejected locally rather than blindly dispatched to emulator actions.

Exact HTTP status code mapping for every error response is not claimed by E09.

## 12. Feature fallback behavior is local, not global

Examples recovered elsewhere:
- Login reload reports worker error and restores row button.
- Start sync retries a temporarily busy slave then skips it.
- config readers return defaults/local fallbacks.
- movement/navigation helpers can return False/fallback rather than terminate the application.
- preview maintenance drops stale HWND/items and rebuilds.

E09 does not invent one universal retry count/backoff policy because the original uses subsystem-specific rules.

## 13. Tcl/Tk lifecycle errors are locally tolerated

`TclError` references are present in shell/tab widget-state and destruction-sensitive code.

This is consistent with widgets disappearing while:
- permissions change;
- tabs are rebuilt/hidden;
- scheduled callbacks race with destruction.

The exact try/except block for every TclError occurrence is not source-decompiled, but the presence of local handling supports a best-effort UI cleanup model rather than process-fatal behavior.

## 14. Error handling is separate from diagnostics

E06 central logging captures errors, but E09 controls what happens next.

A reconstructed path should distinguish:

```text
error occurs
→ record diagnostic
→ classify owner/boundary
→ retry / skip / fallback / deny / notify
→ restore UI state
→ only force-exit for explicit policy paths
```

Do not implement `except Exception: pass` globally, and do not turn every logged error into a fatal popup.

## 15. Reconstruction contract

For parity:

1. retain global worker exception logging and faulthandler;
2. keep feature-worker done/error callbacks owner-local;
3. marshal UI error state back through Tk main thread;
4. keep config I/O errors non-fatal with tab-owned defaults;
5. keep heartbeat failures staged and recorded;
6. preserve runtime permission guard as fail-closed where documented;
7. use timeout/hung-window guards around synchronous WinAPI messaging;
8. preserve Start's short two-retry Unity-busy path and skip-on-failure behavior;
9. preserve stale input-lock watchdog recovery;
10. validate emulator remote payload/token/action/config before dispatch;
11. keep user-facing popup decisions selective;
12. do not invent global retry/backoff or swallow all exceptions.
