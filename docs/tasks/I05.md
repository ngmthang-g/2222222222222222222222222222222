## 9. What press_single_key_dll actually does

The frozen `.keyboard` module independently documents:

`Press key on target window using DLL sync protocol (WM_MY_SYNC_KEY).`

It uses:
- target HWND/title resolution;
- key → virtual-key resolution;
- Windows `PostMessage`;
- `WM_MY_SYNC_KEY`;
- packed key-down/key-up states;
- `version.dll` interception/hook to generate the real game input.

The exact keyboard helper documentation says `sync=True` disables randomized pre-delay/hold for immediate mirrored input.

Default helper signature values are independently decoded as:

`delay=0.02, count=1, pre_delay_range=(0.1,1.0), hold=None,
hold_range=(0.1,0.5), sync=False, retries=0, retry_delay=0.3`.

The Dạ Minh Châu one-shot overrides the relevant defaults with `delay=0, sync=True`.

This proves the TrainLSV schedule mechanism is not a global SendKeys/pynput/physical-keyboard implementation.

## 10. Repeating schedule worker is per account

TrainLsvTab contains:

`_buff_loop(self, hwnd, stop_event, row, gen, ...)`

with exact local surface:

`self, hwnd, stop_event, row, gen, press_single_key_dll, waited_any,
rd, key, mins, secs, interval, deadline, e`.

Exact documentation:

`Vòng lặp buff: gọi phím tắt theo thời gian lặp lại trong từng buff row.`

This locks:
- one worker is bound to one target `hwnd`;
- it walks configured buff rows `rd`;
- it reads each row's key, minutes and seconds;
- it computes an `interval`;
- it tracks a `deadline`;
- it dispatches keys via `press_single_key_dll`;
- send exceptions are handled/logged per key.

The module therefore does not create a physical/global keyboard scheduler.
