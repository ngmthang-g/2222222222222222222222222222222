## 1. UI callback

The button is built inside auto_frame, so it is an Auto-side quick control rather than part of the Xếp-lưới sync frame.

## 2. Exact original command documentation
Original EXE doc:
Xếp gọn: đưa tất cả cửa sổ về vị trí (0,0).

This is exact behavior evidence from the original binary.

## 3. Shared movement engine
_stack_tight_cmd uses the common movement primitive recovered in C06:
- _move_windows_offset
- position source is pos_fn(index)
- current window size is preserved
- master is always index 0
- all other game HWNDs follow.

For Xếp gọn the position function returns the same position for every index:
(0,0).

Therefore the command stacks all discovered game windows at the top-left without resizing them.

## 4. HWND source and ordering
_move_windows_offset recovers:
- _get_preview_hwnds
- master
- wins
- pos_fn.

Thus the command acts on the current game-HWND set already maintained by the Start/preview discovery system. Master is processed first, although visual position is identical for every window in Xếp gọn.

## 5. Hidden-state integration
The same movement path references _reset_hidden_state.

Original _reset_hidden_state doc:
Nếu đang ẩn cửa sổ → reset trạng thái (cửa sổ đã được xếp lại visible).

Therefore using Xếp gọn after the off-screen hide mechanism clears the hidden-state bookkeeping because layout has placed windows back in visible coordinates.

## 6. API behavior
C06 already verified the positioning family uses SetWindowPos semantics and the move-only path preserves size. No MoveWindow literal/import was recovered from the original inner EXE.

Xếp gọn must therefore be reconstructed as the original position-only command, not as a resize-to-default action.

## 7. Runtime log
The shared movement helper contains:
[Xếp] Đã xếp ... cửa sổ

confirming a completed multi-window operation rather than a UI-only callback.

## 8. Mode interaction boundary
The Xếp gọn button is visually present in Auto mode and absent from the visible Xếp-lưới control frame.

C07 proved Auto can run a 1-second auto-tile loop while auto_tile_active=True. Static evidence does not expose the exact race/priority rule if Xếp gọn is pressed while that loop is currently active.

Therefore:
- immediate Xếp gọn action to (0,0) is VERIFIED;
- whether an already-active Auto tile cycle subsequently repositions the windows is an explicit concurrency UNKNOWN until Windows runtime tracing.
