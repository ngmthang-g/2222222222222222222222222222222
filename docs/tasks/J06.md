## 1. The current “Lần” control is an Entry, not a fixed-choice Combobox

The frozen UI block has the column header:

`Lần`

The row-construction locals are:
- `times_val`
- `times_var`
- `cb_times`.

Despite the old local name `cb_times`, the actual widget class serialized in the current EXE is:

`Entry`

not `Combobox`.

No `values=` tuple, readonly-state surface, Spinbox surface, or validation-command surface is present for this field.

Therefore the current UI itself does **not** expose a fixed 1–5 dropdown. It is a free text numeric field.

## 2. Default `times` = 1 is exact

The serialized default tuple for `_add_schedule_row` is exactly:

`(True, None, None, 1, None)`

corresponding to:

`enabled=True, activity=None, name=None, times=1, rows=None`.

The row-construction block also contains:
- literal fallback string `"1"`;
- exception tuple `(ValueError, TypeError)`;
- then construction of the `Entry`.

This is strong static evidence that a seeded/load-time `times` value is numerically normalized and falls back to **1** when that conversion fails.

Exact source expression is not stored in the Nuitka constant stream, so J06 does **not** invent whether the current normalization additionally clamps 0/negative values.

## 3. Legacy/config default is also 1

The frozen legacy-load block contains:

`times -> 1`

as the missing-field default before the row is rebuilt.

Thus both:
- newly-added rows; and
- old config rows missing `times`

begin with the same canonical default count of **1**.

## 6. `times` is part of the selected schedule item

`get_selected_schedule() -> [{activity, name, times, row}]`

The same schedule item is sent to each account worker for that row.

Thus one row owns one logical `times` value shared by all account workers in that row.

## 7. Critical branch difference: `times` is used by Phó Bản, but not by Train

The frozen `_acc_step_worker` dispatch block is asymmetrical.

For `Phó bản`, it calls:

`_do_dungeon(...)`

with the dungeon row data and the seven control/context keywords:
- `stop_check`
- `barrier`
- `cancel`
- `acc_name`
- `is_leader`
- `member_index`
- `total_members`.

The outer `_do_dungeon` local model explicitly includes `times`.

For `Train`, the worker calls:

`_do_train(..., stop_check=...)`

and the frozen Train documentation says only:
1. switch to Train tab once;
2. find the account;
3. activate its ▶;
4. success as soon as activation succeeds.

No `times` parameter exists in the Train execution surface.

Therefore **the Lần field is ignored by the Train activity at runtime**. A Train schedule row executes its Train activation once, even if its preserved Lần field displays another number.

This is a current TLM behavior and must not be “fixed” during parity reconstruction.

## 8. Phó Bản count is manual tool-side repetition, not game RepeatCount

The exact `_config_dungeon_memory` contract sets:
- `SelectedFuBen` from `DUNGEON_FUBEN_CODE`;
- `AutoRepeat=False`;
- `FollowLeader=True`;
- `AutoRevive=True`.

It explicitly says:

`Không động tới RepeatCount.`

The exact `_do_dungeon` documentation then says:

`Hoạt động Phó bản — lặp times lần`.

Therefore the requested count is implemented by TLMTool itself. It is **not** implemented by setting the game's RepeatCount/AutoRepeat controls.

## 9. Configuration is repeated on every requested dungeon repetition

The exact `_do_dungeon` documentation says the memory configuration is:

`thao tác giống nhau mọi lần, không chia lần đầu/lần sau.`

So for each requested dungeon repetition, the common flow re-applies:
- `SelectedFuBen`;
- `AutoRepeat=False`;
- `FollowLeader=True`;
- `AutoRevive=True`;

rather than configuring once and trusting the game to auto-repeat.

The memory write helper itself has its own independent retry policy:
- up to **5 attempts**;
- **2 seconds** between attempts;
- stop/cancel may exit early.

Those five write retries are not schedule repetitions.

## 10. Exact repetition architecture

The frozen `_do_dungeon` documentation defines each repetition as:

1. configure the dungeon through memory;
2. run handler pre/post config hooks;
3. move to the configured meeting/NPC point;
4. movement may retry after failure — the live log format shows `/3`, i.e. initial attempt plus up to 2 retries;
5. wait at the shared row barrier with no barrier timeout;
6. call the FuBen-start retry stage;
7. wait for one dungeon map cycle;
8. synchronize again at the barrier before the next repetition;
9. continue until the requested `times` cardinality is complete.

After all requested repetitions complete, `_do_dungeon` returns success so the schedule worker may continue to the next J04 row.

## 11. The J04 Barrier is reused across dungeon repetitions

J04 proved that `_run_one_group` creates **one `threading.Barrier` per schedule row** and passes that same object to every account worker for that row.

J06 proves that `_do_dungeon` receives that passed barrier and calls the shared `_barrier_wait` inside its repeated dungeon flow.

Therefore the same reusable row barrier synchronizes the accounts across repetition boundaries; TLM does not create a new independent Barrier object for every requested run.

The exact normal contract is:
- all accounts reach the pre-start barrier;
- they proceed into that repetition;
- after the completed cycle they synchronize again;
- only then does the group proceed toward the next repetition.

Failure/abort behavior of a broken barrier remains J07.

## 12. FuBen-start retry is per repetition, not the schedule count

The exact `_start_fuben_retry` documentation says:
- run after the pre-start barrier while still outside the dungeon;
- retry quickly;
- current frozen documentation states **5 × 0.3 seconds**;
- before retry attempts after the first, check MapID;
- if another account has already pulled the party into the target dungeon MapID, treat the start stage as passed;
- transient `None` MapID during loading is not treated as successful entry;
- exhausting the start stage while still outside the dungeon is a hard failure path.

The wording “lượt 1 / lượt 2” inside this helper refers to the start/verification stages of **one dungeon repetition**, not to the user's Lần count.

## 13. Cycle completion is based on MapID enter → exit

The frozen `_wait_dungeon_cycles` documentation defines one completed cycle as:

- `MapID == target map_id` → that dungeon run has entered/started;
- later a **non-None** `MapID != target map_id` → the account has exited, so one run is completed;
- temporary `None` during map transition is ignored and must not be counted as an exit.

The helper owns:
- `times`;
- `done`;
- `deadline`;
- entry/active/exit wait-state locals.

Thus the map transition, not merely clicking Start FuBen, is what proves a completed dungeon cycle.

## 15. `run_idx` exists per dungeon context; exact base remains unresolved

- `run_idx`
- `times`.

The current `_do_dungeon` local model also owns a `run` variable, and its nested context constructor takes `run_idx`.

However the serialized constants do not instruction-bind whether the first context index is:

The current only custom handler, `SatTinhDungeon`, does not branch on `run_idx`, so that base is not observable from existing static/runtime evidence.

## 16. Generic helper `times` documentation vs outer-loop documentation

Another static nuance must be preserved rather than guessed away:

- `_do_dungeon` explicitly documents manual repetition and “chờ **1 cycle map** ... trước lần tiếp theo”;
- `_wait_dungeon_cycles` is a generic helper that itself accepts `times` and documents counting up to that value.

The exact literal positional value passed from the current native `_do_dungeon` call into the helper is not recoverable from printable constants alone.

This does not change the externally locked contract that `_do_dungeon` only succeeds after the requested number of dungeon enter/exit cycles. But reconstruction should preserve the outer per-run context/barrier architecture and validate the helper-call literal later on Windows rather than inventing it now.

## 17. Row completion happens only after the normal dungeon count completes for all accounts

J04 proved:
- one worker thread per account for a row;
- join the whole account batch;
- then normal-path row status becomes `Xong`.

J06 proves the Phó Bản worker does not return normal success until its requested dungeon repetitions are complete.

Therefore on the normal path a Phó Bản row becomes `Xong` only after all account workers for that row have returned from the requested repetition sequence.

How one failed/cancelled worker changes row status is J07 and is not guessed here.
