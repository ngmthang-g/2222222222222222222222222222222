# F03 — Login password behavior

## STATUS
**VERIFIED_VISUAL_MASK_ONLY_WITH_DIRECT_UNENCRYPTED_STORAGE_EVIDENCE**

F03 recovers the password lifecycle from the frozen original EXE and keeps visual masking separate from actual password storage.

Primary specimen:
`TLMTool.dist/TLMTool.exe`
SHA-256:
`15c8044f215680d6851c8f901a5dc7d181068d91a8938f2a628077cf21a2df22`

## 1. Password masking is a Tk Entry display option only

Original Login UI contains:
- `show_pass_var`
- checkbox text `Hiện mật khẩu`
- callback `_toggle_show_password`
- password Entry constructor option `show`
- a one-character `*` constant in the same password-Entry constructor block.

Exact original method documentation:

`Tick = hiện mật khẩu thật, bỏ tick = hiện **** cho mọi entry_pass.`
`Bao gồm cả các dòng đang ẩn trong _hidden_rows.`

Therefore:
- checkbox unchecked → Entry uses `show='*'`;
- checkbox checked → masking is removed and the real Entry text becomes visible;
- the toggle applies to visible and plan-hidden account rows.

Important detail:
the doc's `****` is descriptive. The Entry uses a single mask character `*`, so Tk renders one star per password character; it is not a fixed four-character replacement string.

## 2. Masking does not change the underlying password value

The toggle evidence only changes the Entry's `show` property.

The password remains the same underlying Entry value and is still read through `entry_pass`.

No evidence shows the toggle replacing the Entry content with stars or restoring it from a separate encrypted buffer.

Therefore:
**mask/unmask is presentation state, not data transformation.**

## 3. Password enters the in-memory account model as a plain string

`_sync_accounts_cache` has exact original documentation:

`Ghi data từ widget state vào _accounts_cache (plain dicts).`
`Gọi mỗi lần cần save — đảm bảo cache đúng trước khi ghi file.`

Its local field set includes:
- `check`
- `user`
- `pass`
- `captcha`
- `proxy`.

The normalized stored/cache field is:
`password`.

There is no password-specific encryption/decryption/encoding step recovered between the Entry and the plain-dict cache.

Thus the password exists as an ordinary Python/Tk string in process memory.

## 4. Persistent account password is directly serialized into settings.ini

F02 proved the account persistence format:

`check | user | pass | captcha | proxy`

one row per line under:

`%APPDATA%\TLMTool\settings.ini`
→ `[Settings]`
→ `accounts`.

The save-on-destroy block contains the literal `pass` field adjacent to the pipe-join serializer and `write_settings`.

The load block maps the corresponding field directly to normalized key:
`password`.

The shared E05 `write_settings` service is an INI writer, not an encryption service.

No Login dependency/reference to a credential cipher, DPAPI, keyring, Fernet, AES, base64 wrapper, or password-specific secret service was recovered.

Direct binary re-scan of the Login region also found no strings/references for:
- `encrypt`
- `decrypt`
- `Fernet`
- `base64`
- `DPAPI`
- `CryptProtectData`
- `CryptUnprotectData`
- `keyring`.

Conclusion for parity:
**the persisted account password is stored directly/un-encrypted in the account row string.**

Do not mistake the UI's `*` masking for on-disk protection.

## 5. Password is read directly for selected login rows

The selected-account parser uses:
- `entry_user`
- `strip`
- `entry_pass`
- captcha/proxy state.

Exact original documentation:

`Trả về list [(row_index, tk, mk, captcha_mode, proxy), ...] chỉ các dòng được tick (✅️).`

This proves the password is passed forward as `mk` in the selected account tuple.

A useful difference is visible in the constants:
- username path includes `strip`;
- password path follows `entry_pass` without another recovered `strip`.

That strongly indicates username whitespace is normalized while password text is preserved as entered.

F03 records that behavior for parity but does not claim an instruction-level decompilation of the exact assignment expression.

## 6. Missing credentials are rejected before login

Exact Login text:
`⚠️ Dòng thiếu tài khoản hoặc mật khẩu`

The selected row therefore requires both account and password data before the login worker is allowed to proceed.

The exact branch expression is deferred to F06, but the password-empty validation itself is verified.

## 7. Runtime login path carries the raw password string

Single-account worker constants include:
- `tk_val`
- `mk_val`
- `_login_click_worker`.

The login click/monitor documentation is explicit:

`Thực hiện chuỗi login trên 1 cửa sổ với tài khoản (tk, mk).`

and:

1. click username field
2. enter `tk`
3. click password field
4. enter `mk`
5. click Login.

Therefore the same password value flows:

```text
Entry value
→ selected tuple mk
→ worker mk_val
→ login click worker/monitor
→ game password field
```

The exact hidden-input/WinAPI typing mechanism belongs to F06.

## 8. No Login clipboard password path was recovered

A static scan of the Login block found no:
- `pyperclip`
- `clipboard`
- clipboard API
- password-copy command.

The only nearby copy operation is `shutil.copy2` for Proxifier/profile installation and is unrelated to credentials.

Therefore:
**no explicit password-to-clipboard path is recovered in LoginTab.**

This is not a universal proof that no external subsystem could ever access process memory; it is a statement about the original Login module's static behavior.

## 9. Password logging exposure

The original Login constants contain many row/profile/proxy/status logs.

The password variable `mk_val` is passed to the login worker, but no explicit log format that prints the password value was recovered.

Recovered logs refer to:
- row/profile indices;
- proxy/direct state;
- HWND/readiness;
- success/failure/error text.

Therefore F03 status is:

- explicit password logging: **NOT RECOVERED**
- username/session/proxy/status logging: present
- central stdout/stderr tee from E06 means any future debug print containing a password would be persisted, so parity reconstruction must avoid adding new password debug output.

Do not introduce password logging while rebuilding.

## 10. Hidden rows behave the same

Exact mask-toggle documentation says hidden rows in `_hidden_rows` are included.

F02 proves hidden rows also remain part of the persistence-preservation model.

Therefore a row hidden by plan limit:
- still retains the real password value;
- participates in password mask/unmask handling when restored/iterated;
- is not sanitized or deleted simply because it is hidden.

## 11. Delimiter sensitivity

Account rows use:
- pipe `|` between fields;
- newline between rows.

No escaping/quoting/encoding layer for password text was recovered.

This means parity reconstruction should **not silently introduce escaping or encoding** unless later source evidence requires it.

Potential delimiter edge cases are therefore preserved as original-format behavior.

Exact parser outcome for a password containing `|` or newline is not source-decompiled and remains **UNKNOWN**.

## 12. Hashing evidence is unrelated to account passwords

LoginTab contains `hashlib` / `md5` evidence in:
`_check_dll_hash_worker`.

That hash path checks DLL/package state.

It is not linked to:
- `entry_pass`
- account cache
- account serializer
- login password input.

Therefore F03 must not misclassify DLL MD5 checking as password hashing.

## 13. Security/parity interpretation

Original behavior provides:
- visual masking in the UI;
- direct password string in RAM;
- direct password field in settings.ini;
- direct use of the password for game login.

It does **not** provide recovered evidence of password-at-rest encryption.

A later security-hardening project could change that, but doing so during parity reconstruction would alter the original storage contract and is outside F03.

## 14. Reconstruction contract

For parity:

1. create password Entry with mask character `*`;
2. default Login screenshot state remains masked/checkbox unchecked;
3. `Hiện mật khẩu` only toggles Entry `show`;
4. apply toggle to visible and hidden rows;
5. never replace the actual Entry text with literal `****`;
6. preserve password string exactly for login use; do not trim it unless later direct evidence contradicts this;
7. keep password in the five-field account cache record;
8. serialize it directly in the existing pipe/newline account format;
9. do not add encryption/base64/hash transformations during parity work;
10. do not add clipboard or password debug logging;
11. keep actual game-input mechanics deferred to F06.
