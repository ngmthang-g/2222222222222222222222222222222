## 1. UI/nominal leader = first group combobox

The frozen group UI contract remains exact:

" Tên đội trưởng = acc của combobox đầu tiên; trống → (chưa chọn). "

Therefore the visible leader label is not discovered from TeamID or game memory. It is derived from the first configured group slot.

UI identity:
- first combobox selected -> that name is shown as leader;
- first combobox empty -> "(chưa chọn)".

## 2. Offline/stale first-slot selection is not preserved indefinitely in the live UI

_refresh_group_combo_values says:
- selections from earlier groups are removed from later choices;
- the current value is retained only while still valid;
- a dead/stale selection resets.

Ready accounts themselves are live HWND+PID rows from J01.

Therefore if the first-slot leader disappears from the ready/online set and refresh invalidates that selection, the leader label follows the now-reset first slot instead of retaining a stale game-leader name.

The exact UI callback order between combo reset, label refresh and config save remains a micro-order detail, but the stale-value reset semantic is frozen.

## 3. _group_targets produces the current online execution roster in group-slot order

Exact J01 doc:
"Acc online đã chọn trong Nhóm gd: [(name, hwnd)]."

Strong local mapping for _group_targets:
(self, gd, hwnd_by_name, hwnd, entry, seen, out, var, nm)

This binds the runtime roster to:
- the current group's combobox variables;
- unique names;
- online HWND resolution;
- append/output order following the configured slot iteration.

Blank/offline members are not part of the current execution roster.

## 4. _run_one_group owns a run-local leader HWND and per-member index

The frozen _run_one_group local model contains, in the worker-construction region:

- threads
- _leader_hw
- _idx
- _nm
- _hw
- _t.

The per-account worker receives:
- is_leader
- member_index
- total_members.

This is a separate runtime leader metadata layer from the visible leader label.

The strongest static model is:
- one current online target HWND is captured as _leader_hw;
- each current target is iterated with _idx;
- worker leader/member metadata is derived at thread creation.

Because Nuitka does not store the Python function body, the exact native source expression assigning _leader_hw is not instruction-bound by the constants blob. J02 therefore does not fabricate the literal source line.

## 5. The runtime leader is based on the current online target roster, not a TeamLeader memory read

This is the key architectural finding.

The complete PhoBanTab chunk contains:
- read_team_id: present for J01 party-state verification;
- read_team_leader: absent;
- TeamLeader: absent;
- LeaderID / leader_id / is_team_leader: absent.

The phoban_dungeons chunk also contains none of those team-leader read surfaces.

A shared memory_items read_team_leader helper exists elsewhere in the frozen EXE, but PhoBanTab/phoban_dungeons do not reference it.

Therefore current Phó Bản leader metadata is a **tool-side group/run concept**, not a live query of "who is currently team leader in the game".

## 6. This distinction matters when "Tạo lại đội" is OFF

recreate_team defaults OFF.

When recreation is OFF:
- no J01 B0/B1/B2/B3 team-recreation step establishes/verifies a game leader;
- _run_one_group still creates its per-account workers;
- those workers still receive is_leader/member_index/total_members.

Thus dungeon leader metadata does not depend on successfully recreating the in-game party.

Do not block is_leader creation waiting for read_team_leader; the frozen module has no such dependency.

## 7. Relationship to the J01 effective recreation leader

J01 independently proved that when recreate-team is enabled:
- nominal leader = first combobox;
- if nominal leader is offline, first online target becomes the effective **team-creation** leader;
- one online member skips team creation.

J02 finds the schedule/run side also works from the current online roster and owns _leader_hw.

Because both layers derive from the current group roster, they are designed to align in the normal path.

However the exact source expression proving that _run_one_group sets _leader_hw to targets[0][1] is not recoverable from the constant stream alone. That exact assignment remains **STRONG_STATIC_MAPPING**, not bytecode/source-level proof.

Do not silently equate "nominal UI leader", "effective recreate-team leader", and "run-local is_leader" in every pathological/offline race until Windows runtime resolves the final micro-edge.

## 8. _acc_step_worker explicitly carries leader metadata

Frozen _acc_step_worker local model:

Its exact doc:

"Worker 1 acc thực hiện MỘT bước lịch trình."

The worker dispatch surface contains _do_dungeon plus keyword tuple:

(stop_check, barrier, cancel, acc_name, is_leader, member_index, total_members)

Therefore leader metadata is not merely cosmetic UI data; it is forwarded into the dungeon execution call for each account.

## 12. The common dungeon pipeline does not currently branch on leader

The frozen _config_dungeon_memory documentation says the same memory configuration is written for every run/account:

- SelectedFuBen = selected dungeon code
- AutoRepeat=False
- FollowLeader=True
- AutoRevive=True.

No special "leader writes X / follower writes Y" branch is documented in the common pipeline.

The generic _do_dungeon flow likewise describes the same:
config -> move -> barrier -> start FuBen -> wait cycle

for each account.

Therefore common dungeon orchestration is symmetric across leader/followers except for the metadata carried into hooks.

## 15. FollowLeader memory field is not the same thing as PhoBanTab is_leader

The common dungeon config writes:

for the activity setup.

This is a game auto-FuBen setting written on each participating account.

It is separate from:
- PhoBanTab's tool-side is_leader Boolean;
- the visible first-slot leader label;
- J01's effective recreation leader.

Do not collapse these concepts into one variable during reconstruction.

## J02 reconstruction boundary

Preserve:
1. visible/nominal leader = first group combobox;
2. stale/offline group selections reset through the live ready/combo refresh model;
3. execution roster = current online selected targets in group-slot order;
4. run-local _leader_hw + _idx metadata layer;
5. _acc_step_worker carries is_leader/member_index/total_members;
6. _do_dungeon receives and forwards those fields;
7. DungeonCtx exact is_leader/member_index/total_members fields/defaults;
8. no dependency on read_team_leader / game-captain memory;
9. recreation OFF does not remove leader metadata from the dungeon worker model;
10. common dungeon setup remains symmetric and writes FollowLeader=True for all participants;
11. BaseDungeon has no leader-only behavior;
12. current SatTinhDungeon has no leader-only behavior;
13. first-combo leader source is also the identity source for J03 follow worker, while follower mechanics remain deferred.

Keep explicit UNKNOWN:
- exact native source expression assigning _leader_hw;
- exact Boolean expression producing is_leader from _leader_hw/current target;
- exact member_index base in the native source expression, although _idx/default 0 strongly supports zero-based indexing;
- pathological same-refresh-window handoff when first slot goes offline after targets are collected;
- whether an already-running group recomputes run-local leader metadata mid-step (no such recompute surface recovered);
- Windows/live-game observation of leader metadata and hook context.
