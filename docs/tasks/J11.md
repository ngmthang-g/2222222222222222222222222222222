## 10. One group becomes one runnable job

Exact `_collect_group_job` contract:

> Gom 1 nhóm thành job (num, targets, sched). None nếu nhóm thiếu
> acc online hoặc không có dòng lịch trình được tick.

Therefore start-all does not blindly create workers for every configured group.

For each group:
- resolve current online selected targets;
- get checked rows;
- if either side is empty → no job;
- otherwise produce `(num, targets, sched)`.

## 12. Run ownership is global registry + group-local cancel

Constructor run registry:
- `_run_lock`
- `_active_runs`
- `_run_jobs`.

Group-local state:
- `_run_cancel`.

J07 locked:
- a group is considered running only while its current run-cancel object exists and is not set;
- global state answers whether any group is running;
- group buttons control only their group;
- bottom button controls all.

J11 therefore freezes the ownership split:

```text
tab:
  _run_lock
  _active_runs
  _run_jobs

group:
  current _run_cancel
  current job/run identity
```

## 13. Groups are operationally independent

J04/J07 exact docs say:
- one `_run_one_group` worker per runnable group;
- groups run in parallel;
- rows are sequential only **inside that group**;
- accounts are parallel inside that group's current row;
- stopping one group does not stop the others.

A hard failure also uses the current group's cancel/barrier, not a tab-wide abort.

This is genuine multiple-group execution, not round-robin execution on one global worker.

## 14. One group finishing leaves other groups untouched

Exact `_finish_group_run` documentation:

> Dọn 1 nhóm vừa xong; nhóm cuối cùng xong thì teardown toàn cục.

The finishing block also carries:

`xong, còn <N> nhóm chạy tiếp`.

Therefore:
- Group A may complete/stop/fail;
- its own current run/job state is cleaned;
- Group B/C keep running;
- global teardown occurs only after the last active group is gone.

J07's identity comparison remains authoritative: stale cleanup from an old run may not delete a newly-started run of the same group.

## 15. Cross-group scope of Follow is “each running group separately”

J03 exact worker contract:

- each group's first combobox is that group's leader;

- each group uses its own leader position and member set.

For multiple groups:


## 16. Cross-group scope of discard is all accounts in running groups

J08 exact contract:
- periodic discard is run-scoped;
- member collector uses accounts of groups that are currently running;
- accounts are parallel;
- presets sequential per account.

Therefore an idle/configured group does not participate in the periodic discard pass merely because another group is running.

## 17. Cross-group scope of pickup is intentionally broader

J09 exact `_pickup_members` documentation:

`Tất cả acc được chọn (mọi cụm Nhóm), unique, giữ thứ tự.`

The pickup worker itself is run-scoped, but while at least one schedule run exists it keeps `PICKITEM.IsOn` repaired for **all selected Phó Bản members across all groups**, not only currently-running groups.

This asymmetry is original behavior and must be preserved.

## 18. Cross-group scope of Nga My buff is running groups only

- re-read current character info;
- Nga My + dungeon map → ON;
- otherwise → OFF.

Thus J10 follows running-group scope, unlike J09 pickup.
