## Main findings
- Runtime account rows are keyed by HWND and guarded by expected PID/window identity.
- Persistent Rao assignments are keyed by **real sanitized character name**, not HWND/PID:
  `[Rao] acc_<character name>`.
- Temporary fallback names beginning `Window ` are not normal restore identities.
- `_sanitize_name` removes HTML tags using `<[^>]+>`; no case-fold/lower normalization was recovered.
- Each account owns exactly **4 ordered Rao-selection slots**.
- Current account payload is a JSON list of four Rao display-name strings in slot order.
- `load_acc_config` only restores saved Rao names that still exist and returns True when at least one slot is applied.
- User combobox changes are traced by `_on_rao_var_changed`, mark the row as touched, and save settings.
- Rao rename/delete rebuilds every account combobox option list. Static locals plus the empty-string constant establish that stale selected names are cleared from the live UI; no old-name→new-name alias exists.
- Exact same-callback disk-save timing of that automatic clear remains unknown.
- `_has_real_name / _rao_touched` protect delayed RoleName loading from overwriting a row the user already changed manually.
- Same HWND with a different PID is treated as a dead/reused old window and causes runtime row recreation.
- Closed/reused HWND rows are removed/unbound; persistent name-keyed assignments remain available when the same real character reappears.
- Duplicate same-name characters remain separate runtime HWND/PID rows but collide on the same persistent `acc_<name>` key; exact collision winner is unknown.
- Editing an account's selected Rao while that slot is already running does not require a forced restart. M04's per-cycle resolution means the new assignment is observed on the next cycle after the current wait; blank/invalid selection then fails closed/stops the affected slot.
