## 1. Party has three distinct identity/state layers

Party must not collapse these into one value:

1. **physical runtime identity** — HWND + PID generation, already locked by G02;
2. **display/config identity** — sanitized `RoleName`;
3. **team-action identity/state** — `RoleID` + live `TeamID` from `memory_items`.

These layers have different lifetimes and different failure behavior.

## 2. What Party actually consumes from utils.get_character_info

Direct Party refresh constants:
- `utils.get_character_info`
- `_sanitize_name`
- regex `<[^>]+>`
- `RoleName`
- fallback prefix `Window `.

Within the frozen Party module range, G03 found **no direct Party field constants** for:
- `CurrentHP`
- `MaxHP`
- `HPPercent`
- `Level`
- `MapID`
- `PosX`
- `PosY`.

Therefore the Party ready/member UI consumes shared character info for **name/display identity only** in this layer.

Do not copy every field returned by `utils.get_character_info` into Party state merely because the shared reader can provide them.

## 3. RoleName is display/config identity, not team-action identity

Party's name path is:

`get_character_info(hwnd)`
→ `RoleName`
→ `_sanitize_name`
→ strip HTML-like tags with `<[^>]+>`
→ display/member name.

If a usable real name is not available, the Party block contains the fallback prefix:

`Window `

The exact suffix formatting after `Window ` remains UNKNOWN, consistent with C02/G02.

Important boundary:
- the placeholder is a UI/runtime fallback;
- it is not authoritative `RoleID` identity;
- saved Party groups use member names, not HWND or TeamID.

## 4. RoleID is resolved separately from memory_items.read_own_ids

The action-resolution block does **not** take RoleID from `get_character_info`.

It directly calls:
- `read_own_ids`
- `hwnd_of_pid`.

Original Party documentation:

`Ten acc -> [(name, hwnd, rid)] cho acc online.`

and:

`RoleID doc tu cua so co acc do (read_own_ids + hwnd_of_pid).`

The shared `memory_items` path contains the explicit own-account structure:

`[(pid, RoleID, Name, Lv)] moi cua so game.`

Thus selected Party member names are resolved at action time into:
- name
- owning PID
- current HWND for that PID
- RoleID.

This is intentionally separate from the ready-list RoleName display cache.

## 5. Name-to-RoleID matching behavior

The same Party resolver block contains:
- `strip`
- `by_exact`
- `setdefault`
- `by_lower`.

This proves the resolver builds name lookup structures with:
- trimmed-name handling;
- exact-name lookup;
- lowercase fallback lookup.

A selected name absent from the live own-ID set logs:

`: không online — bỏ qua`

A PID/record that cannot be mapped to a current game HWND logs:

`: không tìm thấy cửa sổ — bỏ qua`

Therefore stale saved/display names do not become synthetic RoleIDs.

## 6. RoleID read failure behavior

The resolver contains the direct diagnostic:

`[Party] Không đọc được RoleID: `

This is adjacent to the `read_own_ids` call surface.

If own-ID acquisition cannot provide a usable live resolution, the resolver does not invent a RoleID. Unresolved accounts subsequently fall out through the online/window-resolution path and are not represented as valid `(name, hwnd, rid)` targets.

### Explicit RoleID unknown
G03 found no Party equivalent of `NO_TEAM_IDS` and no Party documentation assigning a numeric RoleID sentinel such as 0 or 0xFFFFFFFF.

Therefore:
- do **not** declare `RoleID == 0` to mean invalid unless later stronger evidence proves it;
- the verified contract is resolver success vs unresolved/read-failure, not an invented numeric RoleID sentinel set.

## 7. TeamID comes from memory_items.read_team_id, not get_character_info

Party directly calls:

`memory_items.read_team_id(hwnd)`

Party's local documentation says:

`TeamID hien tai cua cua so (0 = chua vao doi, None = doc loi).`

The shared memory_items documentation is stronger:

`TeamID hien tai cua acc (0/0xFFFFFFFF = chua vao doi, None = doc loi).`

The Party module summary also states:
- TeamID is read from `RoleData+0xE8`;
- `0/0xFFFFFFFF` means outside/no team.

Thus the locked team-state model is:

- `0` → no team;
- `0xFFFFFFFF` → no team;
- `None` → read failure / unknown;
- any other accepted TeamID → real team identifier.

## 8. None is not equivalent to “outside team”

This is explicit in Party's wait-state documentation:

`None (doc loi) khong duoc coi la dat.`

Therefore `None` must not be merged into `NO_TEAM_IDS` for state-completion logic.

This distinction matters:
- 0 / 0xFFFFFFFF = known outside-team state;
- None = unknown because memory read failed.

A read failure cannot falsely satisfy “everyone has left the team”.

## 9. Real same-team state

Party has a dedicated same-team wait with exact documentation:

`Cho den khi 2 cua so cung TeamID that (loai 0/0xFFFFFFFF/None).`

So equality is accepted only after excluding:
- 0
- 0xFFFFFFFF
- None.

The group-level equivalent waits for all other targets to share the leader's real TeamID.

G03 records only the state predicate. Invite/create sequencing remains later Party action scope.

## 10. Team snapshot is diagnostic and preserves read failure

Party's `_team_snapshot` documentation says it builds:

`ten=TeamID,...`

for diagnostics, with:

`doc loi -> '?'`

Therefore snapshot/log formatting preserves the difference between:
- a real numeric TeamID;
- no-team numeric sentinel;
- unreadable/unknown TeamID.

It must not silently format read failure as 0.

## 11. NO_TEAM_IDS boundary

Party contains `NO_TEAM_IDS` and uses it in team-state waits.

The verified semantic members are:
- 0
- 0xFFFFFFFF.

`None` is explicitly outside this successful-no-team state because the wait documentation says read failure is not a reached condition.

G03 does not claim the exact Python container type or source-level literal syntax of `NO_TEAM_IDS`; only its evidenced semantic members.

## 12. RoleID/TeamID are not persisted Party configuration

G01 established Party config stores:
- `party_after`
- group member names.

G03 found no persistence contract for live RoleID or TeamID.

Correct lifecycle:
- group selection/config persists human/member names;
- current HWND/PID generation is runtime-only;
- RoleID is freshly resolved from live own-account records when actions need it;
- TeamID is freshly polled from live memory for team-state verification.

This prevents stale process/team IDs from surviving game restarts as trusted identities.

## 13. memory_items.read_team_leader is not the Party action source here

The shared memory_items module also contains a separate helper/documentation for team-leader RoleID at `RoleData+0xEC`.

However the frozen Party block does **not** reference `read_team_leader`.

Party's verified action-resolution source for member RoleID is `read_own_ids + hwnd_of_pid`.

Do not substitute the leader helper merely because it exists elsewhere in memory_items.

## 14. Failure-state matrix

| State | Meaning | Party treatment at this boundary |
|---|---|---|
| RoleName valid | display/config name | sanitize and use |
| RoleName unavailable/unusable | name not ready | temporary `Window ...` fallback |
| selected name absent from live own IDs | offline/stale selection | log + skip resolution |
| own ID read fails | RoleID source unavailable | diagnostic; do not invent RoleID |
| PID found but HWND missing | no current target window | log + skip |
| TeamID = 0 | known outside team | no-team state |
| TeamID = 0xFFFFFFFF | known outside team | no-team state |
| TeamID = None | read failure | unknown; never count as reached |
| TeamID real non-sentinel | currently in a real team | may participate in equality checks |
