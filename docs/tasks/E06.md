# E06 — Logging architecture

## STATUS
**VERIFIED_WITH_EXPLICIT_SIZE_CONSTANT_AND_THREAD_SERIALIZATION_UNKNOWNS**

E06 recovers the original diagnostic/logging architecture. It separates the central stdout/stderr session log, crash/faulthandler output, thread exception capture, memory diagnostics, injected automove diagnostics, and ordinary module log prefixes.

## 1. Central debug_logger startup service

The original `debug_logger` module contains:
- `setup`
- `_TeeWriter`
- `_trim_if_needed`
- `MAX_SIZE`
- `KEEP_SIZE`
- `tlmtool.log`
- `atexit`
- session start/end markers.

Exact module documentation:
- `File Logger - Tee stdout/stderr to an append-only session log in log/.`
- `Sessions run sequentially in one file log/tlmtool.log.`
- `File is trimmed (oldest dropped) when it exceeds MAX_SIZE.`

Thus logging is primarily a **stdout/stderr tee architecture**, not a Python logging.Logger hierarchy created separately for every feature.

## 2. Log path

Recovered startup path logic includes:
- `sys.frozen`
- `sys.executable`
- `join`
- directory `log`
- `makedirs(exist_ok=True)`
- filename `tlmtool.log`.

For the frozen application this supports:
`<tool executable directory>\log\tlmtool.log`.

E06 does not invent a different APPDATA log location.

## 3. Session markers

The logger writes session delimiters including:
- a line of `============================================================`
- `=== Start ... ===`
- `exe: ...`
- the Python runtime string
- `=== End ...`.

This means multiple launches append sequential sessions into the same log file rather than creating one file per launch.

## 4. stdout/stderr tee

Exact original documentation:
`Call once at startup. Tee stdout/stderr -> original + log file.`

and:
`Returns log_path. Sets sys._fl_tee_out / _fl_tee_err for restore.`

Recovered state:
- original `stdout`
- original `stderr`
- `sys._fl_tee_out`
- `sys._fl_tee_err`
- `_on_exit`
- `atexit`.

The tee writer writes to the original stream while also sending diagnostic text to the file. The compiled block also contains timestamp format `%H:%M:%S.%f`.

The exact micro-formatting rule for every partial write/newline fragment is not source-decompiled, so E06 does not fabricate whether every fragment receives its own timestamp.

## 5. Central log trimming

Exact original documentation:
`Drop oldest lines when file exceeds MAX_SIZE, keep newest KEEP_SIZE.`

Recovered behavior:
- checks file size;
- reads/seeks tail data;
- emits marker:
  `>>> log trimmed (oldest removed) <<<`
- retains newest content.

The exact numeric values of `MAX_SIZE` and `KEEP_SIZE` are not present as readable strings and remain **UNKNOWN**.

This is content trimming of one append-only file, not standard RotatingFileHandler filename rotation.

## 6. Startup crash/faulthandler file

Main startup recovers:
- `debug_logger.setup`
- `faulthandler`
- `crash_fault.log`
- a dedicated file handle
- `faulthandler.enable(file=...)`.

Therefore severe/native Python fault diagnostics have a second file path separate from `tlmtool.log`.

The exact resolved directory/mode of `crash_fault.log` is not fully source-visible from readable constants and remains **UNKNOWN**. E06 does not silently equate it with the `log/` directory.

## 7. Thread exception hook

Main startup installs a custom:
`threading.excepthook = main.<locals>._thread_excepthook`.

Recovered fields:
- `log_path`
- `[THREAD-EXC] `
- thread
- exception type/value
- `traceback.print_exception`.

This proves unhandled worker-thread exceptions are explicitly appended/reported through the central log path rather than being allowed to disappear silently.

## 8. Per-module log prefixes

Feature modules primarily use normal `print`/text diagnostics that are captured by the central tee. Representative prefixes recovered across the binary include:
- `[CONFIG]`
- `[DAILY]`
- `[PARTY]`
- `[DEBUG]`
- `[Farm]`
- `[LAYOUT]`

- `[SYNC]`-family messages
- `[Emu]`

- `[Toiuu watch]`

This explains why the central tee is important: feature modules do not need individual FileHandler instances to reach `tlmtool.log`.

## 9. memory diagnostics log

The memory subsystem contains:
- filename `tlm_memory.log`
- timestamp format `%Y-%m-%d %H:%M:%S`
- size check
- file removal/truncation path
- exact documentation:
  `Ghi log chẩn memory ra tlm_memory.log cạnh module (truncate >1MB).`

Therefore memory diagnostics use a **separate specialized log** rather than the general session log.

Verified:
- independent file `tlm_memory.log`;
- timestamped records;
- truncation when the file grows beyond approximately/exactly the documented 1 MB threshold.

Exact rewrite policy after the threshold (delete/recreate vs truncate-in-place branch details) is not fully source-decompiled, though `remove` is present.

## 10. automove/injected diagnostics

The package contains `data/automove_log.txt`.

D06 and Tối ưu static evidence establish:
- Tối ưu locates the log using `get_default_dll_path` + `automove_log.txt`;
- watchdog logic checks file size/position and scans lines such as:
  `[pid=(\d+)] Perf: ping`;
- missing pings contribute to tick-stall recovery logic.

This log is associated with the injected automove/performance payload path. TLMTool monitors it; E06 does not claim the main Python process is the only writer.

## 11. Debug-tab diagnostic exports

Debug tooling contains additional user-triggered diagnostic/log export surfaces, for example Bag Discard diagnostics.

These are feature diagnostics and do not replace the central logger. They are deferred to the relevant Debug/feature task if exact file naming/export semantics become necessary.

## 12. Thread-safety boundary

The central logger is used by many worker threads because stdout/stderr are process-global.

Readable `debug_logger` constants do not expose a dedicated logger mutex/queue.

Therefore:
- multi-thread use of the central tee is **architecturally verified**;
- explicit serialization mechanism for concurrent writes is **NOT RECOVERED**;
- E06 must not invent a queue-based or lock-based logging pipeline.

The operating/file-object behavior of the original writer should be preserved until runtime tests justify hardening.

## 13. Logging is not persistent application state

Logs are diagnostics only.

They must remain separate from:
- `settings.ini`
- `config.ini`
- login JSON state
- forwarder/proxy state files
- guest emulator JSON.

No startup behavior should load feature state from `tlmtool.log`, `tlm_memory.log` or `automove_log.txt` except explicit watchdog/diagnostic parsing such as the Tối ưu automove watcher.

## 14. Reconstruction contract

For parity:
1. call central debug logger setup during main startup;
2. write/append sessions to `log/tlmtool.log`;
3. tee stdout and stderr to original streams plus the file;
4. retain session start/end markers;
5. restore tee/original streams on exit through the recovered atexit path;
6. trim oldest central-log content when size limit is exceeded;
7. keep `crash_fault.log` as a separate faulthandler target;
8. preserve the custom worker-thread exception hook;
9. keep `tlm_memory.log` separate with its own size policy;
10. treat `automove_log.txt` as injected/performance diagnostic input for the watchdog;
11. preserve module prefix text because later parity/log analysis depends on it;
12. do not introduce an unproven logging framework/rotation policy.
