## 4. Memory source has tri-state semantics

Farm calls `is_connected`, which corresponds to the shared memory connection reader.

Exact shared memory documentation:

`Socket game còn nối không (TCPGame.Instance.tcpClient.Connected).
    True = đang nối, False = mất kết nối, None = đọc lỗi.`

The reconnect monitor uses this as a **memory veto**, not as the sole disconnect trigger.

Exact watchdog documentation:
- memory True → reset disconnect strike and never halt falsely;
- memory None → ignore memory result and let pixel detection decide.

Because the same doc still requires the pixel pair for 3 consecutive ticks before halting, a memory False result alone is not enough to trigger reconnect without the persistent dialog evidence.

## 14. Character memory cache is invalidated immediately after reconnect success

`_disconnect_monitor` locals directly include:
- `invalidate_character_cache`
- `_get_pid_from_hwnd`.

The shared helper's exact documentation says:

`Xóa Reader cache của pid — gọi ngay khi reconnect thành công.`

and explains why:
- after reconnect/character reload the in-memory structure may have changed;
- without invalidation, an old Reader pointer-chain cache could survive up to 10 seconds;
- invalidation forces the next read to resolve the chain fresh.

Therefore reconnect success must invalidate the character Reader cache for the current process generation before trusting old memory state.

## 15. Unsuccessful batch waits 30 seconds, then retries forever

Exact failure log:

`chưa kết nối lại được -> thử lại sau 30s`

The frozen block also contains exact integer **30** beside that failure path.

Exact watchdog documentation is stronger:

`KHÔNG BAO GIỜ tắt acc khi chưa kết nối lại được ... giữ trạng thái 'Chờ kết nối lại', thử lại vô hạn.`

Therefore:
- after a failed 5-attempt batch, wait **30 seconds**;
- begin another reconnect batch;
- repeat indefinitely.

The account is not disabled merely because one or many batches fail.

The exact primitive used for the 30-second delay—plain sleep vs interruptible event wait—is not safely source-visible; cancellation/exit checks are still part of the documented watchdog loop.

## 17. Post-reconnect memory-ready gate = 45 seconds / 3 consecutive valid reads

After reconnect success, Farm calls the shared:

`wait_memory_ready`

with exact frozen arguments:
- `timeout = 45.0`
- `need = 3`.

The helper's exact documentation says:
- `common.active` can appear before the character structures have finished loading;
- sending COPYDATA too early may be rejected by the DLL;
- memory is considered ready only after **need consecutive valid reads**;
- a valid read requires a clear RoleName and MapID not None;
- before each read it invalidates the Reader cache so the sample is fresh.

Thus `common.active` success is necessary for reconnect UI success but is not sufficient to trust character memory immediately.

## 18. Memory-ready timeout is explicitly fail-open

Exact `wait_memory_ready` documentation:

`Hết timeout → trả False để caller chạy tiếp như cũ + log (fail-open, không bao giờ kẹt farm).`

Therefore after 45 seconds:
- failure to achieve 3 consecutive valid memory reads does not permanently wedge the Farm worker;
- the gate reports False/logs;
- the caller is allowed to continue its recovery/cycle path.

Do not turn this into an infinite hard block.

## 22. False-positive defenses

The reconnect design has three distinct false-positive defenses:

1. memory True veto:
   - resets strikes;
   - never halts while memory explicitly reports connected.

2. dual-pixel requirement:
   - both disconnect probes must match.

3. temporal persistence:
   - both must match for 3 consecutive 2-second ticks.

A transient matching color in unrelated UI therefore cannot immediately trigger reconnect.
