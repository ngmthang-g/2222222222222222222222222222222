## 2. Ready-account discovery is live and PID-aware

The ready-account block is driven by:
- start_tab.get_windows
- _refresh_acc_list
- _add_or_update_member
- _remove_stale_members
- _pid_of
- bind_window_identity / unbind_window_identity.

Exact refresh documentation says it is incremental, performs window-list + character-info reads on a background thread, and applies UI updates on the main thread.

Exact cadence: 5000 ms / 5 seconds.

Exact stale rule:
- closed window -> remove ready member;
- HWND reused by another process -> remove old member.

## 3. Selected accounts disappear from the ready-account grid

Exact documentation:
"Sắp lại grid 3 acc / dòng; ẩn acc đã được nhóm nào chọn."

Therefore once an account is selected into any Phó Bản group, its ready-list entry is hidden from the free/ready pool.

This is a UI formation rule, not proof that the game party is already formed.

## 4. One group has six account slots

Exact _add_group_cluster documentation says one new group contains the leader row, delete button, "Nhóm n (6 combobox)", activity table and add-row button.

The group builder owns gvars, MAX_GROUP_MEMBERS and COLS_PER_ROW.

B07 independently confirms the visible layout as 6 slots = 2 rows × 3 comboboxes.

## 5. First combobox is the nominal leader slot

Exact leader-label documentation:
"Tên đội trưởng = acc của combobox đầu tiên; trống → (chưa chọn)."

Thus slot 1 has special UI meaning:
- first selected account = nominal leader;
- empty first slot -> leader label "(chưa chọn)".

Deeper leader responsibility is deferred to J02.

## 6. Cross-group account selection is unique

Exact _refresh_group_combo_values documentation says an account selected in an earlier group no longer appears in later-group dropdowns; a valid current selection is retained, while a stale/dead selection resets.

The old Group-1 compatibility helper also removes blank/duplicate names.

Normal UI formation therefore prevents the same ready account from being selected into multiple group definitions simultaneously.

## 7. Selection immediately refreshes formation state

Exact _on_group_selected documentation:
"Chọn xong 1 combobox → cập nhật danh sách các combobox còn lại + save."

Selection therefore immediately refreshes account choices, updates leader labels and enters the save path.

Detailed persistence/migration belongs to a later multiple-groups task.

## 8. Group combobox permission behavior

The module directly uses has_permission and check_account_limit with scope phoban_tab.

Exact docs say:
- enabled combobox state = readonly;
- denied state = disabled;
- permission is reapplied after heartbeat updates.

## 9. "Tạo lại đội" is opt-in and clean-default OFF

The UI variable is recreate_team_var.

Clean config fallback is exactly:
('phoban_recreate_team', '0').

B07 also shows the checkbox unchecked.

If this option is OFF, tool grouping alone does not recreate the in-game party.

## 10. Formation is the first pre-schedule stage when enabled

Exact _run_one_group documentation says that when "Tạo lại đội" is enabled, the group first runs:
B0 autoset -> B1 leave -> B2 leader create -> B3 burst invite.

Only after that does the schedule setup proceed.

If _pb_ensure_party fails, that group stops and does not proceed into its schedule.

## 11. Formation input is selected + currently-online members

Exact _group_targets documentation:
"Acc online đã chọn trong Nhóm gd: [(name, hwnd)]."

So:
- blank slot -> not a target;
- configured but currently offline/stale slot -> not in the current online target list.

## 12. RoleID resolution is a precondition for invite

_pb_resolve_targets transforms:
[(name, hwnd)] -> [(name, hwnd, rid)].

Exact documentation says:
- RoleID comes from read_own_ids + hwnd_of_pid;
- exact name match is preferred;
- case-insensitive fallback is supported;
- the already-confirmed group HWND is retained;
- one unresolved RoleID member is skipped and logged.

If zero targets resolve a RoleID, the group aborts party creation.

## 13. TeamID validity has explicit no-team sentinels

Frozen integer no-team set:

Textual no-team forms:
"0", "false", "".

_pb_wait_team_state says None/read failure never counts as success.

## 14. Effective leader fallback during recreation

Exact formation documentation:
"Trưởng nhóm = acc combobox đầu cụm (offline -> acc online đầu tiên)."

So:
- nominal/UI leader = first combobox;
- effective recreate-team leader = first combobox account if online/resolved, otherwise first current online target.

If only one online member exists, no team creation is needed and the group may continue.

Deeper leader semantics are deferred to J02.

## 16. B1 — leave pre-existing teams

Targets already outside a team skip leave.

Others call leave_team, then party state is polled for all targets to be outside a team.

If the leave-confirmation timeout expires, exact text says:
"chưa xác nhận thoát hết ... — vẫn tiếp tục".

Thus incomplete leave confirmation is warning/fail-open, not a hard abort by itself.

Numeric PB_PARTY_LEAVE_DELAY and PB_PARTY_WAIT_LEFT_TIMEOUT remain UNKNOWN.

## 18. B2 retries until a real TeamID is observed

_pb_invite_create:
- performs leader UI create;
- waits for real TeamID through _pb_wait_team_state;
- retries symbolically PB_PARTY_CREATE_RETRY times.

After all creation retries fail, exact behavior is to stop this group.

Numeric values of PB_PARTY_CREATE_RETRY, PB_PARTY_WAIT_TEAM_TIMEOUT and PB_PARTY_INVITE_RETRY_GAP remain UNKNOWN.

## 19. B3 — burst invite other resolved members

_pb_invite_burst:
1. invites all resolved non-leader members in a burst;
2. waits for all to share the leader's real TeamID;
3. resends only missing members once;
4. waits one more time.

The burst spacing, join poll and join timeout are controlled by PB_PARTY_BURST_DELAY, PB_PARTY_JOIN_POLL and PB_PARTY_JOIN_TIMEOUT; numeric values remain UNKNOWN.

## 20. Missing joins after the second wait are best-effort

The exact frozen _pb_invite_burst documentation says:
"False nếu bị hủy, True nếu xong (kể cả còn thiếu)."

If some invited members still have not joined after the resend, the module logs the missing list and team snapshot, but absent cancellation the burst helper still returns success.

Do not reconstruct "every invite must join or abort"; that would contradict the frozen original.

## 21. Cancellation is cooperative

Formation owns:
- _pb_party_cancelled
- _pb_party_sleep.

Exact sleep documentation:
"Sleep ngắt được: True nếu bị hủy (cancel nhóm hoặc cancel tổng)."

Group or global cancellation therefore interrupts party sleeps/waits.
