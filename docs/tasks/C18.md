# C18 — Đồng bộ các cửa sổ

## STATUS
**VERIFIED_WITH_EXPLICIT_WORKER_CADENCE_AND_INITIAL_STATE_UNKNOWNS**

C18 recovers the layout/window synchronization subsystem from the original TLMTool 2.1.2 inner EXE. Mouse/keyboard event replication is intentionally deferred to C19.

## 1. Real UI control and runtime state
Original Start/Xếp-lưới UI recovers:
- visible button: `Đồng bộ các cửa sổ`
- callback: `_toggle_layout`
- button state object: `btn_layout`.

Original Start runtime state includes:
- `layout_active`
- `sync_layout_running`
- `sync_loop_id`
- `_grid_slots`.

These fields establish a persistent layout-sync state machine rather than a one-shot arrange button.

## 2. Toggle has distinct off/on visual states
Original binary contains the same button label with:
- green `#388e3c` state
- red `#f44336` state.

The text remains `Đồng bộ các cửa sổ`; state is conveyed by the toggle state/color rather than a different visible label.

## 3. Starting layout sync uses a dedicated maintenance pipeline
Recovered methods:
- `_toggle_layout`
- `_sync_windows_loop`
- `_layout_worker`
- `_stop_sync_loop`
- `_refresh_cache`
- `_arrange_grid`.

Recovered runtime log:
`[LAYOUT] ON layout_active=... sync_layout_running=...`

Verified architecture:
`toggle layout ON → synchronization loop/worker → cached current HWND set → arrange grid → continue maintaining layout while active`.

## 4. Layout worker consumes the worker-cached game-window list
Exact original documentation for `_refresh_cache`:
`Cập nhật cache window list từ worker thread (không block main thread).`

Therefore layout maintenance does not repeatedly run a blocking game-window enumeration directly on the Tk main thread.

## 5. Grid application is master-aware
C06/C08 and the original `_arrange_grid` doc establish:
- current `grid_cols` / `grid_rows` are used;
- master HWND is always position/index 0, top-left;
- remaining game HWNDs follow in order;
- `GetSystemMetrics` participates in geometry calculation.

Thus C18 is not merely 'keep current window coordinates'. It continuously reapplies the tool's grid model to the current game-window set.

Exact x/y/w/h arithmetic remains the already-preserved C06 UNKNOWN and is not re-guessed in C18.

## 6. Mode integration
Original `_on_mode_change` documentation states:
- selecting internal mode `sync` / visible `Xếp lưới` automatically enables window/layout sync and input sync;
- switching to Auto/manual automatically disables both.

Therefore layout sync has both:
1. direct user toggle through `Đồng bộ các cửa sổ`;
2. automatic lifecycle control through the Start mode switch.

## 7. Max-window guard is part of the layout-sync path
Recovered around the layout subsystem:
- `_get_max_windows`
- `_count_game_processes`
- warning text for exceeding the allowed number of windows;
- `_auto_stop_sync`.

Exact original `_auto_stop_sync` documentation:
`Tắt cả layout sync và input sync khi quá limit.`

Therefore:
- layout sync cannot remain active beyond the runtime window-limit policy;
- over-limit handling shuts down both synchronization subsystems.

Exact source comparator around the limit remains UNKNOWN from C06/C08.

## 8. Stop lifecycle
Recovered `_stop_sync_loop` is shared in the synchronization lifecycle.

When layout sync is turned off or the mode changes back to Auto/manual, the running layout maintenance path is stopped rather than left as a background arranger.

Readable static evidence does not expose the exact scheduling primitive/cancellation statement for every branch, so the exact stop-call ordering remains UNKNOWN; the existence of the stop helper and mode contract is VERIFIED.

## 9. Master-change interaction
C05 proved that manually changing master while input synchronization is ON automatically disables input sync and unlocks slaves.

No equivalent original documentation says that changing master automatically disables **layout sync**.

Therefore C18 preserves the distinction:
- input-sync auto-off on master change: VERIFIED elsewhere;
- layout-sync auto-off on master change: NOT PROVEN.

Because `_arrange_grid` is master-aware, later layout passes will use the current master at index 0. Exact immediate timing of that re-layout after a master change is UNKNOWN.

## 10. Layout-worker cadence remains unknown
The original EXE has several unrelated timers:
- Auto tiling: 1 second;
- input-sync keepalive: 1.5 seconds;
- embedded preview maintenance: 800/2000 ms;
- Start list poll: 2 seconds.

No readable constant has yet proven the exact `_layout_worker` cadence.

C18 explicitly keeps this UNKNOWN and does not copy one of those unrelated timer values.
