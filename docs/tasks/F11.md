## 5. F11 new static resolution: exact generic readiness poll = 1 second, max 20 polls

The original EXE contains a later Party dispatch helper that explicitly documents itself as the same waiting behavior as `login_tab._wait_and_activate`:

`Giong login_tab._wait_and_activate: tab an khong quet → sau khi chuyen tab phai doi toi da 20s cho du hwnd. Chi doc _acc_rows.get("hwnd") o background ...`

Immediately before that documentation, the frozen EXE constant stream contains:
- serialized integers 0, 20, 1;
- identifier `issubset`;
- identifier `sleep`;
- serialized float 1.0.

Evidence offsets in the frozen EXE:
- integer/range block starts around file offset `0x2b808a4`;
- `issubset` at `0x2b808ab`;
- `sleep` at `0x2b808b5`;
- float 1.0 immediately follows at `0x2b808bd`;
- cross-reference documentation begins around `0x2b8094c`.

Together with the explicit “same as login_tab._wait_and_activate” statement, this closes the F10 generic readiness cadence:

**poll once per second, for at most 20 seconds.**

## 6. F11 new static resolution: generic target-row readiness uses HWND set inclusion

The same original block contains `issubset` and explicitly says it reads `_acc_rows.get("hwnd")` while waiting for enough HWNDs.

The parity model is therefore:

- `want` = target HWND set that must appear after switching to the destination tab;
- each poll builds `have` from the target tab's scanned `_acc_rows` HWND values;
- readiness succeeds when `want.issubset(have)`;
- poll interval = 1.0s;
- maximum wait = 20s;
- actual widget/start dispatch occurs back on the main thread.

This resolves F10's generic Train / Train LSV / Dồn vàng row-match uncertainty.

Party still uses its dedicated `_member_rows` / `_running` / `_toggle_run` path. The exact source expression used to construct Party's readiness set is not separately exposed enough to claim instruction-level identity with the generic `_acc_rows` expression, so F11 does not invent it.

## 7. Completion/routing signature evidence

The frozen login_tab code-object metadata contains:
- `_auto_start_after_login` locals consistent with `self, mode, tab, _TAB_TEXT, _wait_and_activate`;
- `_auto_start_party_after_login` locals consistent with `self, tab, _wait_and_activate`.

No `success` or `results` argument is passed into either routing helper.

The completion metadata also contains a `self, success, total` shape and the completion constant block contains the `_auto_start_after_login` call surface.

This narrows the architecture:
- account workers settle first;
- completion owns success/total aggregation;
- post-login routing helper is invoked without a per-result argument and derives its window target from LoginTab state.

## 8. Remaining runtime-only boundary: mixed success / zero success

Static evidence still does not prove the exact branch guard around the completion call for:
- some accounts succeed, some fail;
- all selected accounts fail.

Because `_auto_start_after_login` receives no explicit success/results argument, the exact rule could depend on the completion guard and/or current tracked-online state.

F11 therefore keeps this as a **runtime-only unknown** rather than inventing a rule.

Required later runtime parity cases:
1. 2 selected, 2 succeed.
2. 2 selected, 1 succeeds / 1 fails.
3. 2 selected, 0 succeed.
4. existing tracked online window + new batch all fail.
5. destination already running.
6. destination tab hidden before routing.

The implementation stage must not mark this branch verified until those cases are compared against the original on Windows.
