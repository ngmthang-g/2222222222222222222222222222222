## Main findings
- Rao message definitions are live rows with name_var/msg_var/chan_var/sec_var.
- The visible trimmed Rao name is the identity used by account selections; no persistent row UUID is recovered.
- _rao_names preserves current row order; _next_rao_name generates the smallest unused Rao N.
- Row variable writes trigger _save_config and _refresh_acc_rao_options through the nested _rao_save trace callback.
- Deletion removes the row, persists the new definition family and refreshes account Rao-name choices.
- _resolve_rao is name-based and fails closed for no selection, empty content, no channel, missing interval or deleted/missing definition.
- Current message storage is under [Rao], name-keyed as rao_<trimmed Rao display name>.
- Payload is JSON with content/channel/sec and ensure_ascii=False.
- Save rewrites only the rao_ message family while the acc_ family remains a separate persistence surface.
- Load sorts rao_ keys, derives name from the key suffix, json.loads the payload and recreates rows via _add_rao_row(name/content/seconds/channel).
- No manual duplicate-name rejection is recovered. Name-keyed persistence means duplicate display names cannot persist as two independent records; exact duplicate winner remains UNKNOWN.
- Rename/delete removes the old name from the valid account option universe; no old→new alias/UUID rename propagation is recovered. Exact immediate StringVar clear-vs-preserve behavior is deferred to M05, but stale old names cannot resolve and later account restore accepts only names that still exist.
- Channel mapping is M03; interval type/default/clamp/timing is M04; account selection persistence is M05.
