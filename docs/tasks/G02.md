## 1. Party does not enumerate Windows itself

Inside the Party module, the refresh path contains:
- `start_tab`
- `get_windows`
- `utils.get_character_info`
- `_get_pid_from_hwnd`

No Party-local `EnumWindows`, `IsWindowVisible`, `GetWindowThreadProcessId`, or independent discovery callback is present in the Party module block.

The already-verified C01 contract for `start_tab.get_windows()` is therefore the upstream source:
- Start owns the physical game-window enumeration;
- its background producer updates the cached window list at about 3 seconds;
- `get_windows()` reads that cache without blocking the Tk main thread.

Party is a **consumer** of the shared Start window cache, not a second enumerator.

## 2. Party has its own incremental refresh loop

G01 established constructor lifecycle:
`_build_ui → _load_config → Destroy bind → _start_refresh`.

G02 recovers the refresh surface:
- `_refresh_acc_list`
- nested `_worker`
- daemon `Thread`
- nested `_apply`
- Tk `after`
- `_refresh_active`
- `_refreshing`
- `_schedule_refresh`
- `_stop_refresh`
- `after_cancel`

The work split is therefore:

`background worker: read cached windows + read character info`
→ `main-thread apply: mutate Party widgets/member rows`.

The worker is explicitly created with `daemon` and `start`.

The presence of `_refreshing` is the Party overlap guard. G02 does not invent its exact source-level Boolean expression.

## 3. Exact Party recurring cadence = 3000 ms

Immediately after the Party refresh scheduling symbols in the frozen constant stream, the encoded integer bytes are:

`6c b8 17`

The small-int encoding used by the same frozen EXE was already validated in F11 (`l 14` = 20; `l 01` = 1). Decoding the two-byte unsigned LEB128 payload:

`0xB8 0x17 → 3000`.

Thus Party's own scheduled refresh interval is:

**3000 ms = 3 seconds.**

This is separate from:
- Start's 2-second Start-tab UI poll;
- Start's approximately 3-second background EnumWindows/cache producer;
- preview repaint clocks.

Party itself consumes the cached window list on its own 3-second loop.

Exact first-tick timing after `_start_refresh` — immediate call vs first scheduled 3-second tick — remains explicit UNKNOWN because the readable constant surface does not prove that micro-order.

## 4. Background worker inputs

Direct Party constants show:
- `start_tab.get_windows`
- `utils.get_character_info`
- `_get_pid_from_hwnd`
- worker result variable `infos`.

The recovered model is:

1. obtain current cached `(hwnd, title)` window candidates from Start;
2. resolve/read character info per HWND in the worker;
3. carry HWND + character data into the UI-apply phase.

This avoids doing character-memory reads directly on the Tk thread.

## 5. Main-thread apply

The nested worker contains nested `_apply` and Tk `after`.

The apply block directly references:
- `_add_or_update_member`
- `_remove_stale_members`
- `active_hwnds`
- `_apply_group_permission`
- `_schedule_refresh`.

Therefore a refresh cycle converges on the main/UI thread to:
1. add or update rows for active windows;
2. remove stale rows;
3. re-apply Party group permission state;
4. schedule the next refresh.

The exact numeric delay passed to the Tk `after` used for the worker→UI handoff is not independently locked by readable Party constants, so G02 records only **main-thread Tk-after dispatch**, not an invented `after(0)`.

## 6. Runtime Party identity is HWND + PID generation

Party direct constants in `_add_or_update_member` include:
- `_pid_of`
- `mouse.bind_window_identity`
- row field `pid`
- `mouse.unbind_window_identity`.

This matches the already-verified C02 global identity contract:
- `bind_window_identity(hwnd, pid)` records the HWND→PID snapshot;
- falsy PID is ignored by the shared helper;
- `unbind_window_identity(hwnd, pid)` removes only the matching generation;
- current PID mismatch means the numeric HWND has been reused by another process.

Thus Party does **not** trust HWND alone.

Safe runtime physical identity is:

**HWND + PID generation snapshot.**

## 7. Same HWND reused by a different process — direct Party proof

The frozen Party bytes contain the exact message fragments that decode to:

`[Party] hwnd=<...> đổi process (pid <old> → <new>) → xóa member cũ`

Adjacent constants include:
- `unbind_window_identity`
- `destroy`
- `_refresh_group_combo_values`.

This directly proves Party handles HWND reuse as a replacement, not an in-place character rename.

On PID-generation mismatch:
1. old member identity is unbound using the old generation contract;
2. old member widget/state is destroyed;
3. group/dropdown state is refreshed;
4. the current HWND/process generation is treated as a new live member.

This prevents an old Party row from silently attaching to a different game process that inherited the same numeric HWND.

## 8. Closed/disappeared windows

The worker/apply path builds `active_hwnds` from the current Start window set and calls `_remove_stale_members(active_hwnds)`.

Therefore a Party row whose HWND no longer appears in the active shared window set is removed incrementally.

Combined with the C02 identity contract:
- disappeared HWND → stale row removal;
- same HWND but new PID → stale generation replacement.

Party does not need a Party-local `IsWindow` scan to implement these two cases.

## 9. Character name used by ready list

Party direct constants show:
- `_get_char_info`
- `_sanitize_name`
- regex `<[^>]+>`
- `RoleName`
- fallback prefix `Window `.

Therefore the ready-list name layer is:
- read shared character info;
- sanitize HTML-like tags from RoleName;
- use the sanitized RoleName when available;
- otherwise use a temporary `Window ...` placeholder.

As already locked by C02, the exact suffix after `Window ` is not statically proven and remains UNKNOWN.

G02 stops at display/logical name identity. HP, level, map, team state and other character semantics are G03+.

## 10. Ready-list relayout

Party contains `_relayout_ready_list` with exact original documentation:

`Sắp lại grid 3 acc / dòng; ẩn acc đã được cụm nào chọn.`

Thus:
- the ready-account list is laid out 3 accounts per row;
- accounts already selected into a Party cluster are hidden from the ready pool rather than duplicated there.

This is dynamic UI state, not a fixed list.

## 11. Group dropdown values follow live Party members

Party contains:
- `_ready_names`
- `_refresh_group_combo_values`
- `_update_all_leader_labels`.

Exact original documentation for dropdown refresh:

`Cập nhật dropdown từng frame: trong 1 frame, acc đã được cụm trước chọn thì không còn hiện ở cụm sau. Giữ giá trị đang chọn.`

Therefore after member-set/selection changes:
- available names are recomputed from the live ready-member set;
- names already taken by an earlier cluster are filtered from later cluster choices;
- the current selected value is preserved where possible;
- leader labels are refreshed.

This is the bridge from HWND lifecycle changes to the six Comboboxes per Party cluster.

## 12. Role of bind/unbind in later actions

The shared C02 action-layer contract rejects a target when the current PID no longer matches the stored HWND snapshot.

Party's direct use of `bind_window_identity` / `unbind_window_identity` therefore is not cosmetic bookkeeping. It supplies the generation guard used by later window-targeted operations so a stale Party member cannot direct clicks/actions to a reused HWND.

Detailed Party action behavior is still deferred; G02 only locks this identity safety boundary.

## 15. G02 reconstruction contract

Later Party reconstruction must:
1. use shared `start_tab.get_windows()`; do not add a second Party EnumWindows scanner;
2. keep window/character reads off the Tk thread;
3. run Party's own recurring refresh every **3000 ms**;
4. apply member/widget mutations on the Tk main thread;
5. key runtime members by HWND with a PID-generation snapshot;
6. bind new/current HWND identities through the shared identity layer;
7. detect numeric HWND reuse by PID mismatch and destroy/recreate the member state;
8. remove rows whose HWND disappears from the current active shared set;
9. sanitize RoleName and support a temporary Window placeholder without inventing its suffix;
10. relayout ready members 3 per row and hide names already assigned to groups;
11. refresh group Combobox values/leader labels when the live member set or selections change;
12. cancel the scheduled refresh when Party is stopped/destroyed;
13. keep deeper character state in G03 and team action behavior in later G tasks.
