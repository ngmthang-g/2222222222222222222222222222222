## 1. “Ngựa” in Train navigation priority is the mounted-movement fallback boundary

H02/H05 already locked:
- four return-home priority choices: `Phù 1 / Phù 2 / Phù 3 / Ngựa`;
- `_get_nav_priority` passes that ordered list into `move_character`.

Inside the frozen `move_character` constant block, the home-priority branch contains:
- exact value `Ngựa`;
- a `Stop` sentinel surface;
- log `[di chuyển]   Về thành: thử <...> → bấm phím <...>`;
- `press_single_key_dll`;
- transfer-dialog probes `common.dichChuyen1` / `common.dichChuyen2`.

The horse value appears at the boundary before the teleport-hotkey path, while the actual mount action is handled later by the shared memory/packet mount machinery.

The safe reconstruction contract is therefore:

- `Phù 1/2/3` participate in the teleport/hotkey attempts;
- reaching `Ngựa` means stop trying further phù-style home methods and fall through to the normal mounted/autopath movement path;
- `Ngựa` is **not** a separate user-configured mount hotkey and no direct horse click is recovered in this priority block.

The exact source spelling/branch around the internal `Stop` sentinel is not instruction-visible enough to reproduce statement-for-statement and remains implementation-level UNKNOWN.

## 2. Current mount engine is ensure_mounted

The shared live helper is:

`ensure_mounted(hwnd, stop_check, stop_auto_first)`

Exact original documentation:

`Đảm bảo đang cưỡi ngựa, hoàn toàn bằng memory + packet (không pixel/click).`

This explicitly replaces the older pixel/click mount method.

No Train reconstruction should reintroduce UI clicking for normal mount actions.

## 3. Riding-state fast path = IsRiding

Exact ensure_mounted documentation:

`Đọc IsRiding từ memory; đã cưỡi (==1) -> True ngay.`

Thus current riding state is read from the live character memory field:
- `IsRiding == 1` → already mounted; return success immediately.

This is distinct from mount ownership/equipment availability.

## 4. HasMount is a separate equipped-mount signal

The shared memory/item layer exposes:
- `HasMount`
- `MountItemID`
- `read_mount_cached`
- `has_mount`.

Exact documentation:

`Acc có EQUIP thú cưỡi không (Site 2 trong RoleData.Items).
1 = có ... 0 = không, None = đọc lỗi.
Khác is_riding (đang ngồi trên ngựa hay không).`

So the current tool separates:
- **HasMount** = account currently has/equips a mount item;
- **IsRiding** = character is currently riding.

Do not collapse these into one boolean.

## 5. Mount-equipment cache TTL = 30 seconds

The frozen memory-reader constant binds:

`MOUNT_CACHE_TTL = 30.0`

and `read_mount_cached` uses that cached equipped-mount state.

This keeps frequent movement polling from repeatedly rescanning the Site-2 equipment structure.

The riding verification itself is explicitly described as fresh and must not rely on stale mount-state cache.

## 6. Optional stop-auto step before mounting

Exact ensure_mounted documentation:

`Dừng auto game (Lua StartAutoFight None) để hành động hiện tại khỏi gián đoạn mount ... — chỉ khi stop_auto_first.`

Direct dependency:
- `set_auto_mode`

Exact logs:
- `[Mount] hwnd=... gui stop-auto that bai (van thu mount)`
- `stop-auto loi: ...`

Therefore:
1. normal mount flow may stop game auto first;
2. failure to stop auto does **not** hard-abort the mount attempt;
3. the helper still tries to mount.

The doc also says:

`stop_auto_first: False khi vừa teleport về (UI reset, khỏi stop thừa).`

Thus callers may deliberately skip this stop-auto precondition after a teleport/reset.

## 7. Mount command is internal, not mouse-driven

The shared mount action surface is:

`toggle_mount`

with frozen internal command:

`Game.SendToggleRideState(Game.CurrentMountSlot)`

The ensure_mounted doc describes it as the same mount packet/action used by the ride button on SkillBar.

Therefore current mount activation is an internal game/Lua/packet action, not a physical click.

## 8. One ensure_mounted attempt sends mount, waits 3 seconds, then verifies fresh IsRiding

Exact documentation:

`Gọi mount qua packet SendToggleRideState ... sleep 3s cho lên ngựa, verify lại IsRiding bằng memory fresh (xóa cache).`

So one ensure attempt is:

1. if already `IsRiding==1` → success;
2. optional stop-auto;
3. consult mount availability/action surfaces;
4. send the internal toggle-mount action;
5. wait exactly **3 seconds**;
6. invalidate/fresh-read character state;
7. verify `IsRiding`.

Return contract is exact:
- True = already riding or successfully mounted;
- False = failed/stopped.

No internal multi-send retry loop is described or recovered inside ensure_mounted itself.

## 9. Mount-action failure is explicit

Exact mount block includes:
- `has_mount`
- log `gui lenh cuoi that bai`
- `toggle_mount`
- `IsRiding`.

The helper therefore does not blindly assume that issuing the command means success.

A successful return requires the post-wait riding-state verification.

## 10. Mid-route mount loss is recovered by _remount_requeue

Exact original documentation for `_remount_requeue`:

`Mất cưỡi giữa đường: stop autopath -> mount lại (memory+packet) -> requeue.
Thay toàn bộ cụm retry-remount cũ (pixel clicks + Reader thủ công).
Trả False nếu bị stop giữa chừng (caller break vòng poll), True để poll tiếp.`

This locks the active remount sequence:

1. stop current autopath;
2. call the memory/packet mount engine;
3. queue the same autopath target again;
4. continue movement polling.

Direct dependencies:
- `stop_autopath`
- `ensure_mounted`
- `queue_autopath`.

Exact logs also exist for:
- stop_autopath error;
- requeue error;
- remount-requeue error.

Unless the user/session stop condition is hit, the helper is designed to let the outer movement poll continue rather than replacing movement with the old pixel retry routine.

## 11. move_character actively tracks mount/remount state

The live `move_character` locals/constants contain:

- logs `bị stop trong lúc remount` and `bị stop sau remount`.

Therefore Train's ordinary movement actively watches whether a mount-equipped account loses riding state during autopath and can perform route-aware remount/requeue.

## 12. There is no active Train-specific dismount routine

In the active FarmTab + shared movement path H10 recovers:

- remount/requeue.

It does **not** recover:
- a Train/Farm `dismount` helper;

- a pixel/click dismount sequence.

Teleport/map transitions may naturally clear `IsRiding`; the current movement system reacts by mounting again when needed.

Do not add an explicit dismount step unless later evidence requires it.

## 13. Same-map NPC movement uses mounted movement

The shared `move_to_npc` exact documentation says:

`Cùng map + tra được pos NPC → move_character (cưỡi ngựa, poll đến nơi, tolerance rộng cho điểm đông) → click NPC → verify dialog.`

This matters because H05's active Truyền `npc_hub` step routes through `move_to_npc`.

When the NPC is on the same map and its position is known:
- the normal mounted `move_character` engine is used;
- mount/remount behavior therefore applies.

## 14. Cross-map/NPC-not-spawn fallback intentionally avoids the horse path

The same exact `move_to_npc` documentation says:

`Khác map / NPC chưa spawn (pos NIL) → fallback logic game (tự đổi map, không ngựa) + verify dialog.`

Thus the route layer has an explicit boundary:
- same-map coordinate approach → mounted movement;
- game-native fallback for cross-map/NPC-not-spawn → no horse movement layer.

Do not force ensure_mounted around every game-native goto fallback.

## 15. A mount-before-goto failure is non-fatal in the NPC helper

The frozen NPC helper contains exact log:

`mount trước goto lỗi (bỏ qua): ...`

Therefore when the helper attempts its mounted approach, a mount preparation error can be logged and ignored so the higher-level NPC navigation logic may still use its fallback path.

This is consistent with the system's broader rule that horse riding is an optimization for movement, not the sole way to progress.
