# G06 — Party sync-keyboard relationship audit

## STATUS
**VERIFIED_NO_PARTY_KEYBOARD_SYNC_OWNERSHIP_OR_START_INPUT_SYNC_CALL_EDGE**

G06 follows the original Party task order from PLAN.md. GitHub was checked first: G01–G05 are complete, no G06 artifact existed, and STATE.md pointed to G06. Completed Party work was not repeated.

G06 audits only Party ↔ keyboard-sync ownership/call edges. It does not redo the Start/input implementation already closed by C19.

## 1. Party implementation range has no keyboard-sync state or listener surface

Static scan of the frozen Party implementation range recovered zero Party occurrences of:
- `keyboard`
- `pynput`
- `keyboard.Listener`
- `_on_master_key_press`
- `_on_master_key_release`
- `input_active`
- `_toggle_input`
- `_sync_keepalive`
- `_sync_locked`
- `WM_MY_SYNC_KEY`
- `GetForegroundWindow`
- keyboard `vk` forwarding state.

Therefore PartyTab does not own a keyboard listener, keyboard-sync state machine, or dedicated key-forwarding worker.

## 2. Party does not call Start's input-sync toggle

G05/G02 already established Party's direct Start dependency is `start_tab.get_windows()` for live member discovery.

G06 found no Party reference to:
- `start_tab._toggle_input`
- `start_tab.input_active`
- Start keyboard listener handlers;
- Start sync keepalive;
- Start custom key-message path.

Thus Party start/stop/group operations do not directly enable, disable or reconfigure Start keyboard synchronization.

## 3. Start/window subsystem remains the keyboard-sync owner

C19 is the authoritative shared input-sync contract.

Verified Start keyboard path:
- UI control `Đồng bộ phím chuột`
- callback `_toggle_input`
- state `input_active`
- selected Start master HWND is the input source
- `keyboard.Listener`
- `_on_master_key_press`
- `_on_master_key_release`
- `GetForegroundWindow`
- virtual-key `vk`
- custom `WM_MY_SYNC_KEY` path.

Exact custom-message payload remains a C19 explicit UNKNOWN and is not reopened by G06.

## 4. Party leader is not the keyboard-sync master

G04 already proved no evidence equates:
- Party group leader
with
- Start master HWND.

G06 finds no new keyboard-side call/assignment that changes that conclusion.

Selecting/changing a Party leader therefore must **not** automatically:
- make that HWND the Start sync master;
- restart Start keyboard listeners;
- enable/disable `input_active`.

If a user independently enables Start input sync, Start's own master rules remain authoritative.

## 5. Party direct action input is not keyboard synchronization

The Party block does contain direct action helpers:
- module/symbol `mouse` around `0x2b7daa3` for shared window-identity functions;
- `click_at` around `0x2b7f0db` / `0x2b7f0e5`;
- `check_pixel`;
- shared `resize_window`.

These are used by Party's own UI/game action paths such as create-team/invite work.

They are fundamentally different from Start keyboard synchronization:

`Party action worker → target one intended game HWND directly`

versus

`Start keyboard listener → capture master key event → broadcast/synchronize to slave HWNDs`.

G06 must not merge those models.

## 6. No Party direct keyboard-send helper recovered

Within the Party range G06 also found zero:
- `press_at`
- `send_key`
- `send_keyboard`
- `PostMessage`
- `SendMessage`
- `SendInput`
for a Party-owned keyboard action path.

This means the currently recovered Party create/invite/group-action surface is click/state based, not a Party-local keyboard macro engine.

This negative result is limited to the frozen Party implementation; it does not assert that shared helpers elsewhere in the executable are absent.

## 7. Party member count/group membership does not define keyboard-sync targets

Party can hold:
- ready accounts;
- group clusters;
- leader/followers.

Start input sync independently computes its slaves from the Start master/current game-window subsystem.

No Party call edge was recovered that passes:
- a Party group member HWND list
into
- Start keyboard-sync target selection.

Therefore reconstruction must not infer that “members of Party group N” are automatically the keyboard-sync slaves.

## 8. Mode and limit behavior remain Start-owned

C19/C08 already prove:
- Xếp-lưới mode can auto-enable input sync;
- Auto/manual disables it;
- changing Start master while input sync is active turns input sync off/unlocks slaves;
- runtime max-window handling can stop input sync.

Party does not override these rules.

G06 adds no Party-specific keyboard-sync lifecycle.

## 9. B04 cross-check after static extraction

B04 shows Party grouping controls and member names.

It contains no keyboard-sync control.

That visual result is consistent with the EXE-first audit, but G06 does not derive behavior from the screenshot.

No B04 geometry or UI change is required.

## 10. G06 reconstruction contract

Later reconstruction must:
1. keep keyboard synchronization owned by Start/window input subsystem;
2. not add `keyboard.Listener` or key-forwarding state into PartyTab;
3. not call Start `_toggle_input` when Party starts/stops or when a group leader changes;
4. not equate Party leader with Start sync master;
5. not use Party group membership as the Start keyboard-slave list;
6. keep Party direct click/state action helpers separate from synchronized keyboard input;
7. not invent Party `press_at`/PostMessage/SendInput keyboard macros where the frozen Party block has none;
8. reuse C19 unchanged if Start input sync is active independently.
