## 1. Quan trọng nhất: 800/2000 ms KHÔNG phải FPS render của game preview

C03 đã xác minh preview hình ảnh dùng **DWM Thumbnail**.

DWM compositor tự render live thumbnail từ source HWND → destination overlay HWND.

TLM không có vòng:
- BitBlt mỗi 800 ms;
- chụp frame mỗi 2000 ms;
- hoặc app-level FPS render preview.

Vì vậy các giá trị **800 ms / 2000 ms** trong Start là cadence của **preview maintenance/update loop**, không phải tốc độ khung hình DWM.

C04 dùng thuật ngữ:
- `preview update cadence`
- không gọi nó là `DWM FPS`.

Exact compositor FPS của Windows/DWM không được binary TLM đặt trực tiếp và không thể suy ra từ các timer này.

## 2. Preview update loop là Tk `after` loop

Class state có:
- `_preview_loop_id`
- `_preview_reposition_after_id`
- `_refresh_active`

Class initialization chứa:
- `after`
- `_update_window_previews_loop`

Original doc của scheduler:

`Hẹn cycle preview tiếp theo (tôn trọng _refresh_active).`

Method:
- `_schedule_preview_loop`

Kết luận VERIFIED:
- normal Start preview maintenance được schedule bằng Tk timer;
- timer id được giữ ở `_preview_loop_id`;
- loop tiếp tục chỉ khi `_refresh_active` cho phép.

Khi rời Start:
- original doc: `Dừng poll nền khi rời tab Start — detached preview giữ nguyên.`
- state có cả `_preview_loop_id` và `_preview_reposition_after_id`;
- class có `after_cancel`.

Vì vậy Start-tab scheduled preview work bị cancel/stop khi tab không active, trong khi detached preview có lifecycle riêng.

## 3. Adaptive delay: 800 ms / 2000 ms

Original exact doc:

`Delay loop preview theo số acc: ít acc mượt 800ms, đông acc 2000ms.`

Readable serialized constants ngay cùng method block:
- integer **6**
- integer **800**
- shared integer **2000**
- state `_preview_proc_count`
- method `_preview_delay`

Do đó VERIFIED:
- preview maintenance delay thay đổi theo số account/process;
- short delay = **800 ms**;
- long delay = **2000 ms**;
- method có threshold constant **6**.

### Explicit unknown

- `count < 6`
- hay `count <= 6`

C04 không tự chọn một công thức.

Tuy nhiên số **6** chính xác là threshold/switch constant thuộc block `_preview_delay`.

## 4. Update loop làm gì mỗi cycle

Original exact doc:

`Vòng lặp cập nhật preview: reposition + làm mới danh sách nếu cần + refresh HP.`

Static locals/symbols trong block:
- `cache_ts`
- float **3.0**
- `alive_hwnds`
- `valid_items`
- `_refresh_preview_labels`
- `need_refresh`
- `_slot_vars`
- `cur`
- `_slot_hwnd_last`
- `_update_slot_comboboxes`
- `_schedule_preview_loop`

Verified functional responsibilities per cycle:

1. **Reposition**
   - keep DWM destination overlays aligned with Tk preview frames.

2. **Check current cached windows vs current preview items**
   - `alive_hwnds`
   - `valid_items`
   - `need_refresh`
   - rebuild only when needed, not blindly every cycle.

3. **Refresh labels/HP**
   - `_refresh_preview_labels`
   - loop doc explicitly says refresh HP.

4. **Update slot combobox bindings if HWND selection changed**
   - `_slot_vars`
   - `_slot_hwnd_last`
   - `_update_slot_comboboxes`

5. **Schedule next preview cycle**
   - `_schedule_preview_loop`

### 3.0-second cache constant
A serialized float **3.0** is embedded immediately after `cache_ts` in the update-loop constant block.

This proves the update loop applies a **3.0-second cache-time criterion**.

### Explicit unknown
The readable constant table does not expose the exact source comparison expression, so C04 does not falsely claim whether it is:
- age > 3.0;
- age >= 3.0;
- or another exact Boolean use.

It is recorded as a cache freshness/rebuild criterion, separate from DWM rendering cadence.

## 5. Metadata comes from background worker, not from DWM frame polling

Worker doc from original:

`Background thread: enum windows + đọc character info mỗi ~3s.`

Also:

`Đọc memory mỗi ~8s (giảm EnumModulesEx load lên game process).`

And:

`Không gọi bất kỳ API Tk nào — chỉ ghi cache.`

Therefore there are separate clocks:

### Background producer
- EnumWindows + character info/cache: approximately **3 s**
- heavier memory read: approximately **8 s**

### Tk preview consumer
- update loop: **800 / 2000 ms** adaptive
- consumes cached data;
- does not itself perform full heavy memory discovery every 800 ms.

This separation is one of the reasons UI stays responsive.

## 6. Name / HP label refresh

Original preview item initial header contains:
- `RoleName`
- `HpPercent`
- text format fragment ` | HP: `

Original helper doc:

`Cập nhật tên nhân vật từ cache worker thread.`

Update-loop doc explicitly says:

`... + refresh HP.`

Therefore normal preview metadata refresh includes at least:
- character name;
- HP percentage.

Name/HP values come from the worker info cache, not by reading DWM pixels.

## 7. List rebuild is conditional

The update loop has:
- `alive_hwnds`
- `valid_items`
- `need_refresh`

and original doc says:

`làm mới danh sách nếu cần`

Therefore:
- preview list is not destroyed/rebuilt every maintenance cycle;
- it compares current alive/cached source HWNDs with currently valid preview items;
- rebuild occurs only when the loop decides `need_refresh`.

This preserves DWM thumbnail objects and reduces churn.

### Exact Boolean formula
The exact source-level expression that sets `need_refresh` is not readable from constants alone, so C04 records the condition structurally rather than inventing exact `set != set` source syntax.

## 8. Reposition debounce = 60 ms

Original doc:

`Schedule reposition after resize (debounced).`

Serialized integer directly in that method block:
- **60**

Therefore:
- Configure/resize events do not immediately execute full reposition on every event;
- TLM debounces DWM destination-window reposition by **60 ms**.

Then:
- `_reposition_window_previews`
- reads current preview widget geometry;
- moves the DWM destination overlay accordingly.

This 60 ms timer is a layout debounce, not preview FPS.

## 9. 2-second Start list poll is another independent timer

From C01:

`Tự động cập nhật danh sách cửa sổ mỗi 2 giây (dừng khi rời tab).`

Serialized integer:
- **2000**

This is the high-level Start refresh/list poll.

Therefore Start has at least these distinct timing layers:

| Layer | Cadence |
|---|---:|
| Start UI list poll | 2000 ms |
| Preview maintenance | 800 / 2000 ms adaptive |
| Reposition debounce | 60 ms |
| Background EnumWindows/info producer | ~3 s |
| Heavy memory refresh | ~8 s |
| DWM image composition | live compositor; not set by these timers |

## 10. Detached preview update loop is independent

Original exact doc:

`Loop kiểm tra cửa sổ tách rời: rebuild nếu danh sách game thay đổi.`
`Độc lập với tab Start hiển thị hay không.`

Method:
- `_detached_update_loop`

Static local:
- `tracked`
- genexpr over tracked/current windows

Verified behavior:
- detached preview maintains its own window-tracking loop;
- it checks whether game-window list changed;
- if changed, it rebuilds detached preview items;
- it continues independently of whether Start tab is currently shown.

Manual detached refresh also exists:
- `_refresh_detached_preview`
- doc: `Đóng rồi mở lại preview — tải lại danh sách cửa sổ mới.`

So:
- normal embedded preview loop obeys `_refresh_active`;
- detached loop does not depend on Start tab visibility.

### Explicit unknown
The exact timer cadence of `_detached_update_loop` is not proven by readable constants in this task.

C04 therefore does not copy 800/2000 ms onto detached mode without evidence.

## 11. What "FPS" means for reconstruction

For a faithful rebuild:

### Must reproduce
- DWM Thumbnail live preview architecture;
- adaptive maintenance scheduling;
- 60 ms reposition debounce;
- conditional list rebuild;
- cached metadata refresh;
- detached loop independence.

### Must NOT implement as a fake equivalent
Do not replace DWM with:
- screenshot every 800 ms;
- BitBlt every 2 s;
- static preview bitmap;
- Tk image polling loop.

That would reproduce neither original runtime behavior nor responsiveness.

## 12. C04 timing model

```text
Windows DWM compositor
└─ continuously/live composes source HWND thumbnail
   (TLM does not set this FPS with 800/2000 timers)

background worker
├─ EnumWindows + cached character info ~3s
└─ heavier memory work ~8s

Start UI
├─ window-list poll 2000ms
└─ preview maintenance
   ├─ account-count switch constant: 6
   ├─ low-count delay: 800ms
   ├─ high-count delay: 2000ms
   ├─ reposition
   ├─ conditional list rebuild
   ├─ refresh cached name/HP
   ├─ refresh slot combobox mapping
   └─ reschedule while _refresh_active

Tk <Configure>
└─ 60ms debounce
   └─ reposition DWM destination HWNDs

Detached preview
└─ independent _detached_update_loop
   └─ rebuild when game-window list changes
      (continues even when Start tab hidden)
```
