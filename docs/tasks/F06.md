## 1. Selected account record
The original selected-row parser returns [(row_index, tk, mk, captcha_mode, proxy), ...] for checked rows only.

Static fields immediately before that documentation are entry_user, strip, entry_pass, captcha_var and proxy.

Missing username/password is rejected with: ⚠️ Dòng thiếu tài khoản hoặc mật khẩu.

F03 remains authoritative that mk is the real credential string, not the visual star mask.

## 2. Single-row Login button flow
A row Login action changes the row button to a busy state: disabled, orange #ef6c00, text beginning ▶ Đang login dòng ... — ẩn captcha: ... .

It starts _single_login_worker.

Exact documentation says:
- Login riêng 1 dòng account (nút ▶ xanh).
- Worker login 1 acc — launch + login, có retry, cập nhật UI qua after.

Therefore row login is asynchronous and UI changes return through Tk rather than blocking the main thread.

## 3. Launch result handoff
The single-account worker contains MAX_LOGIN_RETRIES, cancellation is_set, _launch_one_window, profile_idx, port, iid, use_proxy, hwnd, _login_click_worker, tk_val and mk_val.

The worker therefore repeats launch/login under the feature retry policy until success, cancellation, or retry exhaustion.

The exact numeric value of MAX_LOGIN_RETRIES is not recoverable from readable static evidence and remains UNKNOWN.

## 4. Background mouse input
The Login sequence uses shared mouse.click_at.

The original mouse helper documentation says click_at:
- performs a background click;
- uses the DLL-backed sync protocol;
- accepts window-relative coordinates and direct window_hwnd targeting;
- does not move the physical cursor.

The click flow is activation/block protocol → PostMessage click → restore.

Therefore Login does not move the user's physical mouse onto each game window.

## 5. Background keyboard input
Username/password text uses shared keyboard.press_at.

Exact keyboard documentation says press_at is the recommended path, sends printable characters with WM_CHAR through Unity activation, uses WM_KEYDOWN/WM_KEYUP for special keys, and does not depend on the DLL for the character-send path.

Thus account text is sent to the target window without requiring the user to physically focus/type into it.

## 6. Pre-login readiness via PrintWindow
The original _login_click_monitor documentation says:
Kiểm tra pixel login1/login2 trước (printwindow backend, đọc được cửa sổ bị che).

The pixel helper says check_multipixel captures the full target window once with PrintWindow and returns True only if all requested pixels match.

Login waits for both login.login1 and login.login2.

Exact failure text: ⚠️ Timeout chờ màn hình login sau 100s, bỏ qua cửa sổ.

Therefore login-form readiness timeout is exactly 100 seconds.

## 7. Update popup handling
Before credential entry the same function block contains check_pixel, printwindow, section/key login.update, and log:
[LOGIN] ⚠️ Phát hiện update popup, click để đóng...

The following click_at coordinate tuple decodes to exactly (630, 457).

Thus an update popup is detected from a background PrintWindow capture and closed by a background window-relative click.

## 8. Exact credential-entry coordinates
The original function documentation gives:
1. click username at (613, 302)
2. enter tk
3. click password at (573, 362)
4. enter mk
5. click Login at (684, 506)

The adjacent serialized tuples independently decode to those same coordinates.

Each step has window-close/cancel guards, including messages for window closed before Step 1, Step 2, Step 3, Step 4 and Step 5.

## 9. Wait for and click Vào trò chơi
After the Login click the function repeatedly checks login.vaoTroChoi.

The function block contains:
- failure text Không tìm thấy nút 'Vào trò chơi' sau ... lần thử;
- an encoded loop-bound integer 150 directly beside that retry/failure block;
- a coordinate tuple decoding to (684, 450);
- Step-7 close/cancel guards.

This is strong static evidence for a 150-check ceiling while waiting for Vào trò chơi, followed by a click at (684,450) when available.

The exact sleep/delay between checks remains UNKNOWN.

## 10. Step 8 in-game readiness
After the Vào trò chơi action the function calls await_pixel on common.active and passes window_hwnd, timeout, capture_backend, debug and cancel_flag.

The adjacent timeout integer decodes to 30.

Exact failure text is: [LOGIN] ⚠️ Timeout đợi vào game (common.active).

Therefore Step 8 waits up to 30 seconds for common.active.

## 11. Successful login
Exact success text: [LOGIN] ✓ Hoàn tất login cho cửa sổ ...

The single-account worker then calls _mark_row_online and _record_login_time.

Arguments around _mark_row_online include row_idx, hwnd, pid, user, use_proxy, iid, exe_path, profile_idx, port and proxy.

F02 exact documentation for _mark_row_online says it remembers the successfully logged-in window for that row, paints the row green, saves runtime online state, and preserves row-specific proxy state for later monitor/reload behavior.

## 12. Failure/retry cleanup
The single-account worker contains MAX_LOGIN_RETRIES and _force_close_window.

Thus a failed attempt is cleaned up before the next retry rather than leaving the failed game HWND alive.

F06 records only the mechanical rule: failed attempt → close failed game window → prepare next allowed retry state → relaunch/re-login.

Exact global retry-count value and per-retry delay remain UNKNOWN.

## 13. Multi-account concurrency
The original _login_launch_and_process documentation says exactly:
Login nhiều acc: LAUNCH TUẦN TỰ + LOGIN SONG SONG.

For each account:
1. prepare network/forwarder state;
2. launch the game sequentially under _launch_lock;
3. wait for the correct PID-owned HWND and stability;
4. run click/login on ready HWNDs in parallel.

The parallel login stage uses Semaphore and MAX_PARALLEL_LOGIN.

Therefore MAX_PARALLEL_LOGIN is a real concurrency cap. Its exact numeric value remains UNKNOWN.

## 14. Wait-all before final UI update
The login monitor contains exact documentation:
Chờ tất cả thread hoàn tất rồi cập nhật UI.

It also contains result aggregation, total/success state and _login_reset_ui.

Thus overall Login UI is finalized only after the account-login worker set settles.

Post-login routing remains F10.

## 15. Reset and online-row behavior
_login_reset_ui exact documentation says: Reset UI về trạng thái ban đầu sau khi dừng hoặc lỗi.

Recovered defaults include main text Bắt đầu, green #388e3c, row text Login and RoyalBlue row action styling.

For a tracked-online row, the row action can force-close the tracked game window, unmark the row and restore original appearance rather than starting a second login.

## 16. Cancellation checks
The click monitor has abort messages for:
- window gone while waiting for login form;
- window gone before Steps 1-5;
- cancel/window gone while waiting for Vào trò chơi;
- cancel/window gone in Step 7;
- cancel/window gone before Step 8;
- cancel/window gone after in-game readiness.

Step 8 passes cancel_flag to await_pixel.

This is cooperative cancellation, not a blind fixed sequence.

## 17. F07/F08 boundaries
F06 consumes captcha_mode and row proxy state but does not define their internal policy.

Captcha mode implementation remains F07. Proxy allocation/rotation/pinning remains F08.
