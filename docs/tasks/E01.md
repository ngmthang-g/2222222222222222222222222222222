## 5. Tk root + splash boundary

Main shell constants recover:
- `Tk`
- `TLMMainApp`
- `show_splash`
- `close_splash`
- `mainloop`.

The `splash` module explicitly documents:
- splash is a `Toplevel` over the root;
- root is withdrawn while splash is shown;
- returned `close_splash()` destroys the splash and deiconifies the root.

This establishes the lifecycle:

```text
Tk root exists
→ main app/root setup occurs
→ splash Toplevel participates while root is hidden
→ close_splash destroys splash + deiconifies root
→ Tk mainloop owns the long-running UI
```

The exact instruction-level ordering between `TLMMainApp(root)`, `show_splash(root)`, root withdrawal, and the final deiconify is not directly source-visible from Nuitka constants; E01 records the verified contract and leaves that precise call order explicit UNKNOWN.

## 8. Info tab is a startup service, not only a passive page

`TLMInfoTab.__init__` recovers:
- `create_widgets`

The startup API path:
- collects device/session/running-process information;
- calls the server API;
- validates/decode server response/token;
- updates version/license/plan/permission state;
- starts heartbeat.

Therefore shell startup includes a server/permission lifecycle through Info, not merely local tab construction.

## 9. Plan/permission callbacks can change tabs after startup

`TLMMainApp` exposes:
- `_on_plan_update`
- `_rebuild_tab`
- `_apply_permission_state`
- `_refresh_limit_state`
- per-tab visibility setters
- `_ensure_selected_visible`
- `_toggle_children_state`.

The app can:
- hide/show permission-gated tabs;
- disable/enable child widgets without destroying them;
- rebuild selected tabs when plan data changes;
- force selection back to Info when version/plan state blocks normal tabs.

This makes plan/license state part of the application lifecycle, not a one-time startup check.

## 10. Tab refresh lifecycle

The shell includes:
- `_on_tab_changed`
- `_selected_tab_key`
- `_sync_tab_refresh`
- `_set_tab_refresh`
- `_sync_initial_refresh`.

Exact docs say inactive tab refresh loops are stopped and the newly selected tab is refreshed/started when supported.

This is an important lifecycle boundary: feature tabs do not all need to poll at full rate continuously while hidden.

## 11. Background workers

Shell-level/startup-associated background activity includes:
- CPU monitor worker;
- Info server startup call / heartbeat;
- per-tab refresh loops as tabs become active;
- additional feature workers owned by each tab.

The main shell uses Tk `root.after` to marshal notifier/UI updates from worker threads back to the Tk main thread.

E01 does not collapse those workers into one global worker pool because the original uses module-owned lifecycles.

## 12. Normal destruction path

No explicit main-shell `WM_DELETE_WINDOW` protocol handler was recovered from the main module block.

Instead, many tabs bind `<Destroy>` or have destroy/save/stop handlers, including:
- Info heartbeat cleanup;
- Party/Phó Bản stop/destroy handlers;
- Train LSV save-on-destroy;
- Tối ưu save-on-destroy;
- other tab-specific cleanup.

Therefore the verified normal cleanup model is:
`Tk widget/root destruction → per-tab <Destroy>/cleanup hooks`.

Exact ordering of all tab cleanup hooks during a normal user window close remains explicit UNKNOWN.

## 13. Heartbeat-enforced forced quit

`TLMInfoTab` has:
- `_check_over_limit_autoclose`
- `_force_quit_app`
- exact documentation that a second consecutive blocking heartbeat state waits about 5 seconds and then destroys the app;
- explicit `os._exit` use because non-daemon threads such as pynput/farm workers may otherwise keep the interpreter alive after `mainloop` exits.

The same documentation says the forwarder child process is intentionally left running in this forced-quit path.

This forced shutdown path is distinct from normal user close.

## 14. Helper process lifecycle separation

Main GUI lifecycle must not be conflated with:
- `forwarder.exe` proxy process;
- `update.exe` / `bootstrap.exe` replacement flow;
- Frida/AutoX emulator helpers;
- injected `resources.dat`.

Gate D proved these are separate process/protocol boundaries.

## 15. Reconstructed lifecycle model

```text
process entry
  ├─ optional --forwarder branch
  └─ normal GUI branch
       ↓
diagnostic / thread-exception setup
       ↓
single-instance mutex
       ↓
Tk root + TLMMainApp shell
       ↓
Notebook + potential tab frames
       ↓
Info startup server/plan/license state
       ↓
permission/visibility application
       ↓
CPU monitor + selected-tab refresh lifecycle
       ↓
splash closes / root visible
       ↓
Tk mainloop
       ↓
normal root/widget Destroy hooks
          OR
       heartbeat forced destroy + os._exit
```

The exact micro-order of splash/root/app construction is the only material startup sequencing detail left unresolved by readable static evidence.
