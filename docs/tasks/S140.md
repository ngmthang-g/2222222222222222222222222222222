## Found concrete cause
Prior `tools/S134_WINDOWS_ROLE_CHAIN_FIXTURE_SMOKE.py` native positive test created five independent `ctypes.create_string_buffer` heap allocations. It assumed a separate `role` buffer plus terminal field displacement `role_addr+0x88` could *never* land inside any other allocated test-owned `n1/n2/session` range. That is **not guaranteed** by Windows' heap/ctypes allocator. If an unrelated buffer happened to occupy that address, `SelfOwnedWin32QwordReader.read_u64(role_addr+0x88)` correctly returned an actual QWORD rather than `POINTER_OUTSIDE_TEST_OWNED_RANGES`, falsely failing the negative test **even though** `validate_test_owned_role_chain` had only performed four correct address reads.

This is a TEST-ASSERTION bug, not evidence of real game memory mismatch; we did not change the S134 source algorithm or weaker authentication rules.
