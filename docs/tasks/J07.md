## 1. Run-state ownership has both tab-global and group-local layers

The frozen constructor owns:
- `_running`
- global `_cancel = threading.Event(...)`
- `_run_lock`
- `_active_runs`
- `_run_jobs`.

Each schedule group additionally owns:
- `_run_cancel`.

The exact helper contract is:

`_group_is_running(gd)`:
> true only when the group's run cancel exists and has not been set.

`_any_group_running()`:
> true while any group is in that running state.

Thus:
- global state controls the tab-wide run lifecycle;
- each group has an independent cancellation identity;
- a group can stop without stopping other groups.

The external `stop()` method has exact documentation saying it stops the whole process by applying **global cancel + every group cancel**.

## 2. Start/stop command routing is exact

Exact `_toggle_run` documentation:

- bottom button `gd=None`:
  - if any group is running → stop **all** groups;
  - otherwise → start all runnable groups in parallel.
- button inside a group:

## 4. Stop requests are cooperative, not thread killing

The state model uses Events and barriers; no asynchronous Python thread termination surface was recovered.

A group stop sets that group's cancellation state and the group transitions to the stopping/winding-down UI state while its worker unwinds.

The global stop path is documented as:

`Dừng hết mọi nhóm đang chạy`

and `stop()` states:

`Dừng quy trình nếu đang chạy ... dừng hết mọi nhóm (cancel tổng + cancel từng nhóm).`

Therefore stop means:
- signal cancellation;
- break synchronization safely where required;
- let workers unwind into normal teardown.

Do not reconstruct this as `TerminateThread`, forced exception injection, or abrupt Python thread destruction.

## 5. `_abort_cycle` is group-scoped and idempotent

The exact frozen documentation is:

> Acc nào fail → dừng chu trình của NHÓM ĐÓ ngay, không chạy tiếp:
> bể barrier để các thread đang kẹt ở điểm hẹn cùng thoát + dựng cờ
> cancel của nhóm để worker nhóm không sang bước kế. Idempotent.

Thus `_abort_cycle(barrier, cancel)` has two semantic effects:
1. abort/break the current row barrier so peers do not remain stuck;
2. set the current **group** cancel Event so no account worker advances to the next schedule step.

It does **not** document cancelling unrelated groups.

This is the central hard-failure propagation primitive.

## 6. `_barrier_wait` has no normal timeout

Exact contract:

> Chờ barrier KHÔNG timeout — chờ bằng được đủ quân mới đi tiếp.
> Barrier bị abort (có acc fail / bấm Dừng) → trả False để thoát.

Therefore:
- normal synchronization waits for the complete participating set;
- there is no ordinary barrier deadline;
- failure/user-stop releases blocked peers by aborting the barrier;
- callers treat `False` as stop/abort, not success.

This is why J04/J06 can reuse one row Barrier safely across accounts and repetitions without leaving healthy peers permanently waiting after one account hard-fails.

The exact low-level exception class/catch expression is not preserved in printable constants, so J07 freezes the semantic contract rather than inventing source such as a specific `BrokenBarrierError` handler statement.

## 8. Config failure path

`_config_dungeon_memory`:
- retries up to 5 times;
- retries are 2 seconds apart;
- returns True only after verified write success;
- returns False early if group/global cancellation is observed;
- after five failed writes it concludes hard FAIL.

The `_do_dungeon` frozen block places `_abort_cycle` immediately in the config-stage failure path.

Therefore exhausted config failure is a hard **current-group abort**, after its internal retries are consumed.

## 16. One group finishing does not tear down other running groups

The exact `_finish_group_run` documentation says:

> Dọn 1 nhóm vừa xong; nhóm cuối cùng xong thì teardown toàn cục
> (reset cờ/nút/pickup — logic finally cũ, chỉ chạy 1 lần).

The function local model includes:

`self, gd, job, cancel, still, th`.

`[Phó bản] Hết nhóm chạy — teardown toàn cục`.

Thus a hard failure in Group A does not automatically stop Group B/C.

## 17. Teardown is identity-safe against rapid restart

This is one of the strongest J07 recovery findings.

Exact `_finish_group_run` documentation:

> Chỉ gỡ cancel/job của ĐÚNG phiên này (so identity): user start lại
> ngay trong lúc worker cũ winding-down thì phiên mới không bị dọn
> nhầm → không mất điều khiển nhóm, không teardown sớm kéo nhóm khác.

Therefore cleanup does **identity comparison**, not only “same group number”.

An old worker finishing late must not:
- clear the new run's cancel object;
- clear the new job/thread ownership;
- make the new run look idle;
- trigger global teardown while another/new session is active.

No numeric generation counter is recovered for group runs. J07 therefore calls this an **identity guard**, not a generation guard.

## 18. Recovery model is retry-in-stage + manual restart, not automatic whole-group restart

Recovered automatic retries are local:
- config writes: 5 attempts × 2s;
- movement: initial + up to two retries;
- FuBen start: 5 fast attempts × 0.3s;
- map-cycle watcher: compiled 480s branch.

After a hard stage failure:
- current group aborts;
- barrier peers are released;
- teardown returns the group to an idle/startable lifecycle;
- other groups continue.

No static evidence of automatic whole-group schedule restart after a hard abort is recovered.

A later manual/new start is the recovery path, with:
- progress reset at start;
- new cancel/job identity;
- old winding-down cleanup prevented from deleting the new session.
