## 1. Party has no mouse-listener synchronization surface

Static scan of the frozen Party implementation range found zero Party occurrences of:
- `mouse.Listener`
- `_on_master_click`
- `_on_master_scroll`
- `_on_master_move`
- `_sync_worker`
- `_do_down`
- `_do_up`
- `_slave_client`
- `send_scroll`
- `send_move_slave`
- `WindowFromPoint`
- `GetAncestor`
- `ScreenToClient`
- `GetClientRect`
- mouse button broadcast-message paths.

Therefore PartyTab does not own master-mouse capture, relative-coordinate scaling, click-down/up queueing, scroll replication or move replication.

## 2. Party does not call Start input-sync state/toggle

The Party range also contains no:
- `_toggle_input`
- `input_active`
- `_sync_keepalive`
- `_sync_locked`
- Start mouse-sync target/slave APIs.

G02/G05 established the direct Start dependency as `start_tab.get_windows()` for member discovery.

G07 found no Party call edge that takes a Party leader/group HWND list and feeds it into Start mouse-sync source/target selection.

## 3. C19 remains the authoritative mouse-sync owner

C19's already-verified Start input-sync contract remains unchanged:

selected Start master HWND
→ `mouse.Listener`
→ `_on_master_click` / `_on_master_scroll` / `_on_master_move`
→ master screen/client coordinate resolution
→ size-aware master→slave coordinate scaling
→ ordered click worker
→ Start-managed slave HWND targets.

The Start subsystem also owns:
- left/right/middle support;
- scroll replication;
- throttled move replication;
- slave block/unblock;
- 1.5-second sync keepalive;
- stale-lock watchdog.

Party does not duplicate or override those behaviors.

## 4. Party does contain direct targeted mouse-action helpers

The negative synchronization result does **not** mean Party never clicks the game.

Direct frozen Party evidence includes:
- `check_pixel` around `0x2b7f0bf` / `0x2b7f0cc`;
- `click_at` around `0x2b7f0db` / `0x2b7f0e5`;
- `resize_window` around `0x2b7f0f1` / `0x2b7f100`;
- target field `window_hwnd`;
- create-team UI fallback documentation.

The create-team fallback checks specific pixels and sends specific clicks to the intended leader/create-team window, including:
- `nguoiChoiGan` → click `(391, 683)`;
- `muiTenAnNhiemVu` → click `(34, 462)`;
- later fixed click sequence documented in the original method.

This is **targeted Party automation against one intended HWND**, not synchronized replay from a master window to slaves.

The full create-team action sequence remains for the later action-button task.

## 5. The `mouse` symbol in Party is not evidence of mouse synchronization

Party contains the symbol `mouse` around `0x2b7daa3`.

Its directly adjacent recovered calls are:
- `bind_window_identity`
- `unbind_window_identity`.

G02 already proved these functions implement HWND→PID-generation safety.

Therefore the presence of the module/symbol `mouse` in Party does not imply `mouse.Listener` or master/slave synchronization.

This distinction is critical for reconstruction.

## 6. Party leader is not Start mouse-sync master

G04/G06 established that Party leader and Start master are separate concepts.

G07 found no mouse-side evidence that:
- selecting a Party leader sets Start master;
- changing Party leader restarts a mouse listener;
- Party group members replace Start slave targets.

Party group membership must not control Start mouse synchronization.

## 7. Party's fixed-coordinate click fallback has no C19 scaling stage

The Party create-team block directly carries fixed game coordinates after normalizing the leader window to 1366×768.

No Party references to C19's:
- `ScreenToClient`;
- `GetClientRect`;
- master/slave scaling;
- `_slave_client`

were recovered.

Therefore the Party fallback and Start synchronized mouse are deliberately different models:

Party:
`known target HWND + normalized 1366×768 + fixed UI coordinates`

Start sync:
`master event + current master/slave client sizes + relative coordinate scaling`.

Do not merge them.

## 8. No Party mouse move/scroll broadcast

No Party `send_scroll`, `send_move_slave`, master-scroll handler or master-move handler exists in the frozen Party implementation.

Thus Party does not broadcast cursor motion or wheel events to its group members.

## 9. B04 cross-check after static extraction

B04 contains Party group/action controls and no mouse-sync control.

This matches the EXE-first audit.

No Party mouse-sync button, target list or geometry is added to the B04 reconstruction contract.

## 10. G07 reconstruction contract

Later reconstruction must:
1. keep synchronized mouse ownership in Start/window input subsystem;
2. not add `mouse.Listener`, master click/move/scroll handlers or a sync queue to PartyTab;
3. not call Start `_toggle_input` from Party start/stop/leader changes;
4. not use Party leader as Start mouse-sync master;
5. not use Party group members as Start mouse-sync slaves;
6. preserve Party's direct targeted `check_pixel` / `click_at` action path separately;
7. preserve G04's 1366×768 leader normalization for the fixed-coordinate create-team fallback;
8. not add C19 coordinate scaling to Party's fixed-coordinate fallback;
9. leave full click/action sequencing to the later Party action-button task.
