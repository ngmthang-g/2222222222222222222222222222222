## 3. Exact add-row signature/default model

The serialized default tuple immediately before `PhoBanTab._add_schedule_row` decodes as:

`(True, None, None, 1, None)`

and the function-local argument sequence begins:

`self, enabled, activity, name, times, rows, ...`

This locks the reconstructed signature model to:

`_add_schedule_row(self, enabled=True, activity=None, name=None, times=1, rows=None)`

The exact doc states that `rows=None` means the last group is used by default.

Therefore:
- new rows are enabled by default;
- `times` defaults to 1;
- activity/name are resolved dynamically when omitted;
- the destination rows list may explicitly target one group.

## 6. Progress/status model

The exact canonical progress-style table is:

- `chưa` → label `Chưa`, color `#808080`
- `đang` → label `Đang`, color `#b8860b`
- `xong` → label `Xong`, color `#1b5e20`.

`set_progress` accepts either:
- a row dict; or
- any widget belonging to the row, resolved through `_row_by_frame`.

Status matching is case-insensitive for `chưa | đang | xong`.

`reset_all_progress` sets every row to `Chưa`.
`_reset_group_progress(gd)` resets only rows of one group.
`_set_row_progress` is the background-thread-safe bridge that schedules the UI update back onto the main thread.

Static nuance: row creation itself contains an initial `Chưa` label with foreground `#555555`, while the canonical `chưa` progress style is `#808080`. Do not collapse these two facts until runtime/UI reconstruction shows whether a normalization call happens immediately after creation.

## 7. Schedule collection and ordering

The exact helper contracts are:

### `get_schedule_rows()`
Legacy compatibility surface:
- flattens schedule rows across all groups;
- fields: `enabled/activity/name/times`.

### `get_groups_data()`
Modern full config surface:
- returns groups in UI order;
- exact documented shape:

`[{'num': n, 'members': [...], 'schedule': [...]}, ...]`

where each schedule item stores the four business fields above.

### `get_selected_schedule()`
Execution surface:
- returns only checked rows;
- exact documented shape:

`[{activity, name, times, row}]`

The live `row` object is deliberately included so progress can be updated during execution.

### Ordering
`_all_schedule_rows` documents that rows are combined “theo thứ tự”.
`get_selected_schedule` iterates the existing row list rather than sorting by name/activity.

Therefore the original contract is:
- group order = current group/UI order;
- row order inside a group = current row/UI order;
- enabled rows preserve that order when converted to execution schedule.

Malformed-JSON exception microbehavior is not instruction-bound by the string/constant blob and remains an explicit implementation-time compatibility check, not something to guess here.

## 10. Exact row execution ordering

`_toggle_run` has two distinct modes:
- bottom tab button: start/stop all groups;
- group button: start/stop only that group.

The exact documentation states that all groups are independent and each running group gets its own thread. Other groups keep running when one group is stopped.

Inside one `_run_one_group`:

1. if `Tạo lại đội` is enabled, J01's party-recreation pipeline runs first;
2. target-account setup runs in parallel and those setup threads are joined;
3. only then does schedule execution begin;
4. each schedule row is processed in row order;
5. the row is set to `đang`;
6. a per-step `Barrier` is created;
7. one `_acc_step_worker` thread is started per target for the same schedule item;
8. those worker threads are joined;
9. on the normal path the row is set to `xong`;
10. only then can the next row start.

This gives the core J04 ordering rule:

**groups run in parallel; rows within one group are sequential; accounts within one row run in parallel and share that row's synchronization object.**

Deep abort/cancel/failure transitions are J07 and are not redefined here.
