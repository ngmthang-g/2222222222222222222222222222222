## 4. The three controls are opt-in and only active while a schedule is running

Exact `_toggle_discard` documentation:

- at least one discard tick ON + at least one group already running → start the discard worker immediately;
- ticks ON but no schedule group running → persist the mode and wait; a later run start creates the worker;
- all three ticks OFF → stop the discard worker immediately;
- the worker re-evaluates the enabled ticks each cycle, so turning the final tick off mid-run makes it exit;
- config is saved.

The exact waiting log is:

`[Phó bản] Tick vứt đồ BẬT — chờ lịch trình chạy`.

Therefore these checkboxes are persisted modes, not a permanently-running bag cleanup service.

## 5. Worker lifecycle = stop Event + thread + generation

Constructor state:
- `_discard_stop`

- `_discard_gen`.

The worker documentation explicitly says:
- run start or a newly-enabled tick can build/rebuild the worker;
- `is_alive` prevents duplicate active worker creation;
- a generation value prevents two worker sessions from overlapping;
- the worker exits when all discard ticks are disabled;
- the worker also exits when no schedule group remains running.

This is the same lifecycle pattern seen in J03 follow.

## 7. Worker scope = accounts in currently-running groups only

Exact worker documentation says every poll:
- recompute current enabled preset keys;
- operate on **all accounts in groups that are currently running**;
- idle/configured groups are not processed;
- if no group remains running, the worker exits.

The worker has a nested `_members` helper plus current-running-group locals.

Normal UI group-selection uniqueness already prevents one account from being selected into multiple groups. J08 does not reopen J01 group-selection semantics.

## 8. Accounts run in parallel, presets run sequentially inside each account

> (trang bị -> vật phẩm -> thuốc, theo DISCARD_TICK_KEYS).

Thus the concurrency model is:

```text

within one account: preset 1 → preset 2 → preset 3 sequentially
```

Current preset order is exactly:
`discard_equip → discard_items → discard_meds`.

## 10. One-account execution uses one bag_filter preset at a time

`_discard_one_acc` exact documentation:

> Vứt 1 acc LẦN LƯỢT từng preset được tick ...

For every enabled preset key it calls:

`bag_filter.discard_for_activity`

with activity:

`phoban`.

The doc explicitly states:
- each enabled preset is invoked as its own `discard_for_activity` pass;
- order follows `DISCARD_TICK_KEYS`;
- item delay is **1 second per item**;
- it stops early when the supplied stop condition becomes true.

So the three enabled ticks are **not merged into one single bag_filter call** by PhoBanTab; PhoBanTab intentionally runs one preset at a time.

- the underlying discard path supports `stop_check()` and stops early;
- discard means abandoning the entire selected stack.

## 12. Stop/cancel propagation into an in-progress preset

`_discard_one_acc` receives a `stop` callable and passes it to `bag_filter.discard_for_activity` as `stop_check`.

The exact docs guarantee early stop between discard work when that stop condition becomes true.

The worker itself is explicitly invalidated by:

## 13. Normal group completion has a dedicated final discard pass

The exact `_run_one_group` constant/control sequence is:

```text
row normal completion -> "xong"
                     -> ": vứt lượt cuối ("
                     -> _fkeys
                     -> _ft
                     -> _t
                     -> ": xong vứt lượt cuối"
                     -> "vứt lượt cuối lỗi:"
                     -> "HOÀN THÀNH"
```

The `_run_one_group` local model independently contains:
- `_fkeys`
- `_ft`
- `_t`

after the ordinary row-thread locals.

Strongest static reconstruction contract:

1. after the selected schedule rows finish normally, read the **current** enabled discard preset keys;
2. if that final key set is non-empty, run one final discard batch for the finishing group's target accounts;
3. wait for that final batch;
4. log final-pass completion/error;
5. only then log the group's `HOÀN THÀNH`.

The separate `_ft/_t` locals strongly support a dedicated final account-thread batch rather than merely waiting for the periodic worker.

## 14. Unticking means no forced final cleanup later

Because the final pass reads the current discard key set:
- if the user has unticked all three controls, `_discard_enabled_keys()` is empty;
- `_toggle_discard` has already requested immediate worker stop;
- there is no evidence of a hidden forced “discard anyway” preset after untick.

Thus an unticked discard mode stays opt-out at schedule completion.

## 15. Run-end behavior

### Normal group completion
If one or more discard ticks are still enabled:
- the finishing group gets the final discard pass described above;
- then it reaches `HOÀN THÀNH`;
- J07 cleanup removes only that group;
- if other groups remain running, the periodic discard worker can continue for those groups.

### Last normal group completion
After its final pass and J07 teardown:
- no running group remains;
- the periodic worker's own “no running groups” rule makes it exit.

### User stop / hard abort
The final-pass constants are on the normal post-row path before `HOÀN THÀNH`, not documented as a `finally` cleanup pass.

There is **no static evidence of a mandatory final discard flush after a hard abort/user stop**. The strongest contract is therefore:
- normal completion final pass: yes, when keys still enabled;
- all ticks OFF: skip;
- hard-abort/stop forced final flush: **not recovered**.

A very late cancel arriving after row completion but around the final-pass boundary is a runtime race and remains explicit UNKNOWN.

## 16. Potential overlap is bounded but live race parity remains unverified

The periodic worker has its own per-account `inflight` guard.

The final normal-completion batch is a separate `_run_one_group` batch, not statically proven to share that same `inflight` collection.

Shared `bag_filter` itself owns:
- `_SEND_LOCKS_GUARD`
- `_SEND_LOCKS`
- per-HWND send-lock retrieval surface `_send_lock_for`.

This provides a lower-level serialization boundary around item sends, but J08 does not claim the precise scheduling order if a periodic pass and the final group pass meet at exactly the same instant.

That concurrency edge is left for Windows/runtime parity rather than being invented.
