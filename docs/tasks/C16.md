# C16 — Đóng hết game windows

## STATUS
**VERIFIED_WITH_EXPLICIT_POST_CLOSE_REFRESH_UNKNOWN**

C16 was recovered from the original TLMTool 2.1.2 EXE. This task distinguishes the real game-window close action from preview teardown/rebuild.

## 1. Preview button and callback
- visible text: `Đóng hết`
- callback: `_close_all_preview_windows`
- wrapper: `_close_all`
- shared utility: `close_all_game_windows`

Original docs state that this path closes all game windows and then cleans up lingering Unity crash-handler processes.

## 2. Main game windows are closed with WM_CLOSE
The reusable `utils.py` utility recovers:
- `get_game_windows`
- `IsWindow`
- `PostMessage`
- `win32con.WM_CLOSE`.

Verified model:
1. enumerate the current game HWND list;
2. validate each HWND;
3. post a normal window-close message to each valid game HWND.

No force-termination primitive for the main game executable is recovered in this shared close block.

## 3. Crash-handler cleanup is separate
After requesting the game windows to close, the same utility contains a separate forced-cleanup path for lingering `UnityCrashHandler64.exe` instances/process trees.

This distinction is important:
- game client → normal window-close request;
- leftover crash handler → cleanup process.

## 4. Ordering
`get_game_windows` is based on the current `EnumWindows` result. No RoleName/master-first sort is recovered in the close utility.

Therefore close order is treated as the current enumeration/list order and must not be reconstructed as master-first.

## 5. Preview/cache cleanup after close
C01/C04 already prove that closed HWNDs disappear from discovery and that preview maintenance conditionally rebuilds when the alive HWND set changes.

Therefore eventual preview/master cleanup after the game windows close is VERIFIED.

Readable constants around `_close_all_preview_windows` do not prove an immediate explicit call to `refresh_window_preview_list()` after clicking the button. Exact immediate refresh timing remains UNKNOWN.

## 6. Confirmation behavior
No dedicated close-all confirmation text or close-specific confirmation path is recovered in the callback/utility constants. Confirmation therefore remains `NOT_RECOVERED`, not invented.
