## 3. No Party preview-click activation path

## 5. Shared Start preview ownership remains authoritative

C03 already locked the embedded Start preview architecture:
- source game HWND stored as `src_hwnd`;
- dedicated transparent destination HWND;
- live DWM thumbnail registration/update/unregister lifecycle;
- click preview → activate the corresponding source game window.

C09 locked main preview 1x–5x column layout.

C14 locked detached DWM preview ownership/lifecycle.

G05 does not duplicate any of those systems in PartyTab.

## 6. Party member HWNDs and Start preview HWNDs can refer to the same game windows without shared ownership

G02 Party members are backed by live game HWNDs from `start_tab.get_windows()`.

C03 Start preview items are also backed by game HWNDs.

That does **not** mean Party owns a preview item for each Party member.

The same underlying game HWND may be consumed independently by:
- Start preview subsystem;
- Party member/identity subsystem.

Subsystem ownership remains separate.

## 7. No Party dependency on preview order

C09/C17 establish preview ordering as Start preview state.

The Party block contains no:
- `_preview_order`
- preview move-left/right callbacks;
- `preview_grid_var`;
- `_get_preview_columns`.

Party group order therefore must not be derived from Start preview order, and changing Start preview columns/order must not rewrite Party group membership/order.

## 8. No Party dependency on detached preview state

C14 owns:
- `detached_active`
- detached DWM items;
- detached column state;
- detached update/close/open lifecycle.

No matching Party reference is present.

Party refresh/action state must continue to work independently of whether Start embedded/detached preview is open, hidden or rearranged, subject only to the shared underlying game HWND actually existing.

## 9. B04 cross-check after static extraction

Only after EXE analysis, B04 was reconsidered.

B04 is a Party-tab screenshot and shows Party configuration/group UI. It does not establish a Party preview component.

Any black/live preview areas shown in other Start screenshots belong to the Start/window subsystem already documented by C03/C09/C14.

G05 therefore makes **no new Party preview geometry** and changes no B04 baseline pixels.

## 10. G05 reconstruction contract

Later reconstruction must:
1. not create a DWM preview subsystem inside PartyTab;
2. not copy Start's preview frames, destination HWNDs or DWM registration code into Party;
3. not add Party-owned preview refresh/reposition/detached loops;
4. not use Start preview order as Party group order;
5. keep Party member discovery on `start_tab.get_windows()` as already verified in G02;
6. allow Start preview and Party to reference the same underlying game HWND independently;
7. keep preview click/activation ownership in Start/window subsystem;
8. preserve Party direct action helpers separately from preview activation;
9. not add preview UI merely because PLAN requires a preview audit — the audit result is that Party does not own one.
