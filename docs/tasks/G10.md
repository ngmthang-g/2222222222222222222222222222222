## 1. One Party cluster is explicitly B0 → B1 → B2 → B3

Exact original `_run_one_group` documentation:

`Chay 1 cum (B0 -> B1 -> B2 -> B3), doc lap voi cum khac.`

It further defines:
- B0: write auto-accept + read it back for confirmation;
- B1: all online targets leave current team, skip already-outside targets, then wait for TeamID to become outside-team;
- B2: leader creates a team, verifies a real TeamID, retries/falls back as required;
- B3: burst all invitations, then perform one shared group TeamID wait instead of waiting a fixed 2 seconds per member.

This is the active team protocol. The G09 global/single orchestration both converge on this same `_run_one_group`.

## 2. Target resolution happens against live RoleID/HWND data

G03 remains authoritative:
- configured group members are names;
- `_resolve_targets` reads `memory_items.read_own_ids`;
- live own-account record shape is `(pid, RoleID, Name, Lv)`;
- `hwnd_of_pid` resolves the current game HWND;
- result shape is `(name, hwnd, rid)`;
- offline/missing-window names are logged and skipped.

The protocol therefore never trusts a persisted HWND/RoleID from config.

The `_run_one_group` block also contains an explicit runtime branch for `chỉ 1 acc online — ...` immediately before create/invite helpers. The existence of this insufficient-live-member guard is verified; the final assembled log suffix/source return expression is not fully recoverable from the readable constant table and is not invented.

## 3. B0 — enable AutoAcceptInviteTeam on every live target

The active Party section was built with:
- section/kind: `team`
- accept field: `AutoAcceptInviteTeam`.

Inside `_run_one_group`, direct constants include:
- `set_auto_fields`
- section `UTILITIES`
- type `bool`
- `_is_autoset_on`
- `AUTOSET_DELAY`.

The shared `memory_items.set_auto_fields` documentation states it writes live `AutoFightSettings` and calls `SaveSetting()`.

Thus B0 is:

`target HWND → set_auto_fields(UTILITIES / AutoAcceptInviteTeam / bool = True) → wait AUTOSET_DELAY → read back with get_auto_settings`.

Readback semantics are exact:
- `True` = setting confirmed ON;
- `False` = write was sent but game still reports OFF, commonly because the AutoFight panel/settings object has not materialized;
- `None` = setting could not be read.

Exact Party logs distinguish:
- `(xác nhận BẬT)`
- `(CẢNH BÁO chưa bật — nhận tay!)`
- `(không đọc lại được)`.

A write exception logs `ghi tự-đồng-ý lỗi: ...`.

Important: B0 confirmation failure is a warning/fallback-to-manual-accept boundary, not evidence that Party fabricates a positive setting.

## 4. TeamID state model reused unchanged

G03 is preserved exactly:
- `0` = outside/no team;
- `0xFFFFFFFF` = outside/no team;
- `None` = read failure / unknown;
- other accepted value = real TeamID.

`_wait_team_state` exact documentation:
- with `expect_zero=True`, wait until every target is outside team;
- after team creation, wait until a real team exists;
- `None` never counts as reached;
- success only if condition is met within timeout.

`_wait_same_team` additionally requires two HWNDs to have the same real TeamID after excluding 0 / 0xFFFFFFFF / None.

## 5. B1 — leave current team, then verify outside-team state

For each resolved target:
1. read current TeamID;
2. if already in `NO_TEAM_IDS`, skip the leave command;
3. otherwise call shared `memory_items.leave_team(hwnd)`;
4. use the interruptible Party sleep with `LEAVE_DELAY`;
5. after leave commands, call `_wait_team_state(... expect_zero=True ...)` with `WAIT_LEFT_TIMEOUT`.

The run-one-group log surface includes:
- already outside → `bỏ qua thoát`;
- `thoát lỗi: ...`;
- leave result;
- if the verification wait expires: `chưa xác nhận thoát hết ... — vẫn tiếp tục`.

Therefore B1 timeout does **not** hard-abort the cluster; it logs the diagnostic snapshot and continues.

This is a deliberate distinction from TeamID `None`: unreadable state does not count as successful outside-team confirmation, but timeout still permits the higher-level protocol to proceed.

## 7. B2 — packet-first leader team creation

`_invite_create` exact documentation says the leader creates the team **without inviting anyone yet**, leaving all member invites to B3.

For the active verified team path it first uses:

`GI.create_team`

from `memory_items`.

The shared memory_items documentation proves:
- packet channel: **200057**
- `C_TeamAction.CreateTeam = 0`
- create payload: **"0"**
- the helper is coordinate/window-size independent;
- helper return means command sent, while actual creation is verified by `read_team_id(hwnd)`.

Party then calls `_wait_team_state` with `CREATE_PACKET_TIMEOUT`.

If leader obtains a real TeamID, B2 succeeds immediately.

## 9. B2 retries are TeamID-verified

After a click fallback attempt, Party waits for a real leader TeamID with `WAIT_TEAM_TIMEOUT`.

If still not created:
- it logs `chưa thấy ... — thử lại (...)`;
- retry spacing uses symbolic `INVITE_DELAY`;
- it retries up to symbolic `CREATE_RETRY`.

If exhausted:

`TẠO THẤT BẠI — bỏ qua cụm này`

and the group protocol returns/does not proceed to normal B3.

The current readable EXE proves the symbolic retry/timeout names and the max-retry architecture but does not safely bind a source-level numeric literal to `CREATE_RETRY`; G10 leaves that numeric count explicit UNKNOWN.

The generic helper retains a `verify_team` branch for non-team/legacy use. Its documentation says a non-verifiable corps-style path may return True so the caller can continue to burst invites. The current active Party `team` path is TeamID-verified.

## 10. B3 — burst invite, not sequential 2-second waits

The main B3 path is `_invite_burst`.

Exact documentation:

`Gửi DỒN DẬP invite cho cả nhóm + chờ 1 lần duy nhất (NHANH).`

Instead of:
- invite one member;
- fixed 2-second wait;
- repeat for N members;

B3:
1. sends invitations to all `others` in a burst;
2. spaces sends by `BURST_INVITE_DELAY`;
3. calls one shared `_wait_group_same_team` wait up to `GROUP_JOIN_TIMEOUT`;
4. if some are missing, sends exactly **one more round** to the missing members;
5. performs one additional group wait;
6. returns True when finished even if some are still missing, unless canceled; remaining members are logged.

The documentation explicitly describes the old sequential strategy as `2s` per member and the burst spacing as approximately:

`BURST_INVITE_DELAY (~0.5s)`.

This is the strongest static timing statement for B3. G10 records **~0.5s documented**, not an invented exact binary assignment.

## 11. B3 invitation helper and packet channel

The Party summary explicitly states remaining accounts are invited with:

`invite kind='team'`.

The shared memory_items invite helper documentation states:
- `kind: trade/team/group -> packet 200051`.

Its frozen serialized mapping contains:
- keys `trade / team / group`;
- value prefixes `7:1: / 5: / 10:`;
- then a default/fallback `10:`.

The serialized 3-key map therefore binds team invitation to prefix:

`5:`

and the helper appends the target RoleID.

For the active Party team path, the low-level invitation is therefore:

**packet 200051, payload `5:<targetRoleID>`**.

This is separate from TeamAction channel 200057 used for create/leave.

## 12. Group join verification

`_wait_group_same_team` exact documentation:
- leader must have a real non-sentinel TeamID;
- poll every symbolic `GROUP_JOIN_POLL`;
- each other target is complete only when its TeamID equals the leader's real TeamID;
- timeout returns the list of missing `(name, hwnd, rid)`;
- cancellation returns `None`;
- empty missing list means the entire group joined.

This is a state-based verification step, not a popup/click assumption.

## 13. One resend only, then warn

After the first shared wait:
- if missing is empty: log `cả nhóm đã vào (TeamID=...)`;
- otherwise log `gửi lại <N> acc chưa vào: ...`;
- resend one invitation to each missing account;
- wait one more time.

After the second wait:
- empty missing list → `cả nhóm đã vào sau gửi lại`;
- still missing → log `còn thiếu ...` plus `_team_snapshot`, followed by `kiểm tra auto-accept/popup tay`.

The method documentation explicitly says B3 returns True after completion even when some members remain missing, with diagnostics, unless the operation was canceled.

So retry count for the burst stage is statically exact:

**initial invite round + one resend round**.

## 14. Legacy _invite_join is retained but is not the main B3 engine

A separate helper `_invite_join` remains.

Exact documentation:
- send one invite;
- wait fixed symbolic `JOIN_WAIT`;
- do not inspect TeamID;
- return False only if canceled;
- retained for compatibility / isolated retry.

The B3 documentation explicitly says the main path now uses faster `_invite_burst`.

The burst doc identifies the old fixed strategy as **2 seconds per account**, so 2s is verified as the documented legacy behavior. G10 does not claim the exact module assignment statement for `JOIN_WAIT` itself.

## 15. Direct Rời nhóm button protocol

The separate `_leave_group_worker` path is simpler than B1.

It:
1. imports `memory_items`;
2. resolves live targets;
3. skips targets already in the no-team state;
4. sends `leave_team` for members that are currently in a team;
5. logs OK/FAIL;
6. uses interruptible `LEAVE_DELAY` between actions;
7. logs `rời nhóm XONG`.

The readable leave-button block contains no final `_wait_team_state` call.

Therefore:
- **B1** = leave commands + all-target TeamID-outside verification;
- **Rời nhóm button** = background leave command sweep with skip/delay/logging, without the B1 aggregate confirmation wait.

Do not merge these two paths.
