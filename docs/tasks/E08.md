# E08 — Shutdown / reload / restart boundaries

## STATUS
**VERIFIED_WITH_EXPLICIT_NORMAL_DESTROY_ORDER_AND_START_RELOAD_MICRODETAIL_UNKNOWNS**

E08 separates five behaviors that must not be conflated during reconstruction:

1. normal Tk/widget destruction;
2. in-app tab/view rebuild or refresh;
3. Start-page `Reload` input/window recovery;
4. Login per-account reload/re-login;
5. full updater-driven TLMTool replacement/relaunch.

The original inner EXE is primary evidence. Gate A/D07 remain authoritative for external updater/helper behavior.

## 1. Normal application close is Tk destruction first

E01 found no main-shell `WM_DELETE_WINDOW` protocol handler in the TLMMainApp block.

Instead, many top-level tab objects bind `<Destroy>` to their own cleanup/save handler:

- Daily → `_save_on_destroy`
- Debug Android → `_on_destroy`
- Đồn → `_save_on_destroy`
- Farm → `_save_on_destroy`
- Info → `_on_frame_destroy`
- Login → `_save_on_destroy`
- Party → `_on_destroy`
- Phó Bản → `_on_destroy`
- Rao → `_save_on_destroy`
- Start → `_save_on_destroy`
- Tối ưu → `_save_on_destroy`
- Train LSV → `_save_on_destroy`.

Therefore the verified normal-close architecture is:

`root/widget destruction → child/tab Destroy events → tab-owned save/stop cleanup`.

The exact order Tk emits these child-destroy handlers during root teardown is not source-visible and remains explicit UNKNOWN.

## 2. Destroy handlers combine persistence and worker cleanup

E05/E07 already established that tab-owned destroy paths can:
- save configuration;
- cancel Tk `after` jobs;
- set cancellation/running state;
- stop heartbeat or feature workers;
- restore/close owned views/resources.

Info has a named `_on_frame_destroy` plus `stop_heartbeat`.

Reconstruction must keep cleanup ownership with the tab/service that owns the state rather than centralizing every cleanup into one monolithic shell function.

## 3. Normal close is not proven to kill every helper process

No shell-level normal-close routine was recovered that unconditionally kills all helper processes.

This matters because other paths are explicit:
- forced heartbeat shutdown explicitly leaves the independent forwarder running;
- updater path explicitly calls `stop_all_forwarder_processes`.

Therefore E08 does **not** invent a normal-close `kill all forwarders` policy.

Exact normal user-close behavior for every forwarder/helper process remains UNKNOWN unless its owning module has a direct destroy handler proving otherwise.

## 4. Forced heartbeat shutdown

InfoTab contains `_check_over_limit_autoclose` / `_force_quit_app`.

Exact recovered contract:
- first blocking/bad heartbeat condition records strike 1 and waits for the next confirmation;
- second blocking condition waits about **5 seconds**;
- then the app GUI is destroyed;
- `os._exit` is used to force process termination because non-daemon workers may otherwise keep the interpreter alive;
- the independent forwarder process is explicitly left running / not killed;
- returning to normal resets the strike state.

This is not equivalent to normal Tk close.

Because `os._exit` is used, reconstruction must not depend on ordinary interpreter finalizers/atexit cleanup completing in this forced path.

## 5. In-app tab rebuild is not a process reload

The shell exposes:
- `TLMMainApp._rebuild_tab`
- lazy one-time build guards from E03.

A rebuild replaces/reconstructs tab content inside the existing process/Notebook lifecycle.

It is used for permission/plan/UI lifecycle and must not be implemented as restarting `TLMTool.exe`.

## 6. Preview refresh is not a process reload

Gate C C15 established:
- `refresh_window_preview_list` tears down/rebuilds embedded DWM preview resources;
- `_refresh_detached_preview` closes then reopens the detached preview.

These are view-resource refreshes only.

No game process or TLMTool process restart should be attached to these buttons.

## 7. Start-page Reload is an unstick/recovery command

Start UI contains:
- `btn_reload`
- `_unstick_all_cmd`
- lower-level `_dll_unstick_windows`
- imported `unstick_windows`
- runtime prefix `[Reload]`.

The underlying mouse/input helper also exposes `unstick_window(s)` with documentation describing bulk recovery of tracked input-lock/window state.

Therefore the Start-page `Reload` command is classified as:
**in-process game-window/input-lock recovery**, not a TLMTool executable restart.

The exact source-level sequence of every DLL/window restore call inside `_unstick_all_cmd` is not fully readable from Nuitka constants and remains explicit UNKNOWN.

## 8. Login per-account Reload is a game/account re-login flow

LoginTab has:
- `_reload_account`
- `_reload_worker`
- per-row `btn_reload`.

Exact worker documentation gives this sequence:

1. advance that forwarder instance to the next proxy and update the current proxy;
2. if that account currently has a tracked game window, force-close that game window;
3. immediately log in again using the new proxy, without advancing proxy a second time.

UI completion/error callbacks are returned to the main thread and the reload button is restored to normal/RoyalBlue state.

This reload affects one account/game session. It does **not** restart the main TLMTool process.

## 9. Full update/restart path is explicit and separate

`TLMInfoTab.on_auto_update_click` / update block recovers:
- `update.exe`
- confirmation `askyesno`
- `_close_all_game_windows`
- `stop_all_forwarder_processes`
- `_get_update_link`
- `_find_updater_exe`
- `Popen`.

Verified pre-update sequence:

```text
user confirms update
→ close all tracked game windows
→ stop all forwarder processes
→ resolve update link
→ locate update.exe
→ spawn update.exe
```

Gate A/D07 then establish the external updater lifecycle:
- download update ZIP from Pixeldrain or Google Drive;
- use packaged `tools/7z.exe` for extraction;
- replace TLMTool.dist contents;
- use `bootstrap.exe` when updater self-replacement is needed;
- relaunch `TLMTool.exe`.

This is the real **full-process update/relaunch** path.

## 10. Forwarder cleanup differs by shutdown type

The distinction is explicit:

| Path | Forwarder behavior |
|---|---|
| forced heartbeat quit | **keep running / do not kill** |
| auto-update | **stop all forwarder processes** |
| normal user close | exact all-forwarder policy **NOT RECOVERED** |
| Login one-account reload | advances/uses that forwarder instance; does not imply global forwarder shutdown |

Reconstruction must preserve these differences.

## 11. Game-window cleanup differs by path

- Update explicitly closes all game windows before updater launch.
- Login account reload closes only the game window associated with that account when present.
- Start Reload repairs/unsticks tracked windows rather than closing them.
- Preview refresh does not close games.
- Normal TLMTool root close has no recovered shell-level `close all games` mandate.

Do not attach C16 `close_all_game_windows` to every TLMTool shutdown without evidence.

## 12. Logger/finalizer implications

E06 uses `atexit` to restore tee state and write the end-of-session marker in normal interpreter shutdown.

Forced `os._exit` is a hard process termination path. It must not rely on that normal atexit/finalizer contract.

This explains why normal-close and forced-close logs can legitimately differ.

## 13. Reload taxonomy for reconstruction

```text
TAB REBUILD
  _rebuild_tab
  → widgets/content only

PREVIEW REFRESH
  refresh_window_preview_list / _refresh_detached_preview
  → DWM/view resources only

START "RELOAD"
  _unstick_all_cmd → unstick_windows
  → in-process input/window-lock recovery

LOGIN ROW "RELOAD"
  _reload_worker
  → proxy advance → close that game → re-login account

AUTO UPDATE
  Info on_auto_update_click
  → close games → stop forwarders → spawn update.exe
  → replace files → relaunch TLMTool.exe
```

These five flows are behaviorally different and must stay separate.

## 14. Reconstruction contract

For parity:

1. allow normal Tk destruction to trigger each owner's `<Destroy>` save/cleanup;
2. do not invent a shell-global helper kill on normal close;
3. preserve Info heartbeat forced-exit semantics and its forwarder-survival rule;
4. preserve `os._exit` as a special forced path, not normal close;
5. keep tab rebuild and preview refresh in-process;
6. implement Start `Reload` as unstick/recovery, not restart;
7. implement Login row Reload as proxy advance + game close + re-login for that account;
8. keep full TLM process restart confined to update/relaunch flow unless later evidence proves another path;
9. stop all forwarders explicitly before auto-update;
10. preserve tab-owned persistence and cancellation on destruction.
