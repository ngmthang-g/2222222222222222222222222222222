There is therefore a small text discrepancy between the supplied screenshot (`Đồn vàng`) and the frozen EXE string (`Dồn vàng`). Do not silently normalize it. F11 must decide the final visual literal by direct parity testing while retaining internal mode `don`.

## 2. Persisted setting
The Login config load surface contains `after_login` with default/fallback `wait`.

The save surface also contains `after_login`.

Therefore the selected destination is persistent configuration, not transient UI state.

## 3. One routing coordinator
The original defines:

- `LoginTab._auto_start_after_login`
- `LoginTab._auto_start_party_after_login`

The generic method documentation is explicit:

> Sau khi login xong (tùy chọn Party/Train/Train LSV/Dồn vàng), chờ tab tương ứng quét thấy các cửa sổ vừa login rồi kích hoạt nút Bắt đầu của tab đó. Chế độ "Chờ" → không làm gì.

This is the routing contract. Login does not immediately call Train/Party logic before the target tab has refreshed its own window/account rows.

## 4. Chờ mode
`wait` performs no post-login action.

No tab is auto-started.

## 5. Party is a dedicated path
Party has its own helper because its runtime state differs from Train-like tabs.

Recovered Party-specific surfaces:

- target ref: `party_tab_ref`
- scanned rows: `_member_rows`
- running state: `_running`
- start/stop entry point: `_toggle_run`

Exact helper documentation:

> Sau khi login xong (chọn Party): chuyển sang tab Party, chờ tab quét thấy các cửa sổ vừa login rồi bấm Bắt đầu của Party.

If the Party ref is missing, the original logs a warning and does not invent a fallback.

If Party is already running, the original logs `Party đang chạy rồi — bỏ qua`.

On activation it logs `Đã kích hoạt Party sau login`.

## 6. Train / Train LSV / Dồn vàng share the generic Train-like path
The generic helper contains direct refs:

- `farm_tab_ref`
- `train_lsv_tab_ref`
- `donvang_tab_ref`

and mode/label literals:

- `train` → `Train`
- `train_lsv` → `Train LSV`
- `don` → compiled label `Dồn vàng`

Recovered runtime surfaces:

- `_acc_rows`
- `_farming_acc`
- `_farming`
- `_toggle_farm`

The original therefore activates the target tab's real global Bắt đầu/toggle path. It is not a fake button press and not a new Login-owned automation engine.

## 7. Tab selection occurs before readiness wait
The generic helper contains `_TAB_TEXT`, `tabs`, `tab`, and `select` plus a nested UI lambda.

It logs `Lỗi chuyển tab ...` on selection failure.

The Party helper has the same pattern and logs `Lỗi chuyển tab Party: ...`.

The target tab must be selected first because hidden tabs may not have populated their scanned rows yet.

## 8. Readiness wait is bounded at 20 seconds
A later original Party dispatch helper explicitly documents:

> Giống login_tab._wait_and_activate: tab ẩn không quét → sau khi chuyển tab phải đợi tối đa 20s cho đủ hwnd.

This is direct cross-reference to Login's `_wait_and_activate`.

Therefore Login's post-login routing uses a bounded target-tab readiness wait of at most 20 seconds.

The exact poll sleep/cadence inside those 20 seconds is not recovered strongly enough to claim.

## 9. Readiness is based on target-tab scanned window rows
The Login generic helper documentation says it waits until the target tab scans the windows that were just logged in.

The recovered structures `_acc_rows` / `_member_rows` and the Party cross-reference establish HWND-backed row readiness rather than an arbitrary sleep-only delay.

The exact identity/count formula used by Login's helper (for example exact subset-vs-count rule) remains explicit UNKNOWN.

## 10. Main-thread activation handoff
The generic helper contains nested `_on_main` and a nested lambda; the Party helper contains the same UI-handoff pattern.

The wait/readiness work therefore does not directly mutate Tk state from the background path. Final tab selection/start activation is handed back to the main/UI thread.

The exact Tk `after(...)` delay literal is not recovered and must not be invented.

## 11. Already-running guards
Train-like routing checks the target's farming state before toggling.

Recovered original log:

`[LOGIN] <target> đang chạy rồi — bỏ qua`

Party uses its dedicated `_running` guard and equivalent skip behavior.

This is critical: post-login routing must not invert a running target by blindly calling a toggle.

## 12. Missing-ref guards
For Train-like targets the original contains:

`[LOGIN] ⚠️ Không có ref tab để auto-start ...`

For Party:

`[LOGIN] ⚠️ Không có ref party_tab để auto-start`

Missing target references cause a safe skip/warning, not a guessed substitute.

## 13. Error handling
Recovered errors include:

- `[LOGIN] Lỗi chuyển tab ...`
- `[LOGIN] Lỗi auto-start ...`
- `[LOGIN] Lỗi chuyển tab Party: ...`
- `[LOGIN] Lỗi auto-start party: ...`

A routing error is contained to post-login activation and does not redefine the already-completed Login result.

## 14. Manual and scheduled Login share this routing layer
F09 established that scheduled open calls the same `_open_game_batch` used by manual Login.

F06 established that the Login monitor waits for all account-login workers before final UI completion.

The routing helpers are in that same completion region, so both manual and scheduled batches feed the same `after_login` routing behavior.

The scheduler remains alive after Login completion and continues waiting for the later close event; post-login routing does not disable scheduling.

## 15. Partial-failure boundary
The completion block contains success/total result aggregation and the routing helper call surface.

However static evidence is not strong enough to prove the exact invocation condition when a batch has mixed success/failure, or when zero accounts succeed.

Do not invent a rule such as “route only when all succeed” or “always route if one succeeds” until F11 runtime parity confirms it.

## 16. Reconstruction contract
1. Persist `after_login`; default/fallback is `wait`.
2. `wait` does nothing.
3. `party` uses the dedicated Party helper/state and `_toggle_run`.
4. `train`, `train_lsv`, and `don` resolve to the real tab refs and real `_toggle_farm`.

7. Perform final Tk/tab/start activation on the UI thread.
8. If target ref is missing, warn and skip.
9. If target automation is already running, skip rather than toggling it off.
10. Preserve routing errors as local post-login errors.
11. Manual and scheduled Login must use the same routing layer.
12. Do not implement or modify Proxy runtime.
13. Preserve the screenshot-vs-EXE `Đồn vàng` / `Dồn vàng` text discrepancy for F11 visual decision.
14. Do not invent the exact readiness polling cadence or partial-failure trigger condition.
