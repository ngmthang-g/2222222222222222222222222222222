## 2. Follow only exists while a schedule group is actually running

Exact _toggle_follow documentation:

- ON + some group already running -> start the follow worker immediately.
- ON + no group running -> keep the option enabled but wait; a later run start will create the worker.
- OFF -> stop the worker immediately.
- the worker re-checks the checkbox each cycle, so unticking mid-run causes exit.
- config is saved.

The option is therefore a persisted mode, not a permanent background movement loop.

## 3. Running-group filter is explicit

Frozen group-state helpers have exact docs:

_group_is_running(gd):
“True nếu nhóm gd đang có worker chạy (cancel tồn tại và chưa set).”

_any_group_running():
“True nếu còn bất kỳ nhóm nào đang chạy.”

_follow_worker documentation then states that it processes only groups that are currently running their schedule.

A group that is configured but idle is skipped entirely:
- no leader-position read;
- no follower-position read;
- no follow movement.

## 4. Worker lifecycle has event + thread + generation protection

Constructor state:
- _follow_stop

It also says:

Therefore the architecture is:
1. one current follow worker per PhoBanTab instance;
2. stop event handles immediate stop;
3. generation snapshot prevents an old worker from remaining authoritative after restart;
4. worker self-terminates when no groups remain running.

## 6. Follower set excludes the leader slot

The follow block contains the exact slice constant:

slice(1, None, None).

Combined with first-slot leader semantics and the local _members helper, this statically binds the normal follower roster to group members after the first slot.

The leader is not commanded to follow itself.

Blank/offline members cannot produce a usable HWND/position and therefore do not become movement targets.

## 8. Follow is restricted to dungeon maps

The worker references DUNGEON_MAP_IDS and exact documentation says:

“Chỉ bám TRONG map phó bản (DUNGEON_MAP_IDS).”

If the leader leaves the dungeon-map set:
- the whole group stops following;
- old position/command cache is cleared;
- when the leader enters a dungeon map again, following can resume without the old safety-cache falsely blocking the first new follow tick.

This is not a general open-world “follow player” feature.

## 10. Same-map requirement

Exact worker documentation says:

“thành viên nào cùng map mà cách xa -> move đến vị trí trưởng”.

Therefore movement is only considered when:
- leader is in an allowed dungeon map;
- follower is on the same MapID as the leader;
- distance exceeds the follow-distance threshold.

A member on another map is not pulled by this worker.

## 11. Two different follow thresholds exist

The frozen module directly references:

PB_FOLLOW_DIST_TILES

and:

PB_FOLLOW_MOVE_TILES.

They have distinct meanings.

PB_FOLLOW_DIST_TILES:
- minimum leader/follower distance before a follow move is queued.

PB_FOLLOW_MOVE_TILES:
- safety threshold for detecting that a follower moved significantly on its own between polls.

The startup log format is exact:

“poll PB_FOLLOW_POLL s, bám khi cách > PB_FOLLOW_DIST_TILES ô”

and the worker doc separately uses PB_FOLLOW_MOVE_TILES for command-clash detection.

The numeric values of PB_FOLLOW_POLL, PB_FOLLOW_DIST_TILES and PB_FOLLOW_MOVE_TILES are not safely bound to their names from the serialized constants table alone. They remain explicit UNKNOWN rather than being guessed from nearby shared float constants.

## 12. Safety rule prevents follow from fighting another movement/combat command

The worker owns:
- last_pos
- commanded
- commanded_now
- prev
- moved
- dist.

Exact documentation:

If a follower moves by more than PB_FOLLOW_MOVE_TILES tiles in one poll and that movement was NOT caused by the previous follow command, skip that follower for this poll.

This is specifically described as protection against another active command:
- run-move;
- combat movement.

The intent is not “force the follower back no matter what”; it yields when the account appears to be moving for another subsystem.

## 13. Previous-follow commands are remembered across one poll

The presence of:
- commanded
- commanded_now

combined with the exact wording:

“không phải do follow ra lệnh poll trước”

locks the cache contract:

- the worker remembers which follower HWNDs were commanded by follow on the previous cycle;
- movement caused by that previous follow command does not get misclassified as foreign movement on the next cycle;
- a fresh commanded_now collection is built for the current cycle.

Exact dictionary/set mutation order is not instruction-bound and remains UNKNOWN.

## 14. Shared move-poll guard is an additional command-clash barrier

The follow block directly imports:

is_move_poll_active.

The frozen shared utils helper has exact documentation:

“True nếu đang có move wait_for_arrival poll trên hwnd (còn lái).
Follow worker gọi trước khi queue để khỏi giành lệnh.”

Shared utility state:
- _move_poll_ts
- _MOVE_POLL_TTL.

Exact frozen _MOVE_POLL_TTL:
**0.5 seconds**.

Thus before queueing a follow move, the worker checks whether another move_character wait-for-arrival controller is actively steering the same HWND.

If so, follow must not steal the movement command.

This guard is independent from the last_pos/commanded distance-delta rule.

## 15. Exact movement helper = shared move_character in follow_mode

The follow call has explicit keyword surface:

## 17. Follow does not interrupt Auto FuBen

This is independently explicit in the worker doc:

“Không stop auto ... auto fuben đang bật được giữ nguyên.”

That distinction is critical.

A naive implementation that calls stop_game_auto before following would break the original behavior.

The follow move is deliberately non-destructive to the dungeon auto state.

## 18. Follow worker is periodic, not one-shot

The exact worker documentation says:

“Mỗi PB_FOLLOW_POLL giây...”

and describes a full repeated cycle.

At each cycle it re-evaluates:
- checkbox still enabled;
- worker generation still current;
- any running groups still exist;
- each group still running;
- current leader/follower memory positions;
- dungeon-map eligibility;
- command-clash guards;
- distance.

Therefore the destination is continuously refreshed from the leader’s current memory position.

## 19. Cache reset when leader exits dungeon maps is deliberate

The frozen worker documentation explicitly says that when the leader leaves the dungeon:
- group stops following;
- position/command caches are cleared.

When it re-enters:
- following resumes;
- the first new tick is not rejected because of stale previous movement.

This must be preserved.

Exact low-level clear/pop order for last_pos and commanded is not instruction-bound.

## 20. Group run ending does not clear the saved checkbox

The checkbox is a persisted mode.

When no group is running:
- the current worker exits;
- the follow option may remain ON in config/UI;
- the next group run is allowed to build a new follow worker.

Do not automatically untick “Theo sau đội trưởng” when a schedule finishes.
