## 1. Exact post-party modes

The active Party config already locks these internal modes:
- `wait`
- `train`
- `train_lsv`
- `don`
- `phoban`.

The original `_after_party_action` documentation is explicit:

`Hanh dong Sau khi party (qua main thread):
        - phoban: kich hoat tab Pho ban chay quy trinh cua no.
        - train/train_lsv/don: bat farm rieng tung acc vua party tren tab
          tuong ung (giong nut ▶ tren dong, bo qua acc da chay/khong thay).
        - wait: khong lam gi.`

Thus `wait` is a true no-op.

## 2. Generic mode → destination mapping

Frozen Party constants map:
- `train` → `farm_tab_ref` → label `Train`
- `train_lsv` → `train_lsv_tab_ref` → label `Train LSV`
- `don` → `donvang_tab_ref` → label `Dồn vàng`.

If the corresponding ref is not connected, Party logs:

`[Party] Sau khi party=<mode> nhưng chưa nối tab`

and does not invent a fallback tab.

If there are no saved targets from the just-completed Party run, it logs:

`<label>: không có acc nào vừa party`

and skips dispatch.

## 3. Post-party target set is the just-partied account set, not all ready windows

Party constructor owns:
- `_targets_lock`
- `_last_targets`.

The post-party code-object metadata contains `targets`, and the background readiness method's local tuple shape directly exposes iteration variables:
- `nm`
- `hwnd`.

Therefore the post-party target identity passed to generic Train-like dispatch is a per-account **(name, Party-HWND)** shape.

RoleID and TeamID are not part of this handoff.

This is distinct from:
- all currently ready Party accounts;
- all Start-discovered game windows;
- all rows already present on the destination Train tab.

The target set is specifically the set of accounts accumulated from the Party run that just completed.

### Explicit aggregation micro-order unknown
The exact source-level reset/merge order of `_last_targets` across parallel cluster workers is not exposed by readable constants. `_targets_lock` proves synchronized aggregate storage, but G11 does not invent the exact append/reset statements.

## 4. Phó Bản is a special whole-tab handoff

`phoban` does not use the per-account `_toggle_single_farm` dispatcher.

Original Party logs include:
- `[Party] Sau khi party=Phó bản nhưng chưa nối phoban_tab`
- `[Party] Phó bản đang chạy rồi — bỏ qua kích hoạt`
- `[Party] Sau khi party: kích hoạt Phó bản`
- `[Party] kích hoạt phó bản lỗi: ...`.

A dedicated method exists:

`_after_phoban_main`

with exact documentation:

`Chay tren main thread: chuyen sang tab Pho ban + bat quy trinh.`

The notebook helper uses the exact visible label `Phó bản`.

Therefore Phó Bản handoff:
1. requires `phoban_tab_ref`;
2. skips if the Phó Bản process is already running;
3. runs on the Tk main thread;
4. selects the visible Phó Bản notebook tab;
5. starts the Phó Bản tab's own process.

No Party per-account target list is passed into the Phó Bản handoff.

## 5. Notebook selection is text-based and main-thread owned

Dedicated helper:

`_select_tab_by_text`

has exact documentation:

`Chuyen notebook sang tab co tieu de label. Tra True neu thay.`

Its code-object surface contains:
- `tabs`
- `tab`
- `text`
- `select`.

Thus Party switches the shared notebook by visible tab title rather than hard-coding a notebook index.

This keeps the tab handoff resilient to tab-order changes while preserving exact labels.

## 6. Generic Train / Train LSV / Dồn vàng selects the destination tab before readiness polling

The original post-party flow contains nested `_ensure_refresh` and background method:

`_wait_and_dispatch_after_party`.

Exact readiness documentation:

`Cho tab dich quet xong rows roi moi dispatch (chay background).

        Giong login_tab._wait_and_activate: tab an khong quet → sau khi
        chuyen tab phai doi toi da 20s cho du hwnd. Chi doc _acc_rows.get
        ("hwnd") o background (khong cham widget), dispatch that tren main.`

Therefore the order is:
1. switch/select the destination tab on the main thread so its normal scan can run;
2. perform readiness waiting in a background path;
3. read only destination `_acc_rows["hwnd"]`-style data in that background wait;
4. return the actual UI/farm toggle dispatch to the main thread.

This mirrors the Login F11 hidden-tab readiness principle but is a Party-owned post-action flow.

## 7. Exact readiness loop = 1 second × maximum 20 polls

The frozen constants immediately after local `want` contain:
- serialized range values 0 / 20 / 1;
- `issubset`;
- `sleep`;
- serialized float 1.0.

Thus generic post-party readiness is:

- `want` = target Party HWND set;
- `have` = HWNDs currently present in destination `_acc_rows`;
- ready when `want.issubset(have)`;
- poll every **1.0 second**;
- maximum **20 polls / 20 seconds**.

The wait is bounded.

After that bound, dispatch proceeds to the main-thread matching stage; missing/partial targets are handled individually there rather than turning the whole handoff into an infinite wait.

## 8. Destination dispatch requires _toggle_single_farm

The main-thread generic dispatcher is:

`_after_dispatch_main`.

Its direct surfaces include:
- `_acc_rows`
- `_toggle_single_farm`.

If a destination tab does not expose `_toggle_single_farm`, Party logs:

`[Party] Tab <label> không có _toggle_single_farm`

and skips rather than substituting another start engine.

This preserves the real per-account start semantics of each destination tab.

## 9. Matching layer 1 — exact HWND

The exact dispatcher documentation says:

`Khop 2 lop: hwnd truoc (chinh xac), ten acc sau (phong hwnd stale /
        kieu khac nhau). Dung hwnd cua row tim thay de toggle.`

The dispatcher builds:
- `by_hwnd`
- `by_name`
- `by_lower`.

First preference is exact destination-row HWND equality.

This is the highest-confidence match.

## 10. Matching layer 2 — character-name fallback

If the Party HWND no longer directly matches a destination row, Party falls back to the account name.

Direct original log:

`: khớp theo tên (hwnd party=<old> → hwnd tab=<row>)`

The presence of both `by_name` and `by_lower` proves normal-name and lowercase lookup surfaces.

This is specifically intended to survive:
- stale HWND values;
- different HWND representations between the just-finished Party state and destination tab state.

## 11. Fresh re-resolution fallback

The dispatcher also contains:
- nested/local `_fresh_map`;
- exact log:

`: khớp sau resolve lại (hwnd mới=<...>)`.

Therefore there is a further fresh-resolution attempt before finally declaring the account absent.

G11 does not overstate the source expression used to construct `_fresh_map`; readable constants prove the fresh-resolution layer and its resulting new HWND, but not every internal dictionary statement.

## 12. Missing destination rows are per-account skips

If a target still cannot be resolved:

`(hwnd=<...>): không thấy trong tab <label> — bỏ qua (tab có <N> row...)`

If destination rows are completely empty, Party logs:

`chưa quét thấy acc nào (rows rỗng) — kiểm tra tab có bị hidden/khóa quyền không`.

Therefore partial post-party handoff is not all-or-nothing:
- found targets may start;
- missing targets are logged/skipped individually.

The local `used_hwnd` surface also proves the dispatcher tracks already-consumed destination HWNDs, preventing accidental repeated use of the same destination row during multi-target resolution.

## 13. Already-running target is never blindly toggled

Each matched destination row is checked through:
- `_farming_acc`.

Original log contains:
- `đã chạy <label>`.

If the destination account is already running that tab's farm process, Party skips it.

This prevents a generic toggle from accidentally stopping an already-active automation.

## 14. Successful per-account activation uses the destination row's current HWND

After all matching/fallback logic, the original documentation explicitly says:

`Dung hwnd cua row tim thay de toggle.`

So Party does **not** blindly pass the possibly stale Party HWND to the destination tab.

It calls the destination tab's real `_toggle_single_farm` using the current HWND associated with the matched destination row.

Successful activation log:

`: kích hoạt <label> OK`.

This is the same semantic as pressing the destination row's own ▶ button.

## 15. Target readiness vs stale-HWND fallback is intentionally two-stage

There is an apparent tension:
- background readiness initially waits for the original Party target HWND set;
- main-thread dispatch can later match stale HWNDs by name/fresh resolution.

These are complementary:
- exact HWND readiness gives the fast/normal path;
- the wait is bounded to 20 seconds;
- stale/replaced HWNDs cannot stall forever;
- after timeout, name/fresh fallback still gives each account a chance to map to the current destination row.

Do not change the readiness wait to an unbounded name-based loop.

## 16. Main-thread/background boundary

Verified execution boundaries:

### Main thread
- post-party UI routing entry;
- notebook tab selection;
- Phó Bản activation;
- actual per-account `_toggle_single_farm` calls.

### Background
- `_wait_and_dispatch_after_party`;
- only readiness observation of destination row HWND data;
- 1-second polling.

A nested lambda returns the completed readiness phase to:

`_after_dispatch_main`

on the main thread.

This prevents Tk/widget mutation from the polling worker.

## 17. Global Party run vs single-cluster run

G09 already proved:
- global `_run_worker` calls `_after_party_action` after all global cluster threads settle;
- single `_run_single_worker` reuses `_run_one_group` but goes to `_reset_single_button` and has no post-party dispatch surface.

Therefore "Sau khi party" routing belongs to the **global Bắt đầu aggregate**, not each per-cluster `▶ Tạo nhóm N` button.

Per-group manual creation does not independently trigger Train/LSV/Dồn/Phó Bản routing.

## 18. Failed-cluster aggregate does not have an all-success result gate

The frozen `_run_worker` code-object/local surface contains:
- `threads`
- `own_cancels`
- `join`
- `is_alive`
- `_after_party_action`
- `_reset_run_button`

but no:
- result list;
- success counter;
- per-cluster return-value aggregation.

Its exact documentation says:

`xong het moi lam hanh dong Sau khi party + reset UI (1 lan duy nhat).`

Therefore static evidence supports:

**post-party routing is not gated on every cluster returning success.**

A cluster may terminate early/fail internally (for example create-team retries exhausted); once all cluster threads settle, the aggregate worker still has no recovered all-success predicate before its post-party phase.

This is different from Login F11's unresolved success guard.

## 19. Global cancellation gate remains explicit UNKNOWN

Because `self._cancel` can be checked without introducing a distinct local result variable, the absence of result locals does not resolve this branch.
