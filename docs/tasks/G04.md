## 1. Party does not own the physical game-window grid engine

Static scan of the frozen Party block found no Party references to:
- `_arrange_grid`
- `_move_windows_offset`
- `_auto_tile_windows`
- `_layout_worker`
- `_sync_windows_loop`
- `grid_cols`
- `grid_rows`
- `_get_preview_hwnds`
- master-window layout state
- `SetWindowPos` as a Party-owned primitive.

Therefore Party does **not** contain a second implementation of the Start tab's physical window-grid engine.

The existing C06/C07/C08 Start/window contracts remain authoritative for:
- common grid arrangement;
- Auto tiling;
- Xếp-lưới layout synchronization;
- master-first physical ordering.

## 2. Party does not directly invoke Start's grid/arrange entry points

Party does reference `start_tab`, but the directly recovered shared call is `start_tab.get_windows()`, already locked by G02 for ready-member discovery.

Within the Party implementation block there is no direct reference to:
- `start_tab._arrange_grid`
- `start_tab._move_windows_offset`
- `start_tab._auto_tile_windows`
- `start_tab._toggle_layout`
- `start_tab._sync_windows_loop`.

So Party consumes the shared HWND list but does not ask Start to physically re-tile those windows as part of Party refresh/group state.

## 3. Important distinction: Tk `grid` inside Party is UI layout, not game-window layout

The Party block contains:
- `grid`
- `grid_remove`
- `_relayout_ready_list`
- exact Party documentation: `Sắp lại grid 3 acc / dòng; ẩn acc đã được cụm nào chọn.`

These are Tk widget geometry operations for the Party ready-account list.

Likewise G01's:
- six group Combobox slots;
- `COLS_PER_ROW`;
- visible 2×3 arrangement

describe the Party tab's **UI control layout**.

They do not define positions of physical game HWNDs on the desktop.

## 4. Party group ordering is not physical window ordering

Party maintains logical ordering for:
- cluster/group order;
- six selected member names in each cluster;
- leader + followers;
- later group-action sequencing.

No static Party evidence connects that logical group order to:
- C06 grid slots;
- Start master index 0;
- Auto RoleName sort;
- Xếp-lưới columns/rows.

Therefore reconstruction must not infer:
`Party slot 1 → desktop grid slot 1`,
or any equivalent physical mapping.

The Party group model and Start physical-window layout model are independent subsystems unless later direct evidence proves a call edge.

## 5. One direct physical-window geometry operation does exist: resize_window

G04 found one important exception to the otherwise negative layout result.

Inside `PartyTab._click_create_team`, the frozen Party constants include:
- local/argument `lhwnd` in the code-object metadata;
- shared helper `resize_window`;
- serialized integer **1366**;
- serialized integer **768**;
- direct Party error text beginning `[Party] resize cửa sổ trưởng nhóm lỗi: ...`;
- exact method documentation: `Acc chủ tạo đội bằng click UI (game 1366x768).`

Raw frozen bytes immediately after the `resize_window` constant are:
- `6c d6 0a` → small-int 1366;
- `6c 80 06` → small-int 768.

This is direct EXE evidence that the Party create-team UI path normalizes the **leader window** to 1366×768 before fixed-coordinate UI interaction.

## 6. The Party resize is not grid arrangement

The shared C06 `resize_window` contract is already verified:
- `GetWindowPlacement`
- `ShowWindow(SW_SHOWNORMAL)`
- `SetWindowPos`
- `SWP_NOZORDER`
- `SWP_NOACTIVATE`
- `SWP_NOMOVE`.

Therefore Party's create-team resize:
- changes the target leader window size to 1366×768;
- preserves its current x/y position through `SWP_NOMOVE`;
- does not constitute a tile/grid rearrangement;
- does not activate the window through the resize helper itself;
- does not change z-order through that helper.

The later click helper may target the window separately, but action/click sequencing belongs to the Party action task, not G04.

## 7. Resize scope is leader/current create-team HWND, not all Party members

The code-object local surface for `_click_create_team` contains `lhwnd`, and the method documentation explicitly says:

`Acc chủ tạo đội bằng click UI (game 1366x768).`

G04 therefore locks the resize scope to the leader/create-team window supplied to that method.

No Party loop around `resize_window` was recovered that resizes:
- all six members;
- all ready accounts;
- all Start-discovered windows.

Do not turn this into a global Party resize.

## 8. Why Party needs the resize

The same create-team constant block contains fixed UI-coordinate logic, including:
- click path around `nguoiChoiGan`;
- fixed click `(391, 683)`;
- another fixed path around `muiTenAnNhiemVu`;
- fixed click `(34, 462)`;
- method documentation explicitly says `game 1366x768`.

The 1366×768 normalization is therefore a coordinate-system precondition for this Party UI-click sequence, not a visual layout preference.

G04 does not analyze the full create-team click algorithm; that remains later action-button scope.

## 9. No Party master-window concept recovered

Party has a **leader** concept for a group.

Start/window layout has a **master HWND** concept for preview/layout/input sync.

These are not the same concept.

No Party static evidence equates:
- group leader HWND
with
- Start master HWND.

Do not automatically promote a Party leader to Start master, and do not reorder Start's physical window layout merely because Party leader selection changes.
