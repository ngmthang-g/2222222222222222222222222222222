## 1. Two start/stop entry points share the same lifecycle

The UI has:
- bottom button text `Bắt đầu` bound to `_toggle_run`;
- one per-group `Bắt đầu lịch trình` button, also routed through `_toggle_run` with a group argument.

Exact `_toggle_run` documentation:

> cuối tab (gd=None): dừng HẾT nếu đang chạy nhóm nào, ngược lại chạy TẤT CẢ nhóm (mỗi nhóm 1 thread, song song).
>
> Nút trong cụm (gd): chỉ dừng/chạy NHÓM ĐÓ, các nhóm khác không ảnh hưởng (đang chạy thì chạy tiếp song song).

Therefore:
- bottom button is a tab-wide start-all / stop-all toggle;
- group button is a start-one / stop-one toggle;
- starting/stopping a group does not serialize or cancel the other groups.

## 2. Stop decision is made before start preflight

The frozen block places the exact stop branches ahead of the permission/start-preflight surfaces:
- group stop log: `[Phó bản] Dừng Nhóm ...`;
- all-stop helper: `_stop_all_runs`;
- only after those branches appear `has_permission_with_limit`, job collection and launch surfaces.

This matches the exact doc: pressing an already-running button means stop, not “revalidate then stop”.

Thus a stop request is not blocked by a start permission check.

## 3. Permission gate is before new job launch

The start path directly references:

## 4. Shared dependency preflight belongs to start, not stop

The same start block contains:

`[Party] Lỗi import memory_items:`

before current HWND/job collection.

The group worker later relies on the memory-items surface for setup/configuration.

Static constant order therefore places memory-items dependency acquisition in the **new-start preflight region**, after permission and before runnable-job execution.

Exact exception-return source expression is not instruction-bound, so J12 does not invent a line-for-line `try/except`; reconstruction must simply avoid launching a broken job when required memory plumbing is unavailable.

## 5. Per-group start filters before resetting progress

Exact start surfaces are ordered around:
- `_collect_group_job`;
- invalid-group log `: không có acc online + lịch trình`;
- `_reset_group_progress`;
- `_run_cancel`;
- `_run_one_group`.

Combined with the exact job contract from J04/J11:

`(num, targets, sched)`, or `None` if there is no online selected account or no checked schedule row.

The strongest static lifecycle is:

1. preflight permission/dependency;
2. collect the group job;
3. if not runnable, log and return without a run;
4. reset only that group's row progress;
5. install a fresh group run-cancel identity;
6. register/launch the group run;
7. synchronize visible run buttons.

This preserves the distinction between “invalid request” and “new run”.

## 6. Start-all filters groups independently

Bottom start uses the same `_collect_group_job` contract across groups.

Configured groups lacking:
- online selected targets; or
- checked schedule rows

are skipped rather than preventing valid groups from starting.

Thus start-all means **all runnable groups**, not literally all configured group cards.

## 7. Progress reset semantics differ for one-group versus all-group start

The frozen start block contains both:
- `_reset_group_progress`;
- `reset_all_progress`.

Per-group start uses the group-specific reset surface.

The successful all-groups start path uses the all-row reset surface before the parallel-run state is presented.

Therefore:
- starting one group should not erase progress labels belonging to unrelated running/configured groups;
- start-all begins from a clean progress display across the current schedule rows.

The exact single machine-instruction placement of `reset_all_progress()` relative to construction of the first per-group thread is not recoverable from printable constants; the semantic boundary is that reset belongs to a successful fresh all-groups launch, not to a stop request.

## 8. Every newly-started group receives a fresh cancel identity

J07/J11 already locked that one group is running only while its current `_run_cancel` exists and is not set.

The start region references `_run_cancel` immediately around the `_run_one_group` launch path.

J07 exact cleanup documentation then compares cancel/job **identity**, specifically to protect a rapid restart while an old worker is winding down.

Therefore each new group run must receive a new per-run cancel identity; reusing an old set Event would contradict the frozen restart/identity contract.

## 9. Global cancel is a tab-wide stop signal, not the group identity

Constructor state contains:

## 10. Run registration must precede successful shared-worker activation

J03/J08/J09/J10 all say their background modes only run while a Phó Bản schedule is running.

Their start behavior is exact:
- Follow: ON + running → start; ON + idle → wait for run start.
- Discard: any discard tick ON + running → start; idle → wait.
- Pickup: keepalive only runs during schedule lifetime; tick during run starts immediately.
- Nga My buff: ON + running → start; idle → wait for run start.

Therefore a fresh run must become visible as an active group before a shared worker can successfully pass its own run-scope guard.

This establishes the semantic ordering:

```text
valid group job + current run identity visible
        ↓
shared enabled background modes may be ensured/started
```

## 22. Integrated state transition

The static combined lifecycle is:

```text
IDLE
  ↓ user Start
stop branch? no
  ↓
permission/dependency preflight
  ↓
collect runnable group job(s)
  ↓ none → remain IDLE
  ↓ valid
reset relevant progress
  ↓
fresh per-group cancel/job identities
  ↓
register active run(s)
  ↓
ensure enabled shared worker modes
  ↓
group worker thread(s) execute
  ↓
RUNNING
  ↓ user group stop / stop-all / public stop / normal finish / hard abort
cooperative cancel + worker unwind
  ↓
per-group identity-safe _finish_group_run
  ↓
other group remains?
  ├─ yes → continue RUNNING for remaining group(s)
  └─ no  → one global teardown → IDLE
```

Exact native micro-order among group Thread.start and the four shared-worker start calls is the only unresolved ordering inside the successful-launch segment.
