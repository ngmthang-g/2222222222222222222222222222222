## 1. The controls belong to each embedded preview header

Original `refresh_window_preview_list` constants contain the two visible header symbols:
- `◀`
- `▶`
- button `command` bindings created inside the preview-item builder.

The current Start/Xếp-lưới screenshot shows both arrows on every visible embedded preview item.

Therefore these controls are per-preview-item ordering controls, not game movement buttons and not detached-preview column controls.

## 2. Exact callback and delta semantics

Original method:
- `_move_preview_item`
- state: `_preview_order`.

Exact original documentation:
`Nút ◀/▶ trên header preview: đẩy cửa sổ này lên trước (delta=-1) hoặc sau (delta=1).`
`Lưu thứ tự theo hwnd → refresh sẽ giữ thứ tự sau mỗi rebuild.`

This proves the mapping:
- `◀` → move the selected preview one logical position earlier, `delta = -1`;
- `▶` → move the selected preview one logical position later, `delta = +1`.

The ordering operation is logical preview order only. It does not move the game HWND on the Windows desktop.

## 3. Ordering is keyed by source HWND

The same constant block recovers:
- `src_hwnd`
- `_preview_order`.

Therefore the persistent-in-runtime ordering key is the source game HWND, not the current preview row/column number and not the character label text.

This matters because preview rows/columns are rebuilt whenever:
- the 1x–5x column count changes;
- a full refresh occurs;
- the live game-window set changes.

## 4. Refresh/rebuild preserves the manual order

C15 independently recovered full preview teardown/rebuild.

The original C17 documentation explicitly says refresh preserves order by HWND. Therefore:
`manual ◀/▶ reorder → _preview_order → full rebuild → same surviving HWNDs keep the manual logical order`.

Newly discovered HWNDs or closed HWNDs still pass through the existing discovery/rebuild lifecycle; exact insertion position for a newly appearing HWND relative to an existing manual order is not source-visible and remains UNKNOWN.

## 5. Column count is independent from order

C09 recovered the separate main preview column state:
- `preview_grid_var`
- 1x–5x choices
- `_get_preview_columns`.

C17 ordering is therefore orthogonal:
- 1x–5x decides how many columns the logical ordered list is laid out into;
- ◀/▶ changes the logical list order itself.

A column-count change must reuse the retained `_preview_order`; it is not a request to re-sort previews by character name.

## 6. DWM source/destination identity follows the reordered item

C03 proved each preview item binds:
`destination DWM overlay HWND → source game HWND`.

After an order-changing rebuild, the preview frame position changes but the preview item still represents the same source game HWND. DWM resources are torn down/recreated as needed by the normal refresh lifecycle.

Thus the reorder is safe to model as a UI-list/order change, not as reassignment of one preview image to a different game HWND.

## 7. Boundary behavior is not fully source-visible

The screenshot shows both arrow controls present on the first and last visible preview items; there is no visual evidence that edge arrows are disabled.

Readable static evidence proves only the requested deltas `-1` and `+1`. It does not expose the exact branch when:
- first item receives `delta=-1`;
- last item receives `delta=+1`;
- the target HWND is missing from the current order because a game closed between click and callback.

C17 therefore does **not** invent wrap-around, clamping, or explicit no-op behavior. Exact boundary handling remains `EXPLICIT UNKNOWN` until Windows runtime tracing or stronger decompilation.

## 8. Detached preview relationship

C14 recovered a separate detached-preview subsystem with its own:
- `detached_items`
- `detached_grid`
- control bar.

No `◀/▶` ordering controls were recovered in the detached control bar, and `_move_preview_item` is recovered in the embedded `refresh_window_preview_list` path.

Therefore the verified scope of C17 is the embedded/main preview list.

Whether detached preview indirectly consumes the same `_preview_order` when it opens/rebuilds is not proven by readable static evidence, so detached-order propagation remains `EXPLICIT UNKNOWN`.

## 9. Persistence boundary

No `preview_order` key was recovered in the Start `settings.ini` load/save block.

Therefore the manual preview order is classified as runtime state for the current tool session from current evidence; persistence across application restart is `NOT_RECOVERED`.
