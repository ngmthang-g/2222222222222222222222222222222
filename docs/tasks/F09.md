## 1. Schedule controls
The original Login UI contains Boolean _schedule_on; checkbox `Chạy theo lịch (mở/tắt game)`; close-time controls `Hẹn giờ tắt game:`; open-time controls `Hẹn giờ mở game:`; Boolean _shutdown_after_close; checkbox `Tắt máy sau khi tắt game`; and countdown/status label lbl_sched_countdown.

The locked Login screenshot gives the visible defaults: schedule OFF, close time 04:00, shutdown-after-close OFF, open time 04:20.

## 2. Schedule and manual Bắt đầu are deliberately independent
Exact original documentation for the main Login button says the Bắt đầu button always opens game immediately and a second press stops the active batch.

It also explicitly says the manual button is unrelated to scheduling: the `Chạy theo lịch` checkbox controls scheduling independently; pressing Bắt đầu does not enable/disable scheduling and scheduling does not redefine the manual button.

## 3. Schedule toggle semantics
Exact original documentation says the `Chạy theo lịch` checkbox enables/disables the schedule worker and is independent from Bắt đầu.

When enabled:
- start the schedule worker;
- show the countdown immediately;
- no game needs to be opened at enable time.

When disabled:
- stop/cancel the schedule worker;
- clear the countdown;
- already-open game windows are not touched by merely disabling the schedule.

Visible status text:
- ON: `⏰ Đã bật chạy theo lịch — chờ đến giờ mở/tắt game`
- OFF: `⏰ Đã tắt chạy theo lịch`.

Login initialization owns _schedule_cancel as a threading Event and _schedule_active state. Schedule shutdown is therefore cooperative, not a forced thread kill.

## 4. Background worker cadence
Exact worker documentation says: `Chạy worker nền kiểm tra giờ hẹn (mỗi 20s) khi chọn 'Theo lịch'.`

Therefore event-trigger evaluation runs on a background worker with a documented 20-second check cadence.

## 5. Time parser and next-occurrence rule
The worker defines local _parse and local _next_occurrence.

Exact documentation for _next_occurrence: `Lần hẹn kế tiếp của (h:m): hôm nay nếu chưa qua, mai nếu đã qua.`

Thus each configured event becomes an absolute datetime: today at HH:MM if still future, otherwise tomorrow at HH:MM.

## 6. Critical old-bug fix: no immediate catch-up after enabling late
The original contains a detailed bug-fix note.

Old behavior: enabling schedule at 15:00 with open time 04:30 made a naive `current >= configured` check true immediately, so login started immediately and the close time could also trigger moments later.

Fixed behavior: compute the next absolute occurrence of each event, wait until now reaches that event, then move that event by +1 day.

Therefore enabling scheduling after today's configured time has passed waits until the next day; it does not immediately catch up a missed open/close event.

## 7. Daily recurrence
After each event triggers, its next occurrence is advanced by one day. The scheduler is therefore a persistent daily loop, not a one-shot alarm.

The logic follows actual absolute event time rather than assuming the close event must always precede the open event.

## 8. Countdown display is updated on the Tk main thread
Exact local documentation: `Update label đếm ngược trên main thread (gọi mỗi giây).`

The duration formatter documents examples: `2h05p`, `15p30s`, `45s`, `1d2h05p`.

Adjacent original constants establish the countdown composition using `Tắt `, format `%H:%M %d/%m`, ` còn `, separator ` | `, and `Mở `.

Thus the visual countdown is refreshed about every second on the Tk main thread, while event-trigger evaluation remains on the 20-second schedule worker.

## 9. Scheduled close event
Exact runtime text: `⏰ Đến giờ tắt game (...) — đóng tất cả`.

The verified high-level contract is: scheduled close occurrence -> Login close-all behavior for game windows.

F09 does not invent the exact instruction-level order between cancelling an in-progress Login batch, enumerating/closing windows, and clearing runtime tracking.

## 10. Optional PC shutdown after scheduled close
The schedule worker block contains _shutdown_pc_popup and the persisted UI flag is _shutdown_after_close, paired with exact label `Tắt máy sau khi tắt game`.

When enabled, the close path enters the shutdown confirmation/countdown flow. When disabled, the scheduled close does not intentionally trigger PC shutdown.

## 11. Shutdown popup contract
Exact popup documentation:
- show a confirmation popup with a 60-second countdown;
- Hủy or closing the popup cancels shutdown;
- if 60 seconds expires with no response, shut the PC down.

Recovered UI:
- title `⚠️ Tắt máy tính`;
- geometry 340x150;
- topmost;
- WM_DELETE_WINDOW mapped to cancel;
- body `⏰ Đã tắt game.\nMáy tính sẽ TẮT sau 60 giây.`;
- initial countdown `60s`;
- buttons `Xác nhận tắt máy` and `Hủy tắt máy`.

Cancel outcome includes `[SCHED] Shutdown cancelled by user` and `✅ Đã hủy tắt máy`.
Confirm/timeout shows `⚠️ Đang tắt máy tính...` and calls _shutdown_pc.

## 12. Actual Windows shutdown command
Exact _shutdown_pc documentation: `Gửi lệnh tắt máy (shutdown /s /t 0).`

Recovered argument constants are `shutdown`, `/s`, `/t`, `0`.
Logs include `[SCHED] Shutdown command sent` and `[SCHED] Shutdown error: ...`.

## 13. Scheduled open event reuses the normal Login batch path
The schedule worker block contains _open_game_batch.

Exact method documentation says: `Mở game theo các acc đã tick.` and that this method is used both by the Bắt đầu button and by the schedule worker when the open time arrives.

Therefore scheduled open uses the accounts currently checked for Login and reuses the normal F05/F06 launch/login pipeline.

## 14. Scheduled open does not overlap an active login batch
Exact runtime text: `⏰ Đến giờ mở game (...) — bỏ qua: đang có batch login chạy`.

Therefore the scheduler does not start a duplicate Login batch when one is already active.

## 15. Scheduler remains alive after login result
Original completion/status text includes both failed/successful login outcomes followed by `lịch vẫn chờ giờ tắt`.

Thus a scheduled open/login result does not disable scheduling; the schedule remains active waiting for the close occurrence.

## 16. Persisted scheduler configuration
The Login config load surface contains schedule_on, schedule_close, schedule_open and shutdown_after_close.

F01/E05 already established these are part of the shared Login configuration lifecycle.

Configuration persistence is verified. However, the exact instruction sequence proving that a saved schedule_on=True automatically restarts the worker on a fresh TLMTool process is not source-visible enough to claim from static evidence alone.

Status: persisted setting VERIFIED; automatic worker resume after process restart solely because the saved flag is true remains EXPLICIT UNKNOWN.

## 17. Changing controls persists configuration
The schedule time Comboboxes have selection callbacks, and shutdown_after_close is wired to _save_config. Schedule edits therefore participate in persistent config rather than existing only in worker memory.

## 18. Turning scheduling off does not close existing games
Exact toggle documentation says disabling scheduling stops the worker and clears countdown while leaving already-open game windows untouched.

This differs from an actual scheduled close occurrence, which closes game windows.

## 19. Interaction with post-login routing
Scheduled open invokes the normal Login batch. After that batch finishes, any configured `Sau khi login` destination is handled by the post-login routing layer.

F09 does not define those destinations; F10 does.

## 20. Reconstruction contract
1. Keep scheduling independent from manual Bắt đầu.
2. Use the dedicated cancellation Event/active state for scheduler lifetime.
3. Enabling scheduling starts countdown immediately but does not immediately open games.
4. Disabling scheduling stops worker/countdown and leaves current game windows alone.
5. Evaluate scheduled actions on the documented 20-second worker cadence.
6. Calculate next occurrence as today if future, tomorrow if already passed.
7. Never catch up a missed event immediately when scheduling is enabled late.
8. After each trigger move that event by +1 day.
9. Update the countdown label on the Tk main thread about every second.
10. Scheduled close performs Login close-all behavior.
11. If shutdown-after-close is enabled, show the 60-second shutdown confirmation popup.
12. Popup close/Hủy cancels shutdown.
13. Confirmation or timeout invokes `shutdown /s /t 0`.
14. Scheduled open calls the same _open_game_batch used by manual Login.
15. Use the currently checked account rows.
16. If a Login batch is already active, skip the scheduled open rather than starting a duplicate batch.
17. Keep scheduling active for later events after login success/failure.
18. Keep post-login routing in F10.
19. Do not assume saved schedule_on automatically resumes the worker after process restart until direct proof exists.
