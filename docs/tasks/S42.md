## What was implemented
- NEW `src/login_schedule_worker.py`: **real background Python thread** named `F09-S42-evaluation-only`, daemon, uses `threading.Event.wait(WORKER_CHECK_SECONDS)` where F09 original `WORKER_CHECK_SECONDS == 20`. Cancellation `Event.set()` interrupts a pending 20-second wait; `stop(timeout)` joins before restart and `shutdown()` permanently denies further starts.
- `start()` must be called **explicitly** with a valid `ReadOnlyScheduleSettings` (S40). It instantiates the S39 daily clock at the moment it is armed; does NOT automatically start if original persisted schedule_on happens to be `True`/`1`/`yes` or some unknown token. No immediate catch-up actions when enabled late.
- Every due S39 schedule occurrence produces immutable `BlockedScheduleOccurrence(kind,planned_time,status=BLOCKED_ACTION_UNAVAILABLE)`, audit stored ONLY in bounded memory (max 64; **local memory-safety decision, not original behavior**). The worker never invokes actual callbacks, subprocess/OS shutdown, native HWND closing, Win32 game injection, Login batch or account access; no game/Proxy runtime. `poll_once()` is an explicit read-only testable method, and the worker invokes the same method after each actual 20-second Event wait. S39 suppresses duplicates for the same due occurrence and moves the event to future daily deadline.
- `start` refuses duplicate concurrent background threads, `stop` avoids forced thread kills, returns false and prevents parallel restart if cancellation join times out; `shutdown` is idempotent. Clock rollback/invalid now() fails closed without printing exception/credential values.
- Native Windows test exercises TWO cases: test-owned accelerated **real** Event.wait to verify actual worker passes exactly **20** as timeout and correctly observes due events without dispatch, plus a second *unmodified* Event.wait(20) thread interrupted promptly by cancellation, without waiting the whole 20s. The real background thread scheduling/cancel is tested, not product game automation.
