## 1. Main Open Game guard path
The original _open_game path contains has_permission(login_tab), check_account_limit(login, extra=1), the denial text '❌ Không có quyền mở game — kiểm tra key bản quyền', the missing-directory text '❌ Chưa chọn thư mục game', _get_exe_path, and the missing-EXE text '❌ Không tìm thấy ... trong: ...'.

Therefore the generic Open Game action checks permission, checks account/window limit with extra=1, requires the configured game directory, resolves the canonical executable through _get_exe_path, then dispatches blocking launch work off the Tk thread.

## 2. Generic launch worker
The same block contains _launch_worker plus Thread target/args/daemon evidence, so the generic launch path is asynchronous.

The worker contains _apply_proxy_hook_env, _make_safe_env, spawn_and_inject, exe_path, cwd, env, timeout_ms, an encoded integer 15000, ok, and logs '[LAUNCH] Inject profile ... FAILED:', '[LAUNCH] Exception profile ...', and '[LAUNCH] Launched ... windows with inject'.

Thus the worker builds a clean environment, overlays Login proxy-hook state, calls suspend+inject, uses a 15,000 ms timeout in this path, and counts successful launches.

Explicit unknown: the exact source-level profile iteration/selection rule inside generic _launch_worker is not recoverable from readable constants alone. F05 does not invent whether it picks the first free profile, loops a fixed range, or derives profile state elsewhere.

## 3. Profile-specific launch
The original contains _open_profile and _launch_profile_worker with exact docs 'Mở game với profile index (1-5).' and 'Launch 1 instance via suspend+inject.'

Recovered visible states:

Therefore profile launch is a one-instance operation for profile indices 1–5 with its own busy/success/error feedback. F01 remains authoritative for the fact that hidden/conditional profile-control pixels are not locked by the screenshot.

## 4. Clean launch environment
The shared dll_injector module exposes _make_safe_env(tlm_profile: str) -> dict with exact documentation: 'Build minimal env: Windows essentials + TLM_PROFILE only.' and 'Prevents Python/VirtualEnv vars leaking into game (can break Unity TLS).'

The game is therefore not launched with an unfiltered copy of the Python process environment. Required Windows variables are preserved, TLM_PROFILE is added, and Python/virtual-environment contamination is excluded.

## 5. Login proxy environment overlay
The Login module contains a typed helper shape env, enabled, port -> dict together with exact constants TLM_PROXY_ENABLE, TLM_PROXY_HOST, TLM_PROXY_PORT, TLM_PROXY_FAIL, host 127.0.0.1, and fail-mode literal closed.

The launcher worker references _apply_proxy_hook_env. This proves a Login-specific proxy overlay is applied to the otherwise minimal environment. Exact enable-value string formatting and proxy-selection policy remain F08 scope.

## 6. Injection payload
get_default_dll_path has exact documentation 'Return bundled injected payload path: ./data/resources.dat.' D06 already verified resources.dat is the active x64 PE DLL-format injected payload.

## 7. Suspend → inject → resume
spawn_and_inject has exact original documentation:
1. subprocess.Popen(exe, CREATE_SUSPENDED, cwd=cwd, env=env): process exists but game code has not run;
2. VirtualAllocEx + WriteProcessMemory(dll_path);
3. CreateRemoteThread(LoadLibraryW): DllMain runs and InstallHooks executes while game is still suspended;
4. WaitForSingleObject(thread);
5. NtResumeProcess: game starts after hooks are installed;
returns (success, pid, error_msg).

This is the core launcher contract. Parity must not replace it with a normal start followed by much later injection.

## 8. Injection primitives and failures
Recovered primitives include OpenProcess, VirtualAllocEx, WriteProcessMemory, GetModuleHandleW(kernel32.dll), GetProcAddress(LoadLibraryW), CreateRemoteThread, WaitForSingleObject, GetExitCodeThread, NtResumeProcess, TerminateProcess, and kill.

Recovered failures include Popen failed, OpenProcess failed, VirtualAllocEx failed, WriteProcessMemory failed, CreateRemoteThread failed, LoadLibrary timeout, and LoadLibrary returned NULL.

Exact branch ordering for every failure cleanup is not instruction-decompiled, so F05 does not claim an instruction-perfect cleanup sequence.

## 9. Existing-process injection is separate
inject_into_pid is separately documented for an already-running process. It guards against double injection and returns (True, pid, 'already loaded') if the same DLL path is already loaded. Otherwise it uses OpenProcess → VirtualAllocEx → WriteProcessMemory → CreateRemoteThread(LoadLibraryW) → wait.

The Login launch path under F05 is centered on spawn_and_inject. Later feature modules may use inject_into_pid for existing processes.

## 10. Architecture boundary
The original injector states 'Python 64-bit → inject into 64-bit target only.' Gate A established the tool is x64.

## 11. Working directory
spawn_and_inject receives an explicit cwd, and the Login launcher block also carries exe_path and cwd. The exact source expression deriving cwd from the resolved game path is not recovered, so cwd derivation remains explicit UNKNOWN rather than guessed.

## 12. PID-bound main-window discovery
find_main_window_by_pid(pid) uses EnumWindows, GetWindowThreadProcessId, IsWindowVisible, GetClassNameW and GetWindowTextW.

Exact documentation says it prefers UnityWndClass or a title containing 'Thần Long' because the game may expose multiple top-level windows, then falls back to the first visible window owned by that PID.

## 13. Serialized launch / stable-HWND handoff
_launch_one_window has exact documentation: 'Launch 1 cửa sổ game + CHỜ BẮT ĐƯỢC cửa sổ THEO PID + ổn định.' It runs inside _launch_lock so only one game window is being opened at a time, and returns hwnd or None on failure/cancel.

Recovered failure text says no window found after 25s. Thus account-login launch is serialized by PID until the correct HWND is ready before the next game is opened.

The exact post-HWND stabilization duration is described only as 'vài giây'. A nearby literal 5 exists, but F05 does not bind it to stabilization without instruction-level proof.

## 14. Multi-account launch vs login concurrency
Exact documentation for _login_launch_and_process says 'Login nhiều acc: LAUNCH TUẦN TỰ + LOGIN SONG SONG.'

For each account, the network/forwarder state is prepared, the game window is launched sequentially under _launch_lock, the correct PID-owned HWND is captured and allowed to stabilize, and only then later click/login work can run in parallel under MAX_PARALLEL_LOGIN.

F05 owns only the launcher half. Credential/click-login concurrency remains F06.

## 15. Forwarder readiness precondition
_ensure_forwarder_alive is documented to ensure a forwarder is actually listening on the requested port. It returns True for a living/recently spawned instance and False if readiness cannot be guaranteed, with explicit guidance not to launch the game into a dead network path.

Port allocation, proxy rotation and pinned-proxy semantics remain F08.

## 16. Window-size normalization
_login_resize_monitor has exact documentation: every second it checks all game-window sizes; only if a window differs from 1366x768 does it call resize. It explicitly avoids continuous SetWindowPos to prevent window jitter.

It uses IsWindowVisible, GetWindowRect and the shared resize_window helper.

## 17. Unity crash-handler cleanup surface
The launch/resize block contains taskkill /f /im UnityCrashHandler64.exe. This proves an explicit UnityCrashHandler64 cleanup surface exists, but exact timing/trigger relative to every launch attempt remains UNKNOWN.

## 18. Launcher UI state
Profile-specific UI states are statically verified. The generic Mở game button directly calls _open_game, but an exact busy/disabled animation for that generic button was not recovered, so none is invented.
