# E04 — Shared application state

## STATUS
**VERIFIED_WITH_OWNERSHIP_BOUNDARIES_AND_EXPLICIT_GLOBALS_LIMIT**

E04 recovers which state belongs to the main shell, which state is shared through cross-tab references, and which state is owned by service/helper modules.

## 1. TLMMainApp-owned shell state

The main shell initializes and retains:
- `root`
- `notebook`
- `_tab_frames`
- `_tab_inner`
- `_tab_keys`
- `_callback_ready`
- `_current_tab`
- `_perm_state`
- `_prev_limit_state`
- `cpu_monitor`
- `start_tab`
- tab instance references such as login/party/farm/train-LSV/etc.

These fields are shell coordination state, not module-global game state.

## 2. Cross-tab reference wiring

The shell exposes/wires references including:
- `daily_tab_ref`
- `start_tab_ref`
- `farm_tab_ref`
- `train_lsv_tab_ref`
- `donvang_tab_ref`
- `phoban_tab_ref`
- `party_tab_ref`
- `login_tab_ref`
- `toiuu_tab_ref`.

This is the concrete mechanism behind many cross-tab interactions recovered in D04:
- Start can stop active feature loops before changing mode;
- farm/daily/etc can sync their button/status state;
- permission/plan updates can be propagated without recreating the entire app.

## 3. Permission state is shared through permission_guard

The original binary contains the shared permission API:
- `update_permissions_from_payload`
- `get_plan_status`
- `has_permission`
- `has_permission_with_limit`
- `check_account_limit`
- `is_version_locked`
- `is_plan_banned`
- `set_block_notifier`.

Recovered permission payload fields include:
- `permissions`
- `plan_tabs`
- `plan_status`
- `plan_name`
- `plan_cfg`
- `expiry_ts`
- `version_lock`
- `server_locked`
- `max_windows`
- running game/emulator counts.

This state is shared service state, not copied independently into every tab.

## 4. Main-shell permission snapshot

`TLMMainApp` also stores:
- `_perm_state`
- `_prev_limit_state`.

These are local shell snapshots used to decide whether to:
- show/hide Notebook tabs;
- enable/disable action widgets;
- rebuild/refresh selected tabs;
- avoid repeating the same UI state update when heartbeat payload has not changed.

The authoritative permission calculations still come from `permission_guard`.

## 5. Block-notifier bridge

`TLMMainApp._init_block_notifier` registers a callback through:
`permission_guard.set_block_notifier`.

The callback keeps recent:
- `last_msg`
- `last_ts`

and marshals UI notification work through:
`root.after(...)`.

Exact original documentation notes that the notifier can be called from a worker thread and must pass through `root.after` so Tkinter is not touched outside the main thread.

This is shared-state synchronization between worker/service code and the GUI thread.

## 6. InfoTab owns server/license/heartbeat state

`TLMInfoTab` fields include:
- `new_version_info`
- `server_info`
- `license_expires_on`
- `current_license_type`
- `license_key`
- `session_id`
- heartbeat host/IP/session fields
- `_heartbeat_running`
- `_heartbeat_after_id`
- `_heartbeat_interval_ms`
- `_in_heartbeat`.

InfoTab receives server payloads, updates permission_guard, and invokes `plan_update_callback` back into the shell.

Therefore server/plan/license state ownership is split:
- InfoTab = transport/session/UI service state;
- permission_guard = normalized permission/limit decisions;
- TLMMainApp = current UI application of those decisions.

## 7. Account/window limit state

`check_account_limit` is referenced from the shell and many action tabs.

The payload/service layer exposes:
- `max_windows`
- running EXE count
- running emulator count
- combined running count.

The shell uses `_prev_limit_state` to detect changes and update action-tab enable/disable state.

C06/C18 remain authoritative for Start-tab max-window sync behavior.

## 8. StartTab owns multi-window runtime state

The following are **not** TLMMainApp globals; they belong to `TLMStartTab`:
- selected master HWND
- HWND/name caches
- preview order
- preview/DWM items
- grid rows/columns
- layout/input synchronization state
- detached-preview state
- window discovery cache.

The shell retains the StartTab instance and can call it, but does not absorb its state.

This ownership boundary is critical for reconstruction.

## 9. Per-feature state remains tab-owned

Examples:
- farm/train FSM state stays in FarmTab/farm_data;
- dungeon schedule/session state stays in PhoBan modules;
- Daily state stays in DailyTab;
- login account/scheduler state stays in LoginTab;
- emulator connection/session state stays in emulator modules;
- proxy allocation state stays in forwarder/proxy modules/files.

Cross-tab references do not imply one giant shared mutable dictionary.

## 10. Persistent shared configuration is file-backed

D06 established:
- `%APPDATA%/TLMTool/settings.ini`
- central `config.ini` context
- login/forwarder/proxy runtime files
- guest JSON state.

E04 treats these as persisted state stores, not in-memory shell ownership.

E05 will recover config-management mechanics in detail.

## 11. Shared-state layering

```text
Info/server heartbeat
        ↓
permission_guard normalized state
        ↓
TLMMainApp _perm_state / _prev_limit_state
        ↓
tab visibility + enabled state + callbacks
        ↓
tab-owned runtime state

TLMMainApp
   ↔ cross-tab refs
   ↔ StartTab multi-HWND state
   ↔ feature-tab FSMs
```

## 12. Reconstruction constraints

1. Do not flatten permission_guard state into every tab.
2. Do not move StartTab HWND/preview/sync state into TLMMainApp.
3. Keep server/heartbeat session state owned by InfoTab/service layer.
4. Cross-thread block notifications must return to Tk through `root.after`.
5. Account-limit state changes should be diffed/snapshotted before expensive UI updates.
6. Cross-tab refs are intentional parity behavior; do not remove them merely to create a cleaner acyclic architecture.
7. Persisted file state remains distinct from in-memory app state.
