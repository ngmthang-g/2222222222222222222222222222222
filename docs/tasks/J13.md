## 1. Failure classes

The frozen subsystem has four materially different failure classes:

1. **pre-run reject** — no group worker is created;
2. **per-account degradation** — one target can be dropped while the rest of the group proceeds;
3. **current-group hard abort** — group cancel is set / barrier is broken / no later schedule row should start;
4. **fail-soft/log-only** — the error is logged but does not create a group hard-abort signal.

These distinctions are part of functional parity. Do not convert every error into one universal abort policy.

## 2. Start-preflight failures do not create a run

J12 exact start preflight already locks:
- permission denial: `[PhoBan] Khóa bản quyền - khong cho phep`;
- required `memory_items` import/plumbing error;
- no online target + checked schedule;
- start-all with no runnable groups.

These happen before fresh progress/cancel/thread ownership is committed.

Recovery:
- fix the external condition/configuration;
- start again manually.

There is no whole-run automatic retry at this layer.

## 3. Party-formation failures are deliberately mixed fail-open and fail-closed

When `Tạo lại đội` is enabled, J01's B0/B1/B2/B3 stage runs before account setup.

### Fail-open / degradation paths
- AutoAcceptInviteTeam write/readback problem logs warning; formation can continue.
- leave-team call/read errors are logged.
- leave confirmation timeout explicitly logs **“vẫn tiếp tục”**.
- one member whose RoleID cannot be resolved is skipped.
- after burst invite + one resend + second wait, remaining missing members do **not** by themselves fail the group; helper success remains best-effort unless cancelled.

### Hard current-group stop paths
- zero members resolve a usable RoleID;
- leader party-create exhausts `PB_PARTY_CREATE_RETRY` without a real TeamID;
- `_pb_ensure_party` as a whole returns failure/raises into the run shell.

Exact run-shell text:

`tạo đội không xong — dừng nhóm, không chạy lịch trình`.

No unrelated group is cancelled.

## 4. Account setup is a per-account filter, not automatically an all-group failure

Exact `_acc_setup` contract:

> inject DLL, keep 1366×768, wait `common.active`, click (569,67), return True when ready.

Exact failure surfaces:
- `bỏ qua: chưa inject được DLL`;
- `không thấy common.active`;
- `setup lỗi:`.

The group run owns:
- parallel `setup_threads`;
- shared `results`;
- a later `ready` local list.

The nested `_setup_one` local model is exactly:
- `nm`
- `hw`
- `ok`
- `cancel`
- `self`
- `lock`
- `results`.

This is strong static evidence that setup is recorded per account, then successful accounts form the ready subset.

Therefore:
- one/few setup failures can remove those accounts from the execution set while ready accounts continue;
- if the ready subset becomes empty, exact group log is `không acc nào online` and the group terminates before schedule rows.

Internal setup recovery:
- injection helper attempts its normal inject path;
- `_wait_active` performs a short retry window and is documented to return False after about 2 seconds;
- no automatic whole-group rerun after setup exhaustion is recovered.

A later manual group start re-runs setup.

## 5. Dungeon memory configuration is hard-fail after local retry

`_config_dungeon_memory`:
- writes SelectedFuBen / AutoRepeat=False / FollowLeader=True / AutoRevive=True;
- verifies readback;
- retries **5 times**;
- retry gap **2 seconds**;
- group/global stop exits early.

After five failures it logs the hard FAIL and returns False.

The outer dungeon flow has `_abort_cycle` in this failure region.

Outcome:
- current group hard-aborts;
- shared row barrier is broken;
- peer account workers can escape;
- other groups continue.

Recovery:
- no automatic schedule restart;
- manual fresh group start after fixing memory/panel state.

## 6. Movement is hard-fail after three total attempts

The dungeon move stage retries up to:
- initial attempt;
- retry #2;
- retry #3.

Exact failure text:

`move tới điểm hẹn FAIL (...) → dừng chu trình`.

A stop-triggered false result is not treated as a new independent failure; cancellation is already active.

A genuine exhausted move timeout/error is a current-group hard abort.

## 7. Barrier failure is a propagation mechanism, not a retry stage

Exact `_barrier_wait` contract:
- no normal timeout;
- wait until all participating accounts arrive;
- user stop or account hard failure aborts the barrier;
- aborted barrier returns False.

Thus the barrier does not invent a new retry.

Its role is to propagate:
- one account hard failure; or
- user/group stop

to peer threads so they do not remain blocked or enter the next stage.

## 8. FuBen start has its own fast local retry then hard-fails the group

Exact start stage:
- up to **5 attempts**;
- gap **0.3 s**;
- from retry #2 onward, current MapID can fast-pass if another account already pulled the party into the target map;
- transient MapID None while loading is not accepted as proof.

After retry exhaustion while still outside the target map:

`start_auto_fuben FAIL sau ... lần mà vẫn ngoài map → dừng chu trình`.

Outcome = current-group hard abort.

Thus two frozen artifacts contradict each other on **hook exception** behavior.

What remains exact:

- explicit hook return `False` aborts the current group;

What is no longer safe to claim:

## 11. Generic account worker exceptions are not proven group-hard-fatal; prior J07 overclaim is corrected

The exact `_acc_step_worker` constant surface contains:
- `_do_dungeon`;
- `_do_train`;
- `worker lỗi:`;
- doc `Worker 1 acc thực hiện MỘT bước lịch trình.`

Its local model contains:
- self/name/hwnd/item/barrier/cancel/member metadata;
- activity/name/count;
- stop_check;
- exception local.

It has **no recovered result accumulator and no `_abort_cycle` reference in the worker's own constant block**.

The row shell:
- launches one worker thread per account;
- joins those threads;
- does not collect schedule-worker return values;
- normal continuation then writes `Xong`.

Therefore a generic exception caught only by `_acc_step_worker` is best classified as:

**FAIL-SOFT / LOG-ONLY at the worker shell unless the called dungeon path already set the group cancel itself.**

This directly corrects J07's previous broad statement that any generic account-worker exception necessarily produces a current-group hard failure.

## 13. Train failure is fail-soft at schedule-row level

Exact `_do_train` failure surfaces include:
- `farm_tab_ref chưa wiring`;
- `không tìm thấy trong farm_tab`;
- `dispatch lỗi:`;
- `lỗi main thread:`.

Success surfaces:
- already training → report complete;
- `kích hoạt train OK`.

The `_do_train` local model has no group cancel ownership.

More importantly, `_acc_step_worker` does not store or inspect the return value from `_do_train`, and the row shell does not aggregate worker results.

Therefore a normal-return Train activation failure:
- logs failure/returns from that account worker;
- does **not** set group cancel;
- does **not** abort peers;
- can still allow the row batch to join and the row to reach the normal `Xong` path.

This fail-soft behavior is a parity requirement even if it looks undesirable.

A new manual schedule run is the recovery path after fixing the Train tab/account condition.

## 14. Final discard failure is explicitly fail-open to group completion

Normal completion constants are ordered:

`vứt lượt cuối (...) → xong vứt lượt cuối / vứt lượt cuối lỗi: → HOÀN THÀNH`.

There is no recovered abort surface in the final-discard region.

Therefore:
- final discard errors are logged;
- they do not convert the already-completed schedule into a hard group failure;
- group still proceeds to normal completion/teardown.

No automatic re-run of the failed final discard is recovered.

## 15. Periodic Follow / Discard / Pickup / Buff errors are feature-local

Exact error surfaces:
- Follow: `bám lỗi:`, `[Phó bản] follow lỗi:`;
- Discard: `vứt đồ lỗi:`, `[Phó bản] vứt đồ lỗi:`;
- Pickup: `bật tự nhặt lỗi:`, `[Phó bản] pick lỗi:`;
- Buff: `ghi buff lỗi:`, `[Phó bản] buff lỗi:`.

These live in separate tab-level background workers and no group `_abort_cycle` linkage is recovered from their worker blocks.

Therefore routine background-maintenance errors:
- do not abort the Phó Bản group schedule;
- affect only that maintenance attempt/worker feature.

Specific local recovery:
- Buff `_buff_ensure` retries up to symbolic `PB_BUFF_RETRY`, 1-second gap;
- Discard skips an account whose previous discard thread is still inflight;
- Pickup/Follow/Discard/Buff can be rebuilt by later tick/run lifecycle according to their already-frozen worker rules.

Exact survival of each outer worker after an uncaught top-level worker-cycle exception remains a thread-microbehavior item; the important J13 blast radius is that no schedule-group abort is wired.

## 16. Failure blast radius is current group unless the user explicitly invokes global stop

Hard dungeon/party failures use:
- current group's cancel;
- current row barrier.

J07/J11 exact contract:
- Group A can fail;
- Group B/C continue;
- only final active group completion triggers global teardown.

The global `_cancel` is reserved for stop-all/public `stop()` semantics, not ordinary one-group gameplay failure.

## 17. Row and button outcome model

There is still no Error/Failed/Cancelled row style.

Only:
- `Chưa`
- `Đang`
- `Xong`.

### Hard-abort row
The row is set `Đang` before account workers launch.

When a dungeon hard failure sets group cancel and aborts the barrier:
- future schedule rows are not supposed to start;
- group winds down;
- button passes through stopping/idle lifecycle.

Exact timing of the final `Xong` assignment against a late cancel remains the J07 explicit UNKNOWN. Do not invent a red failure row.

### Train / generic worker fail-soft row
Because no group cancel/result aggregation is produced by a normal fail-soft worker return, the outer row can join and reach `Xong`.

This distinction must be preserved.

## 18. Automatic recovery exists only inside individual stages

Recovered automatic retry/repair loops:

| Stage | Automatic recovery |
|---|---|
| Party create | `PB_PARTY_CREATE_RETRY` attempts |
| Party invite | one resend of missing members + second wait |
| Setup active pixel | short retry window, documented ~2s |
| Dungeon memory config | 5 attempts × 2s |
| Movement | 3 total attempts |
| FuBen start | 5 attempts × 0.3s |
| Cycle auto-FuBen verification | can re-enable when pixel says OFF |
| Buff setting | `PB_BUFF_RETRY`, 1s gap |
| Pickup | periodic readback/repair every PICK_POLL |
| Follow/Discard/Buff | periodic lifecycle according to each worker contract |

No recovered automatic **whole-group schedule restart** exists after a hard group abort.

## 19. Manual recovery is fresh-start recovery

After hard abort/stop:
- current run winds down;
- identity-safe `_finish_group_run` removes only matching old state;
- group becomes startable again;
- new start resets that group's progress;
- new cancel/job identity is created;
- setup/config stages are attempted again;
- persisted Follow/Discard/Pickup/Buff mode selections remain available for re-arm.

This is the intended recovery boundary.
