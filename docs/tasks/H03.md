## 1. Bag fullness is based on occupied Site-10 slots

FarmTab owns `_get_bag_slots`.

Its exact original documentation says:

`Số ô túi đồ đang dùng (Site 10) — None nếu đọc lỗi (giữ giá trị cũ).`

The helper directly calls:
- `memory_items.get_bag`
- reads the returned `slots` field.

Therefore the Train bag metric is:

**number of currently occupied inventory slots at Site 10**

—not free-slot count and not total item quantity.

This matters because stack quantity does not increase the occupied-slot metric unless it occupies another slot.

## 2. Shared get_bag source and failure boundary

The frozen shared bag layer documents `get_bag` as:

`Tổng hợp túi Site 10 + enrich tên. Trả dict hoặc None.`

The returned bag dictionary surface contains:
- `slots`
- `distinct`
- `total_qty`
- `non_bag`
- `info`.

Its underlying reader handles Site 10 bag rows and exposes item records with:
- dbID
- itemID
- site
- pos
- qty.

FarmTab uses only `slots` for the row bag counter/fullness-related display path.

Read failure at the FarmTab display helper boundary is:
- `None`
- keep the prior displayed row value rather than overwrite it with a fake zero.

## 4. _filter_before_town is the shared Train discard stage

Exact original documentation:

`Lọc đồ theo radio Nhặt đồ (preset bag_filter train) — dùng chung
        cho mọi đường về thành / đầy túi.
        Trả slots_after (int) hoặc None (= không lọc: radio Tất cả / lỗi).
        Hiện label tím trong lúc vứt; xong trả state cũ (nếu không ai đổi).`

Direct flow:
1. obtain active pickup preset keys through `get_pickup_preset_keys`;
2. temporarily set row state to `Đang lọc đồ`;
3. call shared `bag_filter.discard_for_activity`;
4. activity = `train`;
5. pass the Farm cancellation `stop_check`;
6. return current occupied-slot count after filtering when measurable;
7. restore the previous row state if no other actor changed it.

## 5. “Tất cả” / no-discard and error semantics

The helper doc explicitly defines its result:
- integer = filtering ran and the post-filter slot count was readable;
- `None` = no filtering because the pickup radio means keep everything, **or** a filter/read error prevented a usable post-filter count.

Thus `None` must not be fabricated into:
- zero slots;
- “bag cleared”;
- “still full”.

It is an unknown/no-filter result at this helper boundary.

The lower-level bag_filter module also documents that empty preset/rule selection performs no discard, and filtering is opt-in.

## 6. never mode — full bag still filters, but does not return town

H02 locked `never` as `Không về`.

The Farm cycle contains exact logs:

- `túi đầy (<slots> ô, Không về) → lọc`
- `lọc xong vẫn đầy (<slots> ô) → ở lại (Không về)`.

Therefore when the fullness predicate triggers in `never` mode:

1. Train does **not** immediately enter the town-return path;
2. it first invokes `_filter_before_town`;
3. when a readable post-filter slot count is still full, it explicitly stays in place;
4. it does not override the user's `Không về` choice just because inventory remains full.

If filtering frees enough slots, the full condition is no longer present and Train can continue its farm loop rather than forcing a town trip.

If `_filter_before_town` returns `None`, H03 does not invent a post-filter slot count; `never` still cannot authorize an automatic return-town action.

## 7. full_bag_timer / legacy full_bag — bag fullness can end the wait early

H02 proved the active/current value `full_bag_timer` and legacy compatibility alias `full_bag` are treated as one bag-enabled family.

The Farm cycle contains:
- tuple/family surfaces `full_bag_timer` + `full_bag`;
- nested `stop_bag_check`;
- `MI.is_full_bag`;
- exact log suffix `<slots> ô) → về thành`.

This locks the interaction:

1. in the bag-enabled mode, the common farm wait installs a bag-stop predicate;
2. `stop_bag_check` polls the dedicated fullness helper;
3. when fullness is reached, the wait can terminate before the normal periodic duration;
4. the cycle transitions to the return-town path;
5. the shared pre-town filter remains available before town processing, per `_filter_before_town`'s exact “mọi đường về thành / đầy túi” documentation.

The actual polling/timer cadence belongs to H04 unless directly required for the bag predicate itself.

## 8. cycle mode does not use bag fullness as its early-stop condition

H02 already locked:
- `cycle` = periodic mode;
- no full-bag early-stop branch from the `full_bag_timer/full_bag` family.

H03 preserves that boundary.

This does **not** mean the bag is never displayed or never filterable in cycle mode. The same bag data and shared pre-town filtering infrastructure can still exist; it only means “bag became full” is not the condition that ends the cycle wait.

## 9. Post-filter recheck is behaviorally significant in never mode

The exact `never` log sequence proves Train checks the post-filter result rather than assuming discard succeeded.

That prevents two incorrect reconstructions:
- always stay even if filtering freed slots;
- always return town after a full-bag event.

The correct no-town behavior is state-based:
- full detected;
- attempt configured filter;
- evaluate post-filter fullness if a count is available;
- remain in no-town policy.

## 10. Filtering source is the Train pickup preset, not the sell-equipment checkbox

`_filter_before_town` calls:
- `get_pickup_preset_keys`
- shared `bag_filter`
- activity `train`.

Its documentation explicitly says the source is the **Nhặt đồ radio/preset**.

Therefore this pre-town discard stage is separate from:
- `sell_equip_var`;
- town shop selling;
- sell-tab selection.

H03 does not merge discard filtering with the later sell workflow.

## 11. Cancellation and UI-state behavior

`_filter_before_town` passes the Farm `stop_check` into the shared discard worker.

Thus a user/global Farm stop can interrupt the discard stage.

While filtering:
- row state temporarily becomes `Đang lọc đồ`;
- after completion, the prior state is restored only if another concurrent actor has not already changed it.

This avoids clobbering a newer state such as stop/reconnect/death handling.

## 12. Runtime fullness-read failure remains explicit

Two failure boundaries are statically clear:
- `_get_bag_slots` returns `None` on bag read failure;
- `_filter_before_town` returns `None` when no filtering is performed or post-filter state cannot be read.

However, the readable static FarmTab constants do not expose the internal implementation of `MI.is_full_bag` well enough to prove its exact return value on a low-level read failure.

Therefore:
