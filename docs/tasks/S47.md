## Confirmed S46 failure
- `F09ReadOnlyTabLifetime.finish_close(timeout)` delegates to `F09ScheduleEvaluationWorker.shutdown(timeout)`, which uses `stop(timeout)`.
- Before S47, `stop(timeout)` could wait **without a time bound acquiring `_lifecycle_lock`**, then apply timeout only to `Thread.join`. If a separate stop caller held the lock after joining the old worker but before cleanup, `finish_close(timeout=0.02)` could wait arbitrarily long. Although not called on Tk main thread, this violates the API's bounded cleanup contract and can cause hangs.
- Second real race: a stop request while `_start_locked()` was blocked in a caller-supplied `now()` source could be erased later by `_cancel.clear()`, potentially rearming the worker, especially when stop timed out acquiring the lifecycle lock.

## Narrow code changes
- `src/login_schedule_worker.py` S47:
  - use monotonic deadline `deadline=monotonic()+timeout`;
  - always signal `_cancel.set()` and `_stop_requested.set()` **before** attempting lifecycle lock;
  - acquire `_lifecycle_lock` with **the remaining timeout**, and `Thread.join` with **whatever budget remains**. If mutex acquisition or join expires, return False promptly and retain a STOPPING cancellation fence;
  - upon successful completed cleanup, clear the pending-stop fence to allow a later explicit legitimate restart. Preserve permanent closure on shutdown;
  - verify `_stop_requested` after the external clock source, after `_cancel.clear()` and after worker thread-start call, preventing a delayed start from replacing an in-flight stop.
- `src/login_schedule_lifetime.py` S46 is preserved untouched; its `finish_close(timeout)` now inherits the corrected total budget without touching Tk. Existing S46 `request_shutdown()` still never blocks GUI.
- No account settings writes, no F09 opaque flags interpretation, no real Login scheduler controls, no dispatch of due event actions.
