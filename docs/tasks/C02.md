## 1. The mapping has three identity layers

The original does not treat the window title as the character identity.

Verified layers:

```text
HWND
↓
PID snapshot
↓
memory_reader.Reader(PID)
↓
RoleName (+ HP / Level / Map / position ...)
```

### Layer A — physical UI handle
The row/list anchor is **HWND**.

Original Phó Bản documentation states:

`Track theo hwnd (như farm_tab) — khi đọc được tên thật thì đổi label;`

and:

`window đóng → row bị xóa nên không còn dòng window default kẹt lại.`

It also explicitly says stale rows are removed when:
- the window is closed; or
- the window has changed process because an HWND value was reused.

Daily/Farm/Party/Phó Bản/Rao/Tối ưu/TrainLSV all contain the same PID-change reconstruction path.

### Layer B — process generation guard
Each row keeps a **PID snapshot** for its HWND.

Daily's original documentation states:
- the row snapshot is stored by HWND;
- the HWND must still belong to the bound process;
- if `IsWindow` still succeeds but the PID differs, the HWND has been reused.

The `mouse.py` identity layer makes this global:
- `bind_window_identity(hwnd, pid)` records HWND→PID when a row is created;
- falsy PID is ignored;
- `unbind_window_identity(hwnd, pid)` removes only the matching snapshot when PID is supplied;
- this prevents one tab from removing the protection belonging to another tab that tracks the same HWND;
- `_identity_matches` returns false when current PID differs from the stored snapshot.

So the safe physical identity is effectively **HWND + PID generation**, not HWND alone.

### Layer C — logical character identity
`utils.get_character_info(hwnd)` converts HWND to PID and reads the game process memory.

Verified returned fields include:
- `RoleName`
- `CurrentHP`
- `MaxHP`
- `Level`
- `MapID`
- `PosX`
- `PosY`
- additional memory-reader fields

`_format_char_info`:
- calculates HP%;
- strips HTML tags from `RoleName`.

The resulting sanitized `RoleName` is the logical/display character identity used by account rows and persisted per-character settings.

## 2. Exact HWND → PID → Reader path

Original `utils.py` contains:
- `_GetWindowThreadProcessId`
- `_get_pid_from_hwnd`
- documentation: `Lấy PID từ HWND window handle dùng ctypes.`

Then:

`get_character_info(hwnd)`
→ resolve PID
→ obtain shared Reader for that PID
→ `Reader.read_all()`
→ format character dict
→ sanitized `RoleName` + HP% + level/map/etc.

The Reader cache is explicitly **PID-keyed**.

Original documentation:

`Dùng shared Reader cache: mỗi PID chỉ OpenProcess + EnumModulesEx 1 lần.`

Subsequent reads reuse the handle/pointer chain and do lighter `ReadProcessMemory` work.

Reader cache refresh:
- **10 seconds**
- documented as protection around game restart / PID reuse.

## 3. Reconnect invalidation

The original has `invalidate_character_cache(pid)`.

Documentation says it is called immediately after successful reconnect because:
- after reconnect/reloading the character, the memory layout can differ;
- next read must re-resolve the pointer chain rather than consuming the old Reader cache until the 10-second TTL expires.

Therefore logical identity is not allowed to remain indefinitely tied to stale memory pointers after reconnect.

## 4. Row creation / update / stale destruction

Verified account-row behavior:

### New HWND
1. discover HWND;
2. read current PID;
3. bind HWND→PID identity;
4. read character info from memory;
5. create row keyed by HWND;
6. show real sanitized RoleName when available.

### Same HWND + same PID
- keep the existing row;
- refresh character data;
- update the label when the real name becomes available.

This is why a row can initially exist before valid RoleName is available.

### Same HWND value + different PID
Original logs across multiple tabs state:

`hwnd=... đổi process (pid ... → ...) — cửa sổ cũ đã mất, tạo lại row mới`

Party/Phó Bản say the old member is removed.

The old row is:
- stopped/removed from active state as applicable;
- identity unbound using its old PID;
- widget destroyed;
- recreated from fresh current process/character data.

This directly prevents Windows HWND reuse from silently reassigning old account state to a new game process.

### Closed HWND
Incremental refresh removes the stale row.

Phó Bản states:
`Xóa acc của window đã đóng HOẶC đã đổi process (HWND tái sử dụng).`

## 5. Placeholder before a real character name is readable

The compiled account-tab helpers contain:
- `RoleName`
- a `Window ` fallback prefix;
- Phó Bản's explicit statement that when the real name is read the label is changed, and closed windows remove the default-window row.

Therefore a temporary **window placeholder identity** exists before memory yields a valid RoleName.

### Explicit unknown
The readable compiled constant table does not prove the exact suffix formatting after `Window ` in every tab, so C02 does not invent whether it is precisely HWND, title, index, or another value.

The important verified behavior is:
- placeholder first if necessary;
- real RoleName replaces it when memory is ready;
- physical row remains HWND/PID guarded.

## 6. Persistent config identity is character name, not HWND

This is explicitly documented in the original.

Tối ưu:
`Khôi phục combobox Giảm cấu hình đã lưu theo tên nhân vật (hwnd đổi mỗi lần mở game nên key theo tên — giống farm/donvang/train_lsv).`

Rao:
`Khôi phục 4 combobox nội dung rao đã lưu theo tên nhân vật.`

Farm/Đồn/Train-LSV likewise contain per-character coordinate/config restore paths by character name.

Therefore:

```text
runtime row key = HWND (+ PID snapshot)
persistent account-config key = sanitized character name / RoleName
```

This separation is intentional because HWND is not stable across game restarts.

## 7. Start preview mapping

The Start subsystem contains:
- `_preview_windows_cache`
- `_preview_info_cache`
- background worker reading windows + character info;
- preview items carrying `src_hwnd`;
- cached fields `RoleName` and `HpPercent`;
- `_refresh_preview_labels`;
- documentation: `Cập nhật tên nhân vật từ cache worker thread.`

This establishes the preview-side association:

```text
preview src HWND
↓
worker character-info cache
↓
RoleName / HP / Level / Map
↓
preview header/labels
```

Start's auto-tile logic also states that game windows are sorted by **character name**, with the master window forced to the first position.

### Structural note
Readable static evidence proves the HWND-bearing preview items and separate character-info cache, and proves that names are refreshed from that worker cache. The exact Python subscript expression of `_preview_info_cache` is not source-level visible; C02 does not fabricate source syntax.

## 8. Fake/debug accounts are a separate namespace

`utils.py` contains:
- `FAKE_ACCOUNTS`
- random fake `RoleName`, HP%, level
- documentation: add fake account and return a **fake HWND**.

These synthetic handles are test/debug compatibility data and must not be treated as physical EnumWindows HWND↔PID mappings.

The identity layer deliberately allows compatibility behavior when no PID binding exists, which is consistent with test/fake rows.

## 9. Safety consequence for later actions

The mapping is not display-only.

The strict target resolver in the action layer checks the stored HWND/PID identity and rejects a reused HWND:

`hwnd=%s đã bị tái sử dụng bởi process khác (lệch pid snapshot) → từ chối, không bấm`

Therefore a stale UI row cannot simply direct clicks to a new process that inherited the same numeric HWND.

```text
EnumWindows candidate

↓

↓

├─ sanitized RoleName
├─ HpPercent
├─ Level
├─ MapID
└─ position / other fields
↓
runtime row remains keyed by HWND
↓
visible label becomes RoleName when valid
↓
persistent tab config restored by RoleName
```

Refresh guard:

```text
same HWND + same PID
→ update existing row/info

same HWND + different PID
→ HWND reused
→ remove old row
→ unbind old identity
→ create/bind fresh row

HWND closed
→ remove stale row

reconnect succeeded
→ invalidate Reader cache(PID)
→ next character read resolves fresh pointer chain
```
